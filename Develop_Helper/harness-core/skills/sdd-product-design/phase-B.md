# 阶段 B：界面风格与按需原型

新建项目在阶段 A 与七层技术方案完成后进入。以已确认 PRD（路径：`<active_project_path>/docs/PRD.md`）和技术方案（路径：`<active_project_path>/docs/tech-spec.md`）为输入，先核对主流程、角色交接、接口数据、等待和失败行为已明确，并定向检查 PRD 的“流程图与时序图”章节已同时具备流程图、技术细化后的时序图且与已确认方案一致，再设计界面。缺图先返回七层技术方案的交接步骤补齐；图暴露关键歧义时返回对应阶段对齐。关键分支仍待讨论时返回对应阶段澄清，不用页面代替产品决策。已有项目仅调整视觉时复用既有确认，不因历史缺图而重跑需求与技术方案；流程发生变化时仅更新受影响的图与文字；不重新选择开发规范集。

## 工作步骤

1. 按需求确定本次必要的页面与交互，关联对应的 REQ / AC（旧项目沿用原 ID）。页面功能、关键文案和业务状态写入 PRD（路径：`<active_project_path>/docs/PRD.md`）的“界面约定”，不在此划分开发 Feature。
2. 读取 [设计风格 Skill](../ui-design-standard/SKILL.md)，由它分析目标、提取设计要素、归纳风格并形成项目 `docs/ui-style.md`（路径：`<active_project_path>/docs/ui-style.md`）。文档包含设计判断、全局视觉，以及每页布局、组件、状态和具体示例；业务要求引用 PRD，PRD 链接该文档，不复制视觉取值。已有已确认文档时只更新受影响部分。
3. 需要可视化确认交互、存在重要视觉要求或用户要求原型时，使用当前可用工具按风格文档制作原型，存入 `docs/prototypes/`（路径：`<active_project_path>/docs/prototypes/`，交付时列出实际文件名）；将实际页面锚点链接到 PRD 和风格文档。简单界面可以只交付风格文档与页面说明，不为完成流程强制制作原型。
4. 实现时区分共用应用外壳与独立页面。互斥导航同一时刻只显示当前页面，隐藏页面不得占位；首次打开、刷新与切换后的地址、选中导航和内容一致，并遵守已定义的登录行为。明确顶栏、侧栏、内容区和底部操作区的高度及滚动归属，长内容不得挤掉输入区或遮挡消息；核对隐藏机制与布局样式不会冲突。
5. 原型可以使用模拟数据，但主流程必须可操作且状态一致：按钮触发后显示相应结果，跨页面的同一记录同步变化，空输入不得伪造成功。普通发送、草稿确认等操作按当前状态组织，不同时堆放含义重叠的主按钮。不能用弹窗说明代替核心操作结果，也不能把未实现控件伪装成可用；演示限制明确说明，不扩建真实后端。
6. 按下述检查完成实际验证。简单界面无需制作原型时，只报告设计文档检查结果。

## 原型交付检查

使用当前可用且允许的浏览器工具，先检查功能与布局，再调整视觉：

- 逐个直接打开原型页面地址或锚点、刷新并切换导航，确认登录或预览行为符合约定、导航与页面一致、非当前页面隐藏且不占位。
- 在设计基准视口及约定的适配宽度下查看实际画面；用长文本和足量列表检查滚动、内容截断、输入区位置、遮挡与溢出。不能只在文档中声明响应式而不检查原型。
- 实际完成主流程和关键失败场景，检查输入校验、等待、成功、失败与跨页面结果；不以“按钮能点击”代替流程完成。
- 核对每页的信息层级、主要操作、组件一致性和产品文案，避免只优化主页面。修正发现的问题后复查受影响页面。

在风格文档的验收部分（路径：`<active_project_path>/docs/ui-style.md`）简记检查过的页面、视口、操作、结果和未验项，不额外生成过程报告。HTML 已生成、源码检查或 DOM 检查均不能代替视觉验收；用户截图仅证明其展示状态。工具不可用或访问被阻止时不绕过限制，明确哪些画面和交互未验证，不宣称验收通过。

## 完成与交接

将本轮风格文档和已有原型共同提交确认一次，不重复确认未改变的需求或技术选择。风格不增加业务能力；发现范围、权限、验收或接口契约变化时，仅返回对应需求或技术方案章节更新并对齐，再完成受影响设计。

用户确认后将本轮设计文档标为 `Confirmed`，进入 [开发循环](../../protocols/development-loop.md)，由主智能体实际派发 Planner 并取得实例标识；读取 planner.md 或主会话直接写任务不算派发。只有 Planner 返回且计划核对完成后才派 Developer；已有任务只调整受影响部分，不重新创建全套任务。后续只回到受影响的界面与验收部分；风格文档、原型有冲突时先对齐，不让开发或测试各选一份。
