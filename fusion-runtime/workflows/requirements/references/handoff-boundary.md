# 需求角色的技术设计交接边界

更新日期：2026-10-30。本文只规定需求角色在“请求技术设计”分流中可以说明什么、不能做什么；不实现主 Agent、方案角色、确认写入或交接执行。业务方法以 [solution-design](../methods/develop-helper/harness-core/skills/solution-design/SKILL.md) 为技术设计入口，需求侧规则以 [requirements.md](../requirements.md) 为准。

## 1. 依据齐备的条件

只有下列条件同时成立，才把当前 PRD 视为可进入技术设计的依据：

- 当前 `docs/PRD.md` 存在且可读，其记录的来源需求版本已与当前 `docs/requirements.md` 核对，差异已说明；
- 恢复读取返回的 PRD 确认核验为 `valid`：确认记录属于本项目，针对当前 PRD 的同一内容摘要与登记版本，用途精确等于“形成技术方案”，没有未决阻塞项，登记引用与确认快照一致；
- 报告中列出实际依据的 PRD 版本、需求版本与确认记录 ID。

## 2. 互相独立的事实

以下事实互不替代，也不自动串联：

1. **Draft**：保存工具写入的需求或 PRD 草稿；保存成功和结构检查通过都不是确认。
2. **登记**：成果路径与版本已登记；登记不等于用户同意任何用途。
3. **正式确认**：持久记录中用户对已展示版本允许的具体用途；需求角色只读核验，不写入、不补造。
4. **交接**：准备、发送、接收核验是另外的 Main／宿主动作；需求角色不创建、不发送、不核验交接记录。

对话中的“可以了”“确认”、截图、转述或 Agent 自述都不是正式确认。

## 3. 需求角色在分流中的行为

- 依据齐备时：指明技术设计方法入口和上述依据版本，由用户或调度方决定是否、由谁开展技术设计。
- 确认为 `missing`、`outdated`、`invalid` 或 `unavailable` 时：按实际状态与原因说明缺口和补齐条件，只处理缺口涉及的需求内容。
- 已有技术方案时：携带方案正文实际记录的 PRD 版本说明差异，不代为修改方案。

需求角色**不得**：保存 tech-spec 或方案文件；启动 Solution Designer、子 Agent 或上游全流程；派发任务或发送交接消息；写确认、登记或交接记录。上游方法正文中关于自动生成方案、派发后续角色或启动子 Agent 的步骤，在本角色中只作为方法背景，不作为执行指令。
