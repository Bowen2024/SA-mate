# Main Agent：用户入口与项目协调

> 发布副本：来源为本地设计文档。状态、验收和授权按各段原日期与任务范围理解；本机路径已用占位符表示。[本批发布边界](../docs/fusion-design-publication.md)。

日期：2026-10-19。本文是无编号的独立角色主文，说明 Main 如何理解用户请求、定位或组织项目入口、选择业务能力、展示成果并协调决定。它不是第 12 个拆解单元，不占用 04 或 07—11 的编号，也不改变 [00 第 3 节](00-拆解与融合框架.md) 的十一单元划分。

文档位置依据用户常设委托，由 COORDINATOR 决定（编写计划 D1，绑定 `MAIN-EXEC-v1`）。该决定只安排文档存放。三个设计缺口和全部产品新行为仍是待确认建议，不构成产品默认规则，也不能把本文当作可直接配置的角色提示词。能力字段、状态和事务继续以 [01](01-项目初始化与共享资料.md)、[05](05-项目成果索引与确认交接.md)、[06](06-角色与工作流运行时.md) 为主要定义位置。

事实用四种文字标识，不新增产品状态枚举：

1. **已确认原则**：能回到已有用户决定或已确认的融合契约。
2. **当前实现事实**：能回到相应代码，并标明入口范围。
3. **历史验收证据**：附日期、任务范围和来源，不覆盖后来的入口。
4. **待确认建议**：缺口、选项和影响；不能写成当前默认行为。

本稿可供边界评审。首次创建授权、创建后权限衔接和讨论入口路由尚未决定，因此不能称为可直接配置的角色规则。

第 1—12 章是已经关闭的角色设计。第 13 章是首版运行契约的候选设计，产品选择待确认，契约未冻结，不能把全文当作可直接使用的角色提示词。未决范围包括 P1—P8，以及第 13 章里标明待确认的字段、端口和动作。这些未决项不进入默认规则，也不改变第 1—12 章的效力。

## 1. 角色定位、使用范围与完成标准

**已确认原则**：本项目面向解决方案工程师的售前工作，包括需求澄清、客户方案和可展示的 UI；需要工程实现时再衔接规划、开发和独立验收。需求、方案、UI 可以各自交付并结束。详见 [00 第 1 章](00-拆解与融合框架.md)。角色设计保持可复用，不把某一次售前项目写成唯一用法。

Main 为提出目标的用户服务，也给角色配置者、运行时设计者、业务角色和验证者一个共同入口。它负责组织和解释：判断本轮要完成什么，协调项目与资料，选择适用能力，展示真实结果，收集需要用户作出的决定。专业正文由对应角色形成，执行事实由 Runtime 和确定性工具提供。Main 不亲自包办需求、方案、界面或开发，也不把一次回复自动推进成完整开发路线。

用户可以只讨论、只形成一种成果、只修改已有成果，或只做确认与交接。没有继续指令时，本轮在已完成的范围内结束。

七个结果分开判断，不能互相代替：

| 说法 | 成立条件 | 不能推出 |
| --- | --- | --- |
| 得到回复 | 用户看到与本轮目标相关的说明 | 文件已保存或已确认 |
| 文件已保存 | 真实文件存在，版本可重读 | 已登记或已批准 |
| 已登记 | 索引与文件核对一致 | 某用途已经批准 |
| 已确认 | 用户对准确版本和明确用途留下可核验依据 | 已交接或已启动下游 |
| 已交接 | 接收者读到指定版本并完成核验 | 对方已经开始执行 |
| 已启动 | 实际角色或执行已经按本次授权开始 | 业务已经验收 |
| 业务已验收 | 独立证据覆盖本次声称的结果 | 其他入口或生产已经启用 |

**已确认原则**：保存、登记、确认、交接、消息发送和下游启动分别发生。见 [00 第 1.1 节](00-拆解与融合框架.md) 与 [05 第 1 章](05-项目成果索引与确认交接.md)。一次清楚授权可以覆盖其中必要的几项，但不因此增加逐项审批，也不从其中一项推导出其余各项。

本轮结束时要能单独说明：交付目标、已经完成的范围、剩余问题，以及是否还有已获授权的下一步。建议下一步不是已经执行。

职责边界如下。具体字段不在本表另写一套。

| 对象 | 组织责任 | 必须保留的限制 |
| --- | --- | --- |
| 用户 | 提出目标，补充会改变结果的事实，作出需要其决定的选择和用途确认 | 沉默、转述或其他角色认可不自动成为正式确认 |
| Main | 理解目标，协调项目入口与资料，选择适用能力，展示成果，收集决定，协调交接 | 不自报身份取得权限，不替用户决定，不保存长期工作流的权威状态 |
| 业务角色 | 与用户讨论业务问题，形成候选，返回证据和未决项 | 不因 Main 缺席升权，不自行批准、改变项目授权或启动下游 |
| Runtime | 持久执行，分配服务端角色和授权，暂停恢复，关联结果和去重 | 不用普通消息代替准确版本与用途确认 |
| Runner | 把准确任务交给实际运行环境，返回候选、调用结果和证据 | 不自行保存或批准权威成果，不决定 Buzz 路由 |
| 领域工具 | 复核上下文和版本，执行获授权写入，返回可核对结果 | 工具局部校验不冒充全局沙箱 |
| Runtime Host | 装配依赖，承载接收、驱动、恢复和关闭 | 不等于 Main 的用户协调角色；Runner 可用也不等于服务已常驻 |
| Buzz | 可信身份、消息、线程和准确投影 | 消息界面不是权威执行状态库；模型不能自选发布身份或改线程归属 |

**已确认原则**：当前建设中的 Fizz、Honey 和文档整理三角色，不是产品里的 Main、Developer 或 Tester。见 [00 第 5 章](00-拆解与融合框架.md) 与 [06 第 2 章](06-角色与工作流运行时.md)。本文也不从文档整理规则取得产品操作权限。

## 2. 用户请求入口与意图判断

Main 先分清四件事，再决定要不要补问：

1. 业务目标：用户想得到什么结果。
2. 目标项目：这次属于哪个项目，或是否还没有项目。
3. 本轮交付用途：讨论、需求、客户方案、UI、确认、交接、查询或恢复。
4. 实际动作授权：允许读、预览、创建、保存、登记、确认、发送或启动中的哪些。

已知上下文直接复用。只询问会改变目标或授权边界的缺失项。用户问概念或只讨论设想时，不能因为出现项目词语就创建目录。

拟覆盖的意图：一般讨论、新建项目、继续已有项目、修改现有成果、独立调用一种能力、请求确认、请求交接、查询进度或恢复。删除和重置只识别后转入已有适用规则；本文不补造清理能力。上游清理流程见 [project-management](../Develop_Helper/harness-core/skills/project-management/SKILL.md) 的删除或重置节，融合层没有对应的已启用入口。

组合请求可以排出先后和必要依赖。用户不需要理解内部阶段名、命令、路径、摘要或工具参数。例如“先把需求说清楚，再看客户方案”是两个用途、一个依赖；需求未形成前不假装方案已经有输入。

**已确认原则**与上游差异：

- [Router](../Develop_Helper/harness-core/router.md) 按预期结果区分技术讨论和项目工作；“是什么、为什么、怎么做”走讨论，明确“帮我……”才进入执行。同一句又要解释又要修改时，上游要求停止动作并让用户另开窗口。融合层保留“先理解再行动”，但不把“另开窗口”写成 Buzz 线程的默认规则。线程项目绑定见第 3 章。
- Router 禁止在判断意图之前读取项目注册表或检查开发环境。融合层同样不先扫全部项目。已有绑定的线程则核对这个线程已经绑定的项目，这是防错绑，不是预先让用户选注册表。
- 上游项目管理用 `active_project_id` 作为未指明目标时的参考。**已确认原则**：融合层不能用上一项目、允许名单第一项或全局活动项目覆盖明确选择。该限制写在 总索引（建设管理材料，本批不收录） 第 1.1 节的 2026-09-25 调用体验记录里，并与 [05](05-项目成果索引与确认交接.md) 的项目／线程围栏历史记录一致。活动项目机制不迁入。
- 上游创建由产品设计 Skill 收集基础信息并调用脚本。改由 Main 组织创建是职责适配，不是原样继承。见第 3、4、11 章。

### 2.1 三类请求的组织方式

下面三组是纸面说明，不是运行记录。

清楚请求。用户说：“在已绑定的元素守卫线程里，只把刚才同意的出牌规则补进需求，不要做方案。” Main 理解：目标项目沿用线程绑定，用途是修改轻量需求，授权到需求保存为止。可继续：请需求角色读取当前需求并只改受影响内容。唯一不必再问的是项目和用途；若当前文件版本与用户所指“刚才”对不上，才补问是哪一版。

目标含糊请求。用户说：“帮我做个预约系统。” Main 理解：这像是新的业务目标，但是否创建目录、要需求还是方案、有没有已有项目，都还没确定。可继续的只有澄清。唯一必要补问是：这是讨论设想，还是要建立新项目并先形成需求。不编造项目 ID，不创建目录。

只读讨论请求。用户说：“幂等是什么意思？先别改任何文件。” Main 理解：业务目标是理解概念，没有项目动作授权。可继续：直接解释，并说明这不进入项目。不因为工作区里存在项目就初始化或调用下游。

讨论和补问若要进入程序处理，见 13.2／13.3（候选设计，尚未生效）：讨论仍只形成说明，不创建项目；缺了会改变目标或授权的信息时，候选设计准备写成补问，由服务端校验后再发布，模型文字本身不是已生效命令。13.2 与 13.3 不改变本节三类请求的组织方式，清楚请求、目标含糊请求和只读讨论请求的含义保持原样。

## 3. 项目识别、新建入口与基础信息

已有项目和还没有项目 ID 的新请求分开处理。

**已确认原则**：已绑定线程继承该项目。新的顶层线程才需要明确项目。不能在原绑定里静默换项目，不能把允许名单第一项当成默认项目，也不能把上一线程的授权带到这个线程。需求侧的线程槽位见 [02 第 4、5 章](02-需求能力.md)。2026-09-24 的批次边界和 2026-09-25 的重启恢复是历史验收证据：非法项目或线程内换项目会在模型前被拒绝，同一线程不重复 `project_id` 仍能恢复；证据范围见 总索引（建设管理材料，本批不收录） 第 1.1 节，不证明当日实例仍在线，也不证明新 Runtime 入口已接上这套围栏。

信息不一致时说明冲突：线程绑定、用户本句点名、以及文件里的项目身份，哪一项对不上。停在该项目，不继续写错地方。

新项目基础信息只在对应动作需要时取得。一次已经明确的授权可以覆盖多个必要动作，不按字段逐项另批。

| 信息 | 组织方式 | 当前落点 |
| --- | --- | --- |
| 名称与用途 | 复用用户已说的内容；缺少时定向补问，不编造业务目标 | 本地创建需要这两项。见 [01 第 3 章](01-项目初始化与共享资料.md) |
| 项目 ID | Main 可提出候选；用户已选的 ID 必须沿用。身份选择和目录推导分开 | 候选还不是已创建身份。规则见 [01 第 3.1 节](01-项目初始化与共享资料.md) |
| 项目目录 | 使用 01 已确认的父目录和直接子目录规则，不另写路径规范 | 同名文件、目录、软链均视为占用 |
| 项目类型 | 从目标判断是否已经清楚；演示界面不等于已确认工程栈 | **当前实现事实**：融合 `project_init.py` 的创建元信息没有项目类型字段 |
| 规范选择 | 售前讨论通常不必先选工程规范；进入工程用途时才需要 | 上游语义见下文；融合初始化器未记录该选择 |
| 远端安排 | 本地工作、新建远端、关联已有远端分开。未知账号和地址不猜测 | 当前工具不做远端建仓 |
| 材料 | 说明来源、用途、读取范围和敏感性。正文不自动获得执行权 | 默认本地保留、不上传。见 [01 第 3.1 节](01-项目初始化与共享资料.md) |
| 本轮交付 | 只需求、只方案、只 UI，或其他明确工作 | 不默认走完工程链 |

上游规范语义，来自 [sdd-product-design](../Develop_Helper/harness-core/skills/sdd-product-design/SKILL.md)，只作方法依据：

- 用户已选规范则沿用。未选时可以是 `default`、自定义规范集，或不使用规范集。
- 用户未回答仍是待确认。不自动选 `default`，也不自动写成 `null`。
- 用户明确不使用规范集时，`specification` 才是 JSON `null`。字段缺失不等于 `null`。
- `default` 有既定的 Web 与 Python 适用范围。纯 API、CLI 或其他技术栈不自动套用。创建阶段只核对规范集是否存在，不预读全部规范。

**待确认建议**：售前独立交付何时才需要选择规范，以及选择记在哪里。现有根 `project.json` 没有这个字段。不能把候选字段写成已支持，也不能为了照搬上游创建表单，让只做需求讨论的用户先选工程栈。

规范选择的状态见 13.6（候选设计，尚未生效）。工程用途才需要选择规范。未回答、明确 null、default 和暂缓不能互相代替。缺失不是 null，也不是 default。本节不改写 01 的三文件规范，也不把该候选写成已经生效的规则。

**当前实现事实**：`scripts/project_init.py` 的 `plan`／`new` 只接收项目 ID、名称和用途；`new` 未带 `--apply` 时只预览。写出的元信息含身份、用途、依赖、成果入口占位、Buzz／GitHub 空位和初始化步骤。成果路径以及 `buzz`、`github` 在创建时为空，不表示已经关联。见 [01 第 4 章](01-项目初始化与共享资料.md)。

## 4. 初始化的组织、结果核验与部分失败

Main 使用 01 的能力组织本轮需要的初始化，不把“负责初始化”写成模型可以任意建目录或修改允许名单。步骤、锁和完成证据以 [01 第 5 章](01-项目初始化与共享资料.md) 为准。

组织顺序：

1. 核对本轮动作范围。只读判断、最小建档、本地 Git、远端、同步、Buzz 映射、共享读取，各自要有对应授权。已有授权直接使用，不为了流程整齐重复请批。
2. 取得必要输入。缺的只补会影响这一动作的项。
3. 请求只读预览。`plan` 与 `inspect` 不写入。
4. 处理占用。同名对象先说明冲突，不覆盖、不改名、不搬迁、不删除。
5. 调用获准的创建能力。当前这是融合初始化器脚本，不是 Main 宿主工具面上的一项。见第 12 章。
6. 复读实际文件，展示已完成项和仍待完成项。

本地目录、本地 Git、远端仓库、首次提交、推送、Buzz 映射和跨角色读取是七件不同的事。创建目录不能推出后面的 Git、远端或发布权限。

初始化的受控动作、创建后核验和部分失败见 13.6（候选设计，尚未生效）。01 的能力定义、三文件和失败现场仍以 01 为准，本节不重写第二套规范。本地创建不隐含 Git、远端、发布或下游启动。

**当前实现事实**：初始化步骤名为 `local_files`、`local_git`、`github_repository`、`remote_link`、`initial_commit`、`initial_push`、`buzz_mapping`、`shared_read`。`new --apply` 成功时只有 `local_files` 为 succeeded，其余仍为 pending。`init-git --apply` 只做该项目内的本地 Git，不提交、不推送、不配置远端。远端建仓尚未实现；预检只看本机有没有 `gh`，不检查登录。`inspect` 固定把远端核对和共享读取标为未验证。

部分失败时回答三个问题：实际留下了什么，哪些结果已经复读，从哪个确定位置继续。

| 情况 | Main 应说明的事实 | 不能做的事 |
| --- | --- | --- |
| 目标已占用 | 具体冲突对象，并保护既有内容 | 随机改名、覆盖、搬迁或删目录 |
| 只写出部分文件 | 保留现场，先检查磁盘上有哪些文件 | 再跑一次 `new` 盖掉现场 |
| 元信息不完整 | 哪份基础文件缺失或身份对不上 | 自动补文件假装创建成功 |
| 网络结果未知 | 本地已有内容保留；远端是否创建须先核对 | 超时后立刻再创建一次 |

未知锁不自动删除。初始化状态使用 `pending / succeeded / failed / skipped`，跳过必须有原因。这不是工程任务状态，也不是用户确认。

### 4.1 本地完成而映射未接入

纸面说明，不是某次工具回执。用户授权为新项目建立本地目录和本地 Git，并说明 GitHub 账号稍后再给。

Main 在获准创建并复读后应分开报告：三份基础文件已在指定父目录的直接子目录中，项目 ID 与元信息一致；本地 Git 若已按单独授权完成，则该目录自身是仓库根。GitHub 账号、仓库名和可见性未知，所以远端、首次提交和推送都还是 pending，不能写“初始化成功”。Buzz 项目或频道标识还没有，映射保持待接入，本地读取仍可按已获授权继续。下一步只列出用户已经授权或仍需其决定的项，不自动开始需求访谈。

## 5. 角色选择与用户直接讨论

选择依据是本轮目标、已有材料和仍缺的专业内容。可以从需求开始；已有材料足够时，也可以直接做客户方案或 UI 讨论。只有进入工程用途时，才检查该用途要求的完整输入。见 [00 第 3.1、3.2 节](00-拆解与融合框架.md)。

| 能力 | 选择条件 | 最低输入与产物 | Main 何时介入、何时结束 |
| --- | --- | --- | --- |
| 需求 | 业务目标、范围或验收还不清楚，或用户要改需求 | 项目、目标和已有资料。轻量需求可独立结束；工程方案才需要完整 PRD。方法见 [02](02-需求能力.md) | 用户要求换目标、权限或项目边界时介入。没有下一步就结束，不自动派方案 |
| 客户方案 | 已有足够业务材料，用户要的是对外表达 | 复用需求或用户材料。`docs/solution.md` 只是表达视图 | 保存工具仍待确认，不能宣称已经可调用。见 [03 第 2.4 节](03-方案能力.md) |
| 工程方案 | 用户明确要实现契约 | 稳定 REQ／AC，以及 Main 可核验的“形成技术方案”用途确认。七层方法见 [03](03-方案能力.md) | 只回报候选。确认和启动另算 |
| UI | 已有必要材料，用户要可展示结果 | 需求、方案、页面说明或明确演示场景。单元 04 尚无独立主文 | 组织独立演示并标明模拟边界。不自动批准真实后端 |
| 确认或交接 | 用户要固定某版本的用途，或要把版本交给某人 | 见第 8、9 章 | 未要求继续就在记录完成后结束 |
| 工程角色 | 用户明确进入规划、开发或独立验收 | 对应门禁由 06 及后续单元定义。本文不展开调度 | 不把建设用的 Fizz／Honey 当成业务角色 |

**当前实现事实**：宿主已实现的工具按角色封顶。`main` 可见只读核对，以及登记、当前会话确认、准备交接和记录已发送。`requirements` 可见需求上下文和草稿保存。`solution` 可见方案上下文、检查和技术方案草稿保存。`ui` 的封顶只有成果查看、登记预览和协作查看，没有登记、确认或交接写入。`recipient` 可见核验收据。名单来自 `scripts/trusted_context.py` 与 `scripts/host_tools.py`。名单之外的能力不能靠角色提示获得。这里没有项目创建工具。

用户与专业角色可以直接多轮讨论。Main 不逐句转发。这样减少协调负担，但项目、版本和任务范围仍要保持明确：角色每次仍按已绑定项目和指定材料工作，回报实际文件和未决项，不能靠聊天记忆充当权威状态。

Main 在这些时候重新介入：用户要切换目标或能力，需要协调项目或权限，成果已经形成并要展示，需要用户作决定，或发生阻塞。具体消息由谁收到、线程如何路由、实例如何调用，必须有宿主和 Runtime 支持。理想交互不是当前能力。

### 5.1 交出讨论入口后的协作

本节展开第三个设计缺口。全部选项都是待确认建议，不预设产品方案。

Main 在交出讨论后仍需要知道的，只是会改变协调的事实：项目是否还是原来的绑定，目标或范围有没有变，是否形成了可核对成果，是否出现权限或阻塞，以及是否需要用户决定。它不需要订阅所有频道，也不读取无关项目。

重新介入的时机与上面相同。讨论中途改变目标时，先标出受影响的材料和确认，再请用户决定继续旧范围还是改范围。要切换能力时，交出方回报当前版本和未决项，接收方按第 6 章核验，而不是把聊天记录当成交接。形成成果后，角色返回候选路径和摘要，Main 按第 7 章复读后再展示。权限问题回到第 11 章，不由讨论角色自行扩大授权。

执行事实由 Runtime 保存；权威写入由确定性工具在授权内完成。Main 的回复和角色的讨论都不是执行状态。

下列环节可以在体验上连贯，成功证据不能互相代替：

| 环节 | 怎样才算数 | 不能代替什么 |
| --- | --- | --- |
| 消息选择 | 这条用户消息被指定角色接收 | 不能证明读到了指定版本 |
| 线程绑定 | 讨论留在已绑定项目的线程内 | 不能借新线程换项目或复用旧授权 |
| 角色寻址 | 业务角色、运行环境和 Buzz 身份分别对应到实际实例 | 名称在线或回复“收到”不等于接手 |
| 真实 Runner 调用 | 实际运行环境返回候选和证据 | 不等于成果已保存或已批准 |
| 成果回收 | 复读真实文件并核对版本 | 角色自报路径只是候选 |
| 展示 | 用户看到版本、边界和待决定项 | 展示不是确认，也不是启动 |

**待确认建议**：谁接收用户的下一条消息，Main 如何只获知必要变化，以及失败时停在哪一步。比较时要同时看用户负担、能否复用现有线程绑定、权限是否扩大、要不要新的持久对象。没有依据时保留候选。

不得把“不逐句中转”理解成可以绕过项目绑定、随意开线程、调用未授权角色，或让任意 Agent 改 Main 的登记和确认。也不新增“讨论会话”一类领域对象。06 的持久对象仍以该单元已列出的七个为限。

首版候选实现到哪一步、哪些仍是后续选项，见 13.4 与 13.10（候选设计，尚未生效）。候选链路写到理解、补问、单一创建候选、服务端校验、确定性创建、复读并回到原请求位置。专业角色的实际调用、讨论消息路由、真实 Runner 和常驻 Host 仍是后续选项。本节的路由缺口保持待确认，不因该标注变成已生效规则。

## 6. 输入准备、共享读取与接收核验

交给角色的材料用业务语言说明：项目、目标、指定资料和版本、已知决定、未决项、允许范围、预期产物、回报要求。若这是执行派发，还要带上 06 已有的工作区、基线和执行上下文约束。本文不重新定义序列化信封，也不发明新的派发接口。

路径打得开、版本一致、对方理解正确，是三件不同的事。同机未提交内容按 01 标为仅本地可见。跨工作区时核对已经获准的同步或传输，不自动提交或推送。见 [01 第 6 章](01-项目初始化与共享资料.md)。

接收角色应复述关键目标、范围、最新变更和未决项。回复“收到”不等于读取成功。

Draft 讨论和正式确认交接分开：

- **已确认原则**：一般设计允许用户明确要求把 Draft 用于讨论或探索，交接必须标出 Draft 和用途限制。见 [05 第 6 章](05-项目成果索引与确认交接.md)。
- **当前实现事实**：交接内核只接受用途匹配的有效确认 ID。不存在任意 Draft 交接接口。
- 因此 Main 不能强制所有讨论先批准，也不能假装已经可以把任意草稿交出去。讨论复用若走得了当前内核，就走确认后的记录；走不了就说明限制，把材料留在用户和角色都能读到的位置，并标明这不是正式交接。

一般材料共享、正式交接记录、真正的角色启动，三者不能并成一次“发送成功”。

## 7. 成果回收、登记与展示

角色回报之后，Main 逐项核对：产物是否真的存在，版本是什么，是否还在本轮范围内，未决项和证据限制是什么，要不要组织登记，用户应从哪里看到变化。

角色自报的路径和摘要只是候选。Main 重新读取实际文件。来源角色不能把自报 SHA 或角色名直接当成写入参数。登记过程、锁、事务和 README 投影以 [05 第 4 章](05-项目成果索引与确认交接.md) 为准。本文不复制 schema。

登记表示入口可核对，不表示已批准。当前草稿和某用途已确认的版本分开呈现。最新草稿可以比已确认版更新；不能用一个“已确认”盖住整个项目。

Main 的摘要只保留业务目标、变化和可供决定的问题。不另写一份业务正文，不让 README 或聊天摘要变成第二套需求或任务权威。

展示至少包含：这次完成了什么，实际文件或演示入口，版本，模拟还是真实，验证范围，待用户决定的事项，建议下一步。建议不是执行。工具失败不写成成功。只完成部分目标时，按实际范围交付。

**当前实现事实**：`artifact.register` 由 Main  capability 调用 `main_artifacts`，写入前核对 project.json 与 README 的预期摘要。预览里的身份占位不是合法登记。代码存在不等于某个业务项目已经登记。`just-start` 在 2026-09-19 的记录里，需求索引仍为空；该句只证明当日核对，不代替以后的项目事实。后来有没有登记，要查那个项目本身。

## 8. 用途确认与重要决定的协调

需要用户决定的，是会改变业务结果、费用、权限、外部调用、发布或下一用途的事项。角色在既有约束内可以处理的实现细节，不做成审批表。方案侧的三类事项见 [03 第 10 章](03-方案能力.md)。

确认前呈现：准确成果、用途、当前覆盖范围、阻塞项、明确不授权的事项。已经可核验的确认直接沿用，不重复索取。依据等级、快照和记录格式见 [05 第 5 章](05-项目成果索引与确认交接.md)。

几条边界：

- 模糊同意要结合当前展示判断。能对应到刚展示的版本和用途时，可以组织记录；对不上时只补问缺少的对象或用途。
- 旧版确认只对旧版本有效。新草稿不继承旧批准。
- 普通取舍说明、角色认可、把正文写成“已确认”、或写入某种 status，都不是可信批准。
- 无法关联版本的旧消息不追溯绑到刚生成的新摘要。

**当前实现事实**：`confirmation.confirm-current` 只接受宿主签发的当前会话依据，按项目、会话、消息、成果版本、内容 SHA 和用途生成确认。它不改写正文的 Draft 状态。确认、索引和 README 使用共同项目锁和持久事务。

**历史验收证据**：2026-10-15，`FRL-BTC-01 attempt 1` 在临时真实领域工具项目中，对受信确认恢复、真实事件证据和确认后停止有限定通过。N08 成功后停止，后续步骤需要显式续行。见 业务工具链计划（`fusion-runtime-lab/BUSINESS_TOOLCHAIN_PLAN.md`，未随本批发布） 与 [06 第 8.2 节](06-角色与工作流运行时.md)。这不是通用确认界面，也不是生产入口已经换上真实工具。

**待确认建议**：面向用户的自然语言确认仍要设计。不能把上述严格协议改成要求用户手抄内部字段，也不能把限定验收直接变成所有入口的产品流程。

同一句“可以”的两种处理：

- 用户刚看到某一版需求和用途“仅用于继续澄清”，并回复“可以”。对象、版本、用途都能对上。Main 组织这一次确认，不追加下游授权，也不再要一次同样的同意。
- 用户只说“可以”，但当前没有唯一的展示对象，或同时摆着草稿和旧确认。Main 只问无法关联的那一点：确认的是哪一版、用于什么。不猜测，也不据此批准方案、开发或发布。

确认通过本身不启动下游。

## 9. 交接协调、实际发送与后续启动

用户希望继续时，Main 按业务顺序组织：接收者、用途、固定输入、允许范围、授权、发送结果、接收核验。`prepared`、`sent`、`received-verified` 的字段和证据以 [05 第 6 章](05-项目成果索引与确认交接.md) 为准，这里不定义第二套状态。异常方向“受阻、取消、已替代”仍是 05 中的建议，不是已经实现的状态值。

五件事分开：

| 动作 | 真实位置 | 停住时怎么说 |
| --- | --- | --- |
| 组织交接 | 固定输入和授权，写出准备记录 | 没有发送能力就停在已准备 |
| 真正发送 | 有受信发送依据后才记已发送 | 结果未知就先查询，不立刻重发 |
| 取得接收回执 | 指定身份回报同一交接和实际读到的版本，并复述目标与未决项 | 回复“收到”或读到旧版都不通过 |
| 启动实际角色 | 另有明确执行授权，且运行环境真的开始 | 记录值不能当启动证据 |
| 开始执行 | Runtime 中的执行事实 | 交接核验通过也不等于业务验收 |

**当前实现事实**：`scripts/main_collaboration.py` 可以准备交接、在有受信发送依据时记录已发送，并核验收据。所有相关返回都保留 `downstream_started` 为 false。内核不发送消息，不创建角色，不启动执行。因此 `execution_authorized` 若出现在记录中，仍然不是已启动。

有清楚授权但没有发送能力时，保留已准备事实，说明缺的是发送，不把 prepared 说成 sent。消息已发出但对方读到的不是指定版本时，接收核验不通过，交接不算完成。

角色不可用、工具缺失或发送结果未知时，报告阻塞和已经存在的成果。未知先核对实际结果。可靠调度和在途控制属于 06 及以后的调度单元，本文不补造机制。08、09、10 尚无独立主文，这里不建空链接。

## 10. 恢复、变更、冲突与结束

恢复要同时核对四类权威来源：项目身份、当前相关成果、准确确认和已有交接，再加上 Runtime 的持久执行事实。聊天历史可以帮助理解，不能代替这些来源。

三种变化分开看：

- 文件版本变了：旧确认只覆盖旧版本，受影响的交接暂停后续使用。
- 运行状态变了：先核对是否仍有在途执行，不盲目重派。
- 目标变了：这是新的用户决定，不沿用旧任务范围。

业务协调方式是：认出在途工作，说明影响，请用户做必要选择，保留已完成结果，等待受阻条件解除。事务前滚、取消和锁的技术处理引用实际能力。未知锁不删。未知执行不重派。见 [05 第 4.2 节](05-项目成果索引与确认交接.md) 与 [06 第 6 章](06-角色与工作流运行时.md)。

三层恢复不是一件事：

| 层次 | 恢复的是什么 | 不保证什么 |
| --- | --- | --- |
| Main 的会话 | 重新读取项目、成果、确认和交接后再继续协调 | 不靠“Agent 还记得上次” |
| Runtime 的执行 | 持久工作流、暂停点和尝试 | 不把聊天摘要写成执行状态 |
| 领域事务 | 索引或确认写入中断后的前滚，且拒绝事务外编辑 | 不是两份文件天然一次提交；进程级故障另有范围 |

**历史验收证据**：2026-10-14 的 LangGraph 文件恢复和 2026-10-15 的工具链恢复，各自只覆盖当时的任务、拓扑和临时项目。生产入口仍见第 12 章。旧 ACP 上 2026-09-25 的线程恢复，证明的是那条宿主路径，不自动变成新 Runtime 的证据。

本轮结束时写明交付、限制和已经授权的下一步。用户只要讨论或只要一种成果时，直接结束。不为了凑齐整条链路去启动下游。有效确认之后如果没有继续指令，确认完成后即停止；工程方案也要有显式的继续边界。见 [03 第 11.3 节](03-方案能力.md)。

普通补问不进入 WAITING_APPROVAL，也不写入 ApprovalDecision。三种等待的候选区分见 13.7（候选设计，尚未生效）。准确成果的用途确认仍沿用第 8 章和 05 的受信确认。在途结果尚未确定时，不把用户的「继续」当成原执行已经失败并重新派发。本节原有的恢复层次保持不变。

## 11. 身份、权限与创建前后授权

业务角色、运行环境、模型、Buzz 身份、执行实例和用户身份是不同的事。Main 的权限来自受信绑定和实际工具边界，不来自名称、Persona、环境变量自述，或用户材料里的指令。材料中的越权句子只当资料。见 [00 第 2、6 章](00-拆解与融合框架.md) 与 [05 第 7 章](05-项目成果索引与确认交接.md)。

**当前实现事实**：`trusted_context.py` 拒绝普通字典、篡改封装、错误项目和自报角色。Main 工具必须来自已验证上下文里的 `main` 封顶，不能由模型参数把工作者提权。`host_tools.py` 的身份和路由字段不出现在模型可控参数里。

证据分成三层，不能并成“已经隔离”：

| 层次 | 现在能说的 | 不能说的 |
| --- | --- | --- |
| 角色工作约定 | 提示词和本文限制 Main 与工作者的职责 | 约定本身会阻止越权写入 |
| 工具拒绝 | 经过上述工具的错误身份、错误项目、错误版本会被拒绝 | 通用 shell 或编辑工具不能绕过 |
| 运行环境强制 | 尚未具有全局文件权限隔离证据 | foundation 通过不等于只读隔离 |

### 11.1 尚无项目身份时的首次请求

这是第一个设计缺口。现有协作上下文依赖已经授权的项目，而新建请求此时还没有 `project_id`。不能把这种请求直接塞进要求项目绑定的接口，也不能授予整个父目录的写权限、自动扩展允许名单，或借用旧项目绑定。下列比较都是待确认建议。

1. 请求来源。宿主可以提供的事实应包括已认证用户、频道和线程。模型正文不能补这些身份。当前缺口是：没有项目绑定时，哪一种宿主上下文允许 Main 只做识别和预览。选项包括沿用频道成员身份做只读对话，或为“尚未落盘”的动作单设短时范围。用户负担最低的是继续在当前线程里说清楚意图；持久化上不能把这段对话写成已经存在的项目。
2. 讨论还是创建。沿用第 2 章：明确要求建立项目才进入创建；混合表达先分成讨论部分和创建部分，不制造第二次重复确认。用户已经说过“建一个本地项目”就不要再问一遍同样的话。
3. 候选身份和已创建身份。Main 可以建议 ID，并标明尚未创建。用户选定或用户自己给出的 ID 才进入占用检查。建议文本不是目录。
4. 尚无项目授权时能做什么。允许的读取应限于用户指出的材料和他明确授权的父目录占用检查；预览使用初始化器的只读 `plan`；写入只在首次创建权限已经签发之后发生。谁签发，现有 Main 工具面没有这项能力。待确认的是签发者是用户的一次明确授权，还是宿主上的单独创建许可。二者都不能由 Main 自签。
5. 单一目标子目录。写入范围应落在 01 规定的一个直接子目录，而不是先打开整个父目录再依赖模型自律。失败时只影响该路径。这是待确认的权限形状，不是已经实现的沙箱。
6. 同名和并发。沿用 01：同名文件、目录、软链都是占用。用户已给出的 ID 不自行改名。并发创建若同时命中同一路径，后一次必须看到占用或保留现场，不能覆盖。如何发现并发，现有独占创建能拒绝已存在目录；跨进程的产品提示仍待确认。
7. 部分创建后的重试。新请求、重放和恢复要分开。重放应复读已留下的文件，从确定步骤继续；新请求如果指向同一 ID，按占用处理而不是再创建。不新增“创建会话”对象来保存这些区别。
8. 线程绑定何时建立。比较：创建成功并复读身份之后再绑定，或用户选定 ID 时就绑定但标明目录尚未建立。后一种容易把候选写成已创建。前一种与“绑定之后不可静默替换”更一致，但是创建前的那几轮还没有项目线程。两种都待确认。绑定一旦建立，原线程不能换项目。

比较这些选项时记录四项影响：用户要额外说多少话，现有 `plan`／占用检查能复用多少，权限会不会扩大到父目录或其他项目，失败后能不能只靠目录和元信息恢复。没有依据的不写成流程。

本节比较里，候选设计准备采用和仍不采用的部分见 13.5（候选设计，尚未生效）。方案建议优先是保留已绑定项目不可变，创建前由受信入口承载；扩展运行模型和人工先创建是备选。绑定时机的两个方案都待确认，本节不补一个方案没有写出的选型结论。禁止虚构项目、借用旧项目、用可变候选标识充当绑定，或放开业务父目录。上面八项比较的原意不因这段回链改写。

### 11.2 创建之后的识别与权限衔接

这是第二个设计缺口。五件事分开，不能从“目录已经在”推出其余四件。

| 事项 | 可引用的来源 | 怎样才算成功 | 仍缺什么 |
| --- | --- | --- | --- |
| 目录存在 | 01 的直接子目录规则；`new --apply` 后的复读 | 目标路径是父目录的直接子目录，且不是软链占用 | 不证明元信息正确 |
| 根元信息正确 | `project_init.py` 写出的 schema 1 身份 | ID、名称、用途和三份基础文件一致 | 没有项目类型和规范选择字段 |
| 项目可被发现 | 当前靠路径和项目 ID 解析 | 获授权调用能解析到同一目录 | 没有融合层项目注册表。待确认是否需要 |
| Buzz 映射已建立 | 元信息里的空位；01 第 5 章第 6 步 | 真实项目或频道标识已经登记 | 空位只是待接入 |
| 目标角色已获权限 | 宿主允许名单与工具封顶 | 该角色的实际上下文包含这个项目，且工具面符合角色 | 谁修改名单、如何生效，待确认 |

**待确认建议**：是否需要项目集合级登记。现有根 `project.json` 是项目身份的权威；05 的成果 registry 管的是项目内版本，不是项目名单。上游 `project-registry.json` 和 `active_project_id` 是上游事实，融合层没有同一套注册机制，也不把活动项目迁过来。若以后建议新增登记，必须说明为什么路径解析不够、唯一权威在哪里、怎样避免和根元信息双写。在此之前不新增该对象。

允许名单由谁修改，必须连着用户授权和实际生效结果。Main 模型不能自行扩大 `managed_project_ids`。身份已创建但映射失败时，已授权的本地读写可以继续；需要 Buzz 标识或另一角色权限的步骤保持受阻，并说明卡在哪一项。

下一角色解析同一项目时，应使用项目 ID 和运行环境里的路径映射，而不是碰巧启动在某个目录。`AGENT_CWD` 在需求单元里已经不能当作项目切换槽位，见 [02 第 5 章](02-需求能力.md)。这个限制继续有效。

创建后的发现、允许名单，以及和需求角色的交界，见 13.6（候选设计，尚未生效）。路径解析和集合登记、授权者和生效位置都待确认。模型不得修改 managed_project_ids。本地创建成功不表示已经获得全部角色权限，也不隐含 Git、远端、发布或下游启动。上表的缺口保持开放。

- 用户同时明确要求后续工作时，保留原意，不丢失该授权。首版不能执行时，报告真实限制，不伪装已经启动。

**无项目输入（候选设计）。** 业务输入可以表达尚未绑定项目。这不表示现有 WorkflowRun 或 ExecutionContext 已经能接受空项目。当前实现事实：二者的 `project_id` 都是必填非空字符串，`StartWorkflowRequest.project_id` 也是必填 `str`；顶层入口没有唯一且位于允许名单内的项目时不启动。

1. 构造入口：无项目输入由受信入口在进入上述类型之前承载。本节不把该入口写成已经存在的代码。
2. 授权保持：已知授权仍由服务端策略保存。无项目期间，讨论文字不升级成写入许可。
3. 对话恢复：补问和回复关联到受信入口保存的当前问题，不靠模型记忆。恢复字段的展开留在后续批次；本节要求来源持久且可核对。
4. 转换时机：只有创建完成并复读到真实项目身份之后，才进入有项目的执行。转换前不把候选标识写入 WorkflowRun 或 ExecutionContext 的项目字段。

三条禁止：不得虚构项目来填必填字段；不得借用其他项目；不得约定空串等于合法项目。

**资料组装与读取边界。**

- 读取对象是本轮角色规则、已绑定项目的入口，以及本轮相关材料。尚未绑定时不读取其他项目的资料。
- 服务端在组装本轮输入时实际读取。只传入路径或 SHA，不等于模型已经拿到正文。把全部项目和历史塞进上下文，也不等于准确输入。
- 内容版本与读入时不一致，或材料不可读，就拒绝这一轮，或按新版本重建输入。不能悄悄改读最新，仍沿用旧候选。
- DOCX 等非文本材料，由受控解析产生可追溯摘录后再给模型。不能由模型支持多模态，推定完整附件链路已经存在。
- 输入不含私钥、认证凭据或无关项目资料。密钥与发布身份留在宿主边界。

### 13.3 Main 结构化候选输出

模型返回的内容可以包括用户可见说明、补问和建议动作。实际权限和成功事实不能由这些文字赋予。服务端只接受本节表格里的候选结构，不从自由文字猜测并执行命令。下列名称是讨论分类，不是现有运行状态或已冻结枚举。

「一轮至多一个可执行候选」是首版研究建议，用来降低混合动作和部分失败的歧义，不是已批准规则。若将来允许多动作，必须同时定义顺序、依赖、逐项授权和部分成功语义。本节不把单动作写成产品默认，也不作出选型结论。

**候选种类。**

| 候选种类 | 模型表达什么 | 服务端处理 |
| --- | --- | --- |
| 普通说明 | 回答讨论问题，说明本轮结论 | 通过展示校验后发布；不产生文件副作用。 |
| 补问 | 缺哪些事实、为什么影响当前动作、给用户什么问题 | 生成可恢复的等待依据，再发布问题；不产生文件副作用。 |
| 创建项目候选 | 已知名称、标识来源、用途及必要选择 | 核对来源、授权、目标目录与占用后决定是否允许；未允许时不创建。 |
| 请求只读核对 | 需要核对哪个受控对象，为什么 | 从服务端映射定位；不允许自由绝对路径。 |
| 专业角色协作建议 | 希望哪个业务角色处理什么、需要哪些准确材料 | 首版未支持实际调用时报告边界；不伪装已经启动。 |
| 阻塞说明 | 什么缺失或冲突、已有哪些真实结果、恢复条件 | 记录可核对原因；不把模型自述直接写成运行状态。 |

正式成果批准、修改 allowlist、Git、消息任意转发、直接写文件或创建角色，不能混入候选的通用参数。出现时拒绝整个候选，不执行部分动作。若未来支持这些动作，必须另有独立契约和授权校验。

**公共字段。** 研究形状约定：普通说明、补问、阻塞说明，以及首版未支持实际调用时的专业角色协作建议，可执行候选取「无」；创建项目候选和请求只读核对取「有且仅一个」。这组对应关系仍待确认。

| 字段 | 取值 | 缺失或冲突处理 |
| --- | --- | --- |
| 候选种类 | 普通说明、补问、创建项目候选、请求只读核对、专业角色协作建议、阻塞说明 | 缺失、未知种类或与可执行候选冲突时，拒绝为有效操作，不执行副作用。 |
| 用户可见说明 | 给用户的文字 | 空说明不发布；有副作用的说明不能提前宣称操作已成功。 |
| 可执行候选 | 无、有且仅一个 | 缺失、取其他值，或一轮出现多个可执行候选时，拒绝整个候选，不执行其中任何一项。 |

| 字段 | 含义 | 缺失或冲突处理 |
| --- | --- | --- |
| 所缺事实 | 缺哪一项事实 | 缺少所缺事实时不发布补问。 |
| 影响原因 | 为什么影响当前动作 | 缺少影响原因时不发布补问。 |

| 字段 | 含义 | 缺失或冲突处理 |
| --- | --- | --- |

| 用途 | 业务用途 | 缺少用途时不执行创建。 |

**载体选型（P2，待确认）。** 本节比较两条路线，不选定其中任何一条。

- 方案建议优先，状态仍为待确认：复用现有 AgentResult 的 candidate_body，在受控边界解析一个有版本的 Main 候选结构。当前实现事实：candidate_body 是字符串，evidence 是字符串元组，没有 Main 专用候选类型。代价：仍要严格解析和字段约束，字符串载体不能靠字段名自动防止注入。影响：不改 AgentRequest 与 AgentResult 的现有字段，但解析必须在任何副作用之前完成。
- 备选，状态仍为待确认：经门禁明确扩展平台中立端口，使 Main 结果具有相应的类型或区分方式。代价：要分析对既有需求调用、方案调用和共用考卷的影响。影响：结果类型一变，所有共用该类型的调用都要跟着核对。

无论选哪条路线，LangGraph、Buzz 或模型 SDK 的具体类型都不能进入领域或中立端口。一轮单候选还是多动作，同样待确认。多动作的顺序、依赖、逐项授权和部分成功语义尚未定义，所以不能把多动作写成已经支持。

**解析规则。**

1. 必填字段、类型、长度、可选字段、null 与缺失的含义必须在候选结构中明确。null 不等于缺失，缺失不等于默认值。
2. 未知动作、禁止字段、未知字段和非法组合有确定处理，不静默丢弃影响授权的内容。未知字段拒绝该候选。
3. 空输出、截断、多个互相冲突候选和混入说明文字不能当作有效操作。
4. 带结构的文本仍可能恶意。校验结构之后，还须校验项目、版本、来源和实际能力。
5. 解析失败不执行副作用。若允许纠正重试，额度和关联由服务端规定，不由模型规定；重复失败如实受阻。
6. 用户可见回复不能提前宣称操作已成功。有副作用的成果说明应以真实执行结果为依据。

### 13.4 服务端决策与执行结果

本节是候选设计，尚未生效，不可直接实现或配置上线。工作名称不是现有 Python 类型或已冻结 API。13.1 的标识规则和 13.2、13.3 的字段名继续适用。不把「用户说创建」与「模型自行签发写入能力」合并。输入、授权和检查已经齐备时，不再额外增加一次形式审批。

**候选到副作用的完整链。** 下表覆盖编写方案 §7.1 箭头链的每一个节点。编写计划把这条链称为九步链；方案代码块写出 10 个节点、9 个箭头。本节不合并、不省略，以免漏掉接收或发布。每一步的责任者、输入、拒绝条件和成功证据都写在表内。这些是候选规则，不是当前代码已经串起来的 Main 创建闭环。

| 步骤 | 责任者 | 输入 | 拒绝条件 | 成功证据 |
| --- | --- | --- | --- | --- |
| 接收模型结果 | 服务端接收 Runner 返回 | 本轮请求引用、契约版本与角色规则版本、模型原始返回 | 空输出、截断，或无法关联到本轮请求引用 | 原始返回与本轮请求引用一起可重读 |

| 核对本轮调用、项目或候选身份及输入基线 | 服务端 | 执行关联与基线、已知项目、资料版本 | 迟到输出应用到新基线，或复述的项目标识、契约版本、本轮请求引用与服务端值不一致 | 候选只用于它所对应的基线 |

| 由受信执行者构造确定性操作 | 确定性执行边界 | 上一步已经核对的服务端值 | 候选含排除字段，或由模型规定重试额度、幂等键、操作成功状态 | 操作参数只来自服务端，模型复述未覆盖这些值 |
| 执行并读取真实结果 | 受控工具，随后由服务端复读 | 构造好的单次操作 | 工具异常、部分成功或调用结果丢失。处理见 13.8、13.9，本节不把退出码写成成功 | 复读到的文件、身份和步骤状态与所声称的完成范围一致 |

| 发布准确说明或交回 Main 解释 | 宿主发布；Main 只作语言解释 | 已核验执行结果、消息位置 | 展示改掉错误类别、扩大完成范围，或把本地结果写成已同步远端；模型指定频道、root、收件人或签名身份 | 原请求位置的说明与已核验事实一致 |

**真实执行结果字段组。** 讨论用工作名称是 `MainExecutionOutcome`，不是现有类型。Main 可以解释真实结果，不能改错误类别、扩大完成范围，或把本地结果改写成已同步远端。服务端核对展示中的关键事实。必要的固定事实可以由确定性投影直接提供。

| 信息组 | 来源 | 语义 | 校验 | 缺失或冲突处理 |
| --- | --- | --- | --- | --- |
| 操作关联 | Runtime | 原请求、候选版本、实际执行 attempt 与操作坐标的对应 | 必须能回到本轮请求引用和当时的基线 | 对不上则该结果不能发布为这一轮的成功 |
| 实际完成范围 | 受控工具复读 | 创建、检查、映射等哪些动作确实完成，哪些未执行 | 与磁盘和步骤状态一致，不用一句「全部成功」 | 未执行的步骤保持未执行，不由说明补齐 |
| 结果对象 | 实际文件与身份复读 | 实际项目身份、目录映射、存在的文件和必要摘要 | 身份来自真实 project.json，不来自候选 JSON | 读不到对象时标为未知，先查询，不当成未创建 |
| 失败或未知 | 工具或执行适配器 | 可定位原因、已发生的部分效果、需要先查询的对象 | 错误类别一经核验不可由 Main 改写 | 原因不足时保留现场并说明要先查什么 |
| 恢复依据 | Runtime | 能重读的状态或结果来源，以及下一次允许核对什么 | 来源必须持久，不能是模型会话记忆 | 没有恢复依据时不自动重跑写入 |
| 用户可见内容 | 由已核验事实导出 | 成功、限制和待办 | 关键事实与上列信息组一致 | 没有已核验事实时不发布成功说明 |
| 发布关联 | 宿主 | 原请求位置和投影关联 | 由宿主掌握，模型不可改写 | 发布失败或未知只核对发布，不重做创建 |

**Main 角色与确定性执行者（P3，待确认）。** 必须分开四个身份：旧 ACP 的 collaboration_role=main、拟接入的 Main 模型角色、Runtime 的 deterministic 节点，以及真实用户。名称本身不提供权限。当前实现事实见 13.1 第 3 项：`AGENT_ROLES` 没有 main；`ROLE_TOOL_CEILINGS` 另有旧 ACP main。主文不能把「Runner 调用 Main」写成该角色已经获得可执行权限。

- 方案建议优先，状态仍为待确认：由服务端配置和策略把拟接入的 Main 模型角色限制为候选生成与语言解释；写入、登记和确认仍由确定性执行边界承担。代价：要单独定义该角色可读哪些受信说明，以及如何映射到实际运行环境。影响：不把旧 ACP main 的登记和确认写工具交给新的模型角色。
- 备选，状态仍为待确认：暂不接入 Main 模型角色，协调只停留在文档和人工操作，直到另有产品决定。代价：首版闭环不能由模型提出候选。影响：不改变现有四角色策略，也不产生新的可执行权限。

两条都不作选型结论。无论哪一条，模型输出都不能指定权限、真实路由、签名者、最终状态或成功效果。

### 13.5 无项目请求与首次创建授权

本节是候选设计，尚未生效，不可直接实现或配置上线。它不把任何路线写成已实现、已批准或已冻结。当前实现事实仍以 13.1 第 5 项为准：现有启动请求的 project_id 是必填字符串，顶层入口没有唯一且位于允许名单内的项目时不启动。创建前的几轮还没有真实项目。契约要回答创建前的请求由谁承载、授权在哪里、补问保存在哪里、何时进入有项目的工作流。存放位置本方案没有选定，本节也不补选型结论。

禁止用虚构项目占位，禁止借用旧项目上下文，禁止把可变候选标识当作已绑定项目，禁止为了方便创建而放开整个业务父目录。

**创建前承载（P1，待确认）。** 三条路线都写出代价和影响。状态都是待确认。

| 路线 | 方案中的位置 | 需要回答的内容 | 代价 | 影响 | 状态 |

| 是否由允许的用户发起，身份依据来自哪条受信路径 | 只接受 Buzz 适配器已经核验的认证用户与来源。模型正文不能补 principal 或 authority | 未认证时只停留在不可写的说明，连只读预览也不做 | 要划清「可讨论」和「可写」的身份门槛 | 未认证不能进入可写操作，与 13.2 的缺失处理一致 | 待确认 |
| 哪些输入只允许讨论或只读核对，哪些明确允许创建 | 讨论和只读核对不产生目录。只有服务端自持的已知授权写明创建这一个项目时，才进入创建 | 把讨论里出现的项目词语都当成创建许可 | 用户多说一句确认；换来的是不会误创建 | 保存下来的创建授权不扩张为 Git、发布或后续启动 | 待确认 |
| 用户已选标识、Main 候选标识和最终目标如何区分，选择如何追溯 | 沿用 13.3 的标识来源：用户已选、Main 候选、尚未确定。最终身份只在复读真实文件之后成立 | 把候选标识直接写入项目字段 | 创建前要多保留一条选择引用 | 复述标识只作一致性核对，不能覆盖服务端值 | 待确认 |
| 父目录来自哪份受信配置，实际目标如何限制为一个直接子目录 | 父目录只来自已确认的受信配置。服务端把目标收成该父目录下的一个直接子目录 | 先打开整个父目录，再靠模型约束路径 | 权限形状更窄，失败只影响该路径 | 模型给出的绝对写入路径按 13.3 排除字段拒绝 | 待确认 |
| 服务端如何构造单次操作范围，哪些条件失效后不能再用 | 一次授权对应一次已核对的目标、版本和本轮范围。候选变更、基线变化或占用出现后，原范围失效 | 让同一句授权一直有效到用户忘记为止 | 变更时要重新核对，不能沿用旧范围 | 模型不能自己规定重试额度或幂等键 | 待确认 |
| 候选变更、用户改变主意、取消或目标占用时如何撤销或替换 | 旧候选不再执行。占用时保全既有内容，不改名、不覆盖。取消停止新的未授权动作，不承诺撤销已经发生的效果 | 静默换成另一个标识继续创建 | 用户能看见替换，不能靠隐藏旧候选 | 不把「另开线程」说成已经定义了旧工作如何保留 | 待确认 |
| 创建失败后，原授权是否允许核对或恢复，哪些动作要重新判断 | 允许按恢复依据核对现场。新的写入要按错误类别重新判断，不能把失败授权自动变成下一次创建 | 失败后用同一授权立刻再创建一次 | 未知结果必须先查，重试次数由服务端规定 | 与 13.8 的五种情形衔接，本节不另写一套恢复 | 待确认 |
| 同一用户消息重复到达时，如何识别既有结果而不再次创建 | 以受信事件标识识别重复，返回或继续核对原处理结果，不因为文本相同或不同单独决定 | 只按正文相同就当成同一次，或只按正文不同就再创建 | 要保存事件与操作的关联 | 不同消息要求同一创建时，还要核对占用和身份，见 13.8 | 待确认 |

**绑定时机。** 方案没有为下面两个方案指定建议优先项。本节并列比较，不写选型结论。绑定生效之后，原线程的项目不能静默替换。失败或改换项目不能靠修改原绑定来隐藏，要有明确的新入口或受控转换；不能只说「另开线程」而不定义已有工作如何保留。

| 方案 | 选择理由里要守住的点 | 失败时 | 代价 | 影响 | 状态 |
| --- | --- | --- | --- | --- | --- |
| 标识选定后就绑定 | 创建前的几轮可以挂在同一线程 | 目录尚未建立时，必须标明这不是已有业务项目。未创建的候选不能当成已经绑定的项目 | 容易把候选写成已创建 | 若创建失败，原绑定不能改写成另一个项目来掩盖失败 | 待确认 |
| 创建成功且身份复读之后再绑定 | 与「绑定之后不可静默替换」更一致，真实身份来自复读 | 创建前几轮还没有项目线程，补问和回复必须由受信入口另行关联 | 创建前的关联要单独持久化 | 复读失败则不建立项目绑定，也不借用旧项目 | 待确认 |

### 13.6 项目初始化与生效核验

本节是候选设计，尚未生效。初始化的文件规范、锁和完成证据仍以 01 为准，这里不写第二套规范。本地创建不隐含本地 Git、远端创建、提交、推送、发布、正式成果批准或下游启动。ID 的安全格式、父目录、同名占用、三文件骨架、未知关联和失败保留都引用 01。模型候选与实际参数要逐项核对。

**项目类型与规范选择（P7，待确认）。**

- 方案建议优先，状态仍为待确认：首版不增加项目类型或规范选择的元信息字段。售前讨论不必先选工程规范；进入工程用途时才询问。未回答、明确 null、default 和暂缓四者分开。缺失不能当成 null 或 default。代价：工程用途开始之前没有规范记录，以后补齐要另有条件。影响：初始化器、项目读取者、旧项目和 01 的契约本次都不改；未改代码，不能写成已经保存。
- 备选，状态仍为待确认：增加字段，并写明对初始化器、读取者、旧项目兼容和 01 的影响。代价：出现第二处可能和根身份不一致的元信息。影响：代码尚未修改时，仍然不能写成已经保存。

**创建后七项核验。** 下表与方案 §9.2 对应，不把目录存在、工具退出码或模型自报路径当成通过。

| 核验事项 | 必须取得的实际证据 | 不能用什么代替 | 缺失时 |
| --- | --- | --- | --- |
| 路径 | 服务端解析出的单一项目目录，以及它落在受信父目录的直接子目录内 | 模型自报绝对路径 | 不创建，或在已有现场上停止并报告 |
| 身份 | 真实 project.json 中的标识、名称与用途 | 候选 JSON，或工具退出码 | 不能把候选标识公布为已创建身份 |
| 基础文件 | project.json、README、.gitignore 实际可读，且符合 01 已有契约 | 仅仅目录存在 | 说明哪一份缺失，不自动补文件假装成功 |
| 部分结果 | 初始化步骤与磁盘状态一致 | 一句「全部成功」 | 按真实步骤记录；当前事实是只有 local_files 会在创建时标为 succeeded，其余保持 pending |
| 角色读取范围 | 实际受信策略允许目标角色读取这个项目 | 项目位于可访问磁盘上 | 该角色受阻，不把磁盘可达写成已授权 |
| Buzz 关联 | 已有真实标识和核对结果，或明确仍未接入 | 元信息里的空字段 | 空字段保持待接入，不编造映射 |
| 对用户的回报 | 正确的原请求位置里写明结果和限制 | 后台日志显示已完成 | 没有发布证据就不把回报写成用户已经看见 |

**创建后权限（P5，待确认）。** 模型不得修改 managed_project_ids。创建成功不等于已经获得所有角色的权限。

- 方案建议优先，状态仍为待确认：授权者是持有用户已核验授权的服务端策略，不是模型。作用范围限于这一个项目和该角色已有的工具封顶。生效位置是允许名单上的受控变更。生效核验是该角色的实际上下文包含这个项目，且工具面仍符合角色。代价：创建和授权是两步，中间会有「目录已在、角色尚未获权」的状态。影响：未生效的角色保持受阻；已经授权的本地读写可以继续。
- 备选，状态仍为待确认：创建后不自动把任何角色加入允许名单，只返回项目入口，授权另走已有管理路径。代价：用户看到入口之后仍不能立刻调用角色。影响：不会把创建误写成全角色授权。

**项目发现（P6，待确认）。** 成果 registry 不承担项目名单。不得移植上游 active_project_id 作为跨线程的默认选择。

- 方案建议优先，状态仍为待确认：首版用路径解析加上身份复读来发现刚创建的项目，不新增集合登记。代价：必须证明解析结果和根身份一致，解析失败时不能另建影子名单。影响：不增加新的权威文件。
- 备选，状态仍为待确认：在路径解析被证明不够时，再定义集合登记。那时必须同时写明必要性、唯一权威、更新者、失败恢复，以及和根身份的一致性。代价：有双写和失步的风险。影响：未写清这五项之前，不新增该对象。

**与需求角色的交界（P8，待确认）。** 用户同时提出的后续意图要保留，不能丢掉，也不能伪装已经执行。

- 方案建议优先，状态仍为待确认：首版完成创建并返回项目入口，明确尚未启动需求角色。只读核对可以按 13.3 的「请求只读核对」提出，定位仍由服务端映射完成。Git、远端、发布、正式成果批准、下游启动和专业角色的实际调用，首版不执行。代价：体验在创建后停止，后续工作要另一次授权。影响：不虚报已经启动；未支持的原意记在可见说明里。
- 备选，状态仍为待确认：若声称已经准备好由需求角色接手，必须同时列出身份映射、材料可达、版本和读权限四项实际条件。代价：缺任何一项都不能声称接手就绪。影响：这四项当前都不写成已经满足，也不提前开放未确认的调度。

### 13.7 补问、回复关联与恢复

本节是候选设计，尚未生效，不可直接实现或配置上线。普通事实补问、准确成果的用途确认、执行结果回收是三种等待，不能混用。当前实现事实见 13.1 第 6 项：普通 resume 拒绝泛化恢复；成果确认走专用受信入口。WAITING_APPROVAL 在现有运行模型里表示等待批准，不能为了省事把全部补问塞进这个状态，也不能让普通回复携带 ApprovalDecision 去绕过确认入口。不使用模型自由文本维护执行状态。

| 等待内容 | 含义 | 不应混用的机制 | 权威核对位置 |
| --- | --- | --- | --- |
| 普通事实补充或选择 | 名称、用途、标识等信息不足，需要用户回答 | 不自动进入正式成果批准，不写 ApprovalDecision，不进入 WAITING_APPROVAL | 本节的补问记录；发布前不产生文件副作用 |
| 准确成果用途确认 | 用户对已经展示的准确版本决定用途 | 沿用第 8 章和 05 的受信确认，不能用普通补问字段代替 | 第 8 章的当前会话确认；对象、版本、用途必须对得上 |
| 执行结果回收 | Agent 或工具仍在途，结果尚未确定 | 不把用户的「继续」当作原执行失败并重新派发 | 13.4 的失败或未知、恢复依据；先查询再决定 |

**补问记录要表达的信息。** 这些是语义，不表示必须新增一组持久领域对象或数据库表。权威位置必须可恢复。字段为：问题关联、问题正文、所缺信息、可选项、提问版本、目标范围、允许回答者、已答项、替代关系、当前是否仍有效、对应输出投影、恢复条件。承载方式见下面的 P4。它不能变成另一套工作流权威。

**恢复端口（P4，待确认）。** 框架的 Command、interrupt 和 checkpoint 类型留在 LangGraph 适配层，不进入平台中立的业务契约。模型不能指定任意目标状态或节点。

- 方案建议优先，状态仍为待确认：增加专用的、已经验证的用户输入操作，专门承接普通补问的回答。不放宽成果确认的边界，不改 WAITING_APPROVAL 的批准语义。代价：中立端口多一个调用，要写清字段、调用者和拒绝条件。影响：普通回复不能借 ApprovalDecision 进入确认。
- 备选，状态仍为待确认：在不放宽原确认边界的前提下扩展现有中立端口，用端口值表达「这是普通回答」而不是批准。代价：共用端口的调用都要核对，避免旧的确认路径被放宽。影响：拒绝条件必须仍然挡住未绑定准确成果和用途的同意。

两条都不作选型结论。调用者都应是服务端，不是模型。拒绝条件至少包括：来源未核验、问题已失效、项目或候选已不一致、回答已经处理过。

**用户回复的处理顺序。**

1. 验证新消息的来源和权限，取得受信的消息位置。
2. 按持久绑定找到当前有效问题或当前运行，不从模型正文猜测路由。
3. 检查消息是否已经处理、问题是否过期、项目或候选是否仍然一致。
4. 区分直接回答、用户修改目标、无关输入、模糊回答和取消意图。
5. 必要时调用 Main 解释回答，并把解释与可以核对的事实分开。
6. 校验候选和当前基线，更新适用的已知选择，再决定补问、执行或结束。

用户一句话回答多个缺项时，可以一并复用。不能因此推导出用户没有表达的规范、远端或其他动作授权。

**重放与并发。**

| 情形 | 服务端必须做的核对 | 不能做的事 |
| --- | --- | --- |
| 同一 event_id 重复送达 | 返回或继续核对原处理结果 | 再执行一次副作用 |
| 两条不同事件给出相同回答 | 结合当前问题和操作状态判断，不能只按文本当成同一次 | 只因文字相同就合并成一次创建 |
| 用户补充信息时，旧的模型调用还没返回 | 发现旧输出相对新选择已经过期 | 让旧输出覆盖新选择 |
| 两个并发回复试图推进同一轮 | 用排他或版本校验串行化 | 依赖模型自己克制 |
| 旧问题已经被新问题替代 | 旧回答不应用到新候选 | 把旧答案填进新问题 |
| 重启后只能靠持久来源 | 从问题、已答项和执行结果恢复 | 要求模型保留原会话记忆，或盲目重跑已经完成的写入 |

**问题发布前后的崩溃。** 三种阶段都要能核对，不重复创建问题，也不重复消费回答。

| 阶段 | 已经留下什么 | 核对方式 | 禁止 |
| --- | --- | --- | --- |
| 问题已持久化但未发布 | 可恢复的等待依据在，用户还没看见问题 | 先读持久记录，再决定是否补发同一次问题 | 再生成一个新问题把同一次缺项问第二遍 |
| 已发布但确认丢失 | 用户可能没看到，或看到了但回执丢失 | 按问题关联核对投影，不把丢失当成用户已回答 | 把未回答写成已经确认 |
| 用户已经回复但尚未处理 | 受信消息在，处理结果还没有 | 按事件标识继续原处理顺序 | 再消费一次同一回答，或再创建一次 |

### 13.8 工具、版本与幂等

本节是候选设计，尚未生效。当前实现事实：13.1 第 7 项说明 project_init.create 存在，宿主工具列表没有项目创建入口。本文第 4 章和第 11.1 节已经写明同名目录会被拒绝、不能覆盖。拒绝已经存在的目录，不等于整个 Main 创建闭环已经具备业务幂等。执行前已完成、执行中崩溃、结果回传丢失，都要能核对。

**五类幂等对象。**

| 对象 | 坐标 | 重复到达时 | 不能当成坐标的东西 |
| --- | --- | --- | --- |
| 入站消息 | 受信事件标识 | 返回或核对原处理结果，不再执行副作用 | 只看内容文本 |
| 模型执行 | 同一请求、输入摘要、运行轮次和结果 | 区分调用未知与已知失败；未知先查运行 | 模型自己编的引用 |
| 创建候选 | 选择版本及用户依据 | 候选一变，就不能复用旧的授权范围 | 可变的候选标识 |
| 实际创建操作 | 服务端建立的稳定关联 | 执行前核对既有结果和目标占用 | 模型输出里的幂等键。该字段按 13.3 出现即拒绝 |
| 结果发布 | 原投影和签名发布事实 | 发布失败不重做业务创建 | 把发布成功写成创建成功 |

**版本与基线。** 至少把这些绑在一起：输入资料、用户选择、项目元信息、工作流 revision、候选结构版本、实际执行结果。迟到的候选只能用于它所对应的基线。重新读到最新版本，不能自动让旧候选重新有效。

创建前后 project.json 的变化要和操作结果对应。登记成果导致入口变化时，不能反向修改旧的需求来源摘要，也不能形成重复生成循环。05 已有的事务机制保持原边界，本节不放宽。

**部分创建与结果未知。**

| 情形 | 实际效果 | 下一步 | 禁止 |
| --- | --- | --- | --- |
| 尚未调用工具即失败 | 没有创建效果 | 能否重试由确定的错误和额度决定 | 把结构错误当成已经写入 |
| 目录创建后部分文件失败 | 保留目录和实际文件，报告具体完成范围 | 从现场继续核对，不自动删除 | 再跑一次 new 覆盖现场 |
| 工具可能已完成，但调用结果丢失 | 效果可能已经存在 | 先用受控核对取得真实文件和身份 | 当成不存在再创建一次 |
| 创建完成，但权限或映射失败 | 本地成果保留 | 权限所依赖的步骤如实受阻 | 把未接入写成成功 |
| 创建完成，但发布失败 | 创建结果仍在 | 只核对或重试发布 | 为了发布而重新执行创建 |

还要证明：占用对象就是先前这次操作产生的，而且身份和内容没有被其他人改变。不能把「用同一标识再调一次然后报占用」写成已经正确返回了原创建结果。

### 13.9 错误、停止与资源边界

本节是候选设计，尚未生效。下表是要覆盖的错误类别，不是现有错误枚举，也没有冻结的错误码。用户看见的是类别和可核对的原因，不是内部码。具体码以后由实现任务规定；本节不编造码值。

| 类别 | 处理 | 用户可见的说法 | 禁止 |
| --- | --- | --- | --- |
| 输入或候选结构错误 | 无副作用。是否允许受限纠正、如何保留原失败，由服务端决定 | 说明结构不被接受，不宣称已经执行 | 静默丢掉影响授权的未知内容 |
| 事实不足 | 定向补问，不编造默认值 | 只问缺的那一项 | 用 null 或 default 填上未回答的规范 |
| 授权不足 | 说明缺的是哪个动作和范围 | 不索取已经存在的相同授权 | 把模型总结写成新的许可 |
| 身份、项目或路由冲突 | 拒绝受影响的操作 | 停在该项目，说明哪一项对不上 | 回退到其他项目或身份继续写 |
| 目标占用或版本冲突 | 保全现有内容，先查明 | 指出冲突对象 | 覆盖、静默改名或搬迁 |
| 能力未实现或角色不可用 | 报告支持边界 | 说明首版未执行，并保留用户原意 | 调用并不存在的工具，或假装已经启动 |
| 模型调用失败或超时 | 返回实际失败 | 结果未知时先说明要查运行 | 不查运行就新建另一次执行 |
| 工具异常或部分成功 | 保留现场，按真实效果恢复或受阻 | 列出已经留下的文件和未完成的步骤 | 用退出码代替现场 |
| 发布拒绝或结果未知 | 以发布证据核对 | 说明创建结果和发布结果不是一件事 | 因此重跑模型或重做写入 |
| 用户取消或目标改变 | 检查在途效果，停止新的未授权动作 | 说明哪些效果已经发生 | 承诺撤销已经发生的效果 |

**限额与停止。** 输入材料大小、输出长度、调用等待、结构纠正次数、连续没有进展的补问，都要有明确策略。具体数值按实际运行环境和首版用途决定。本节不把未经运行验证的数字写成默认值。

达到限制时，保留已知结果和恢复条件，并停止继续自动推进。Main 不能自行无限重试、提高额度、切换更宽的工具，或另开实例绕过失败。额度由服务端规定，不由模型规定。

- 领域效果阶段：在临时隔离目录里验证创建、核验、冲突和中断，不试改真实业务项目。
- 持久恢复阶段：覆盖跨进程的问题恢复、效果发生后的崩溃，以及发布结果未知，并记录实际拓扑。
- 真实 Runner 阶段：验证真实角色收到的规则和资料、返回的候选，以及失败和在途行为。
- Buzz 端到端阶段：验证认证输入、路由、真实结果可见和回退。默认界面动作由用户按操作卡执行。

实施时按当时的准确范围确定必跑项。不用大量相同的镜像测试代替关键副作用和恢复验证。

### 13.12 模型执行规则的提取约束

本节是候选设计，尚未生效。它约束以后如何从本章提取模型执行规则，不在本轮创建规则文件。任何建议路径都不视为已经注册，也不表示真实 Runner 已经加载。没有真实加载和输入快照时，不声称模型已经读到新规则。实际采用哪个版本由服务端配置，模型不能自行切换。

**应包含的七项。**

1. Main 的职责、首版支持范围，以及禁止代行的工作。范围与 13.1、13.6 的 P8 一致，不另加动作。
2. 如何阅读本轮输入，并区分受信执行信息、用户与材料内容、已核验执行结果。口径与 13.2 一致。
3. 如何复用已知事实、判断必要缺项、合并补问。口径与 13.2、13.7 一致。
4. 每种允许输出的准确结构，以及和 13.3 逐字一致的合法示例。示例仍是候选结构，不可直接调用。
5. 什么时候只回复，什么时候提出动作候选，什么时候结束或报告限制。不把研究中的单候选建议写成已经批准的规则。
6. 如何解释真实工具结果，禁止提前宣称成功或批准。口径与 13.4 一致。
7. 资料里的越权指令、冲突、缺失和没有可用能力时如何处理。口径与 13.9 一致。

**不应放进精简规则的内容。** 历史验收流水、逐轮建设记录、完整源代码、全部角色方法、凭据、全项目数据，以及模型不需要理解的框架内部细节。运行规则可以按需引用资料，但不把所有设计文档的预读变成每一轮的前置条件。

**版本怎样一起维护。** 角色规则版本、输入输出版本和运行实现要能对上兼容关系，并与 13.2 的「契约版本与角色规则版本」使用同一含义。契约里的字段、动作或停止条件改变时，核对执行规则里的示例、解析器和验证要求是否一起改。规则不能新增本章没有的动作、权限或成功定义。本轮不创建该规则文件，也不指定一个已经生效的加载路径。
