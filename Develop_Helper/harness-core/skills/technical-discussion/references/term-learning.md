# 技术名词的复述与沉淀

一个名词的闭环是：登记提问 → 客观解释与项目对照 → 用户亲自复述 → 核对理解 → 写入名词文档 → 下一个名词。不能由 Agent 代替用户完成复述。

## 固定目录

学习记录独立于业务项目，存放在 `<harness_root>/learning/technical-terms/`，重置业务项目时保留。

- [index.md](../../../../learning/technical-terms/index.md)（路径：`<harness_root>/learning/technical-terms/index.md`）：记录所有问过的名词、别名、状态、首次提问时间和当前待复述项；不是只记录已完成名词。
- [glossary.md](../../../../learning/technical-terms/glossary.md)（路径：`<harness_root>/learning/technical-terms/glossary.md`）：仅在用户复述理解到位后写入完成记录。未完成的讲解不提前写成已掌握。

文件不存在时按此结构创建；当前框架已有空文件则直接使用。只读索引的“当前学习”和本次名词对应行，必要时读取 glossary 对应条目，不每次通读全部学习历史。名称与常用缩写归为同一名词，编号用 TERM-001 等，不与项目任务编号混用。

## 进入与等待

1. 新名词先写入 index，状态为“待讲解”；没有未完成项时将它设为当前学习，随后按 Skill 解释并做项目对照。讲解后状态改为“待复述”，在当前学习区保留一个简短的复述问题及必要的项目依据。
2. 请用户用自己的话口述，例如：“请你自己解释一下它解决什么问题，再说说刚才项目采用和不采用时有什么区别。”可以使用语音输入；收到用户自己的语音转写即可核对，不要求提供音频文件。用户明确改用文字复述时沿用其选择，不声称验证过声音。
3. 未收到复述、用户只说“懂了/继续”，或直接提出另一个名词时，不开始下一个名词的完整讲解。新提问先登记为“待讲解”，保留当前项，简短提醒先复述当前名词；不重复输出整篇解释。
4. 同一名词的追问、举例或澄清可以继续，不能误当成跳到下一词。一次提多个名词时全部登记，按用户指定顺序、无指定时按提问顺序逐个完成；辅助术语只解释到足以理解当前词，不强行扩展学习队列。

## 判断是否理解

核对用户能否用自己的话说明核心含义、解决的问题，以及项目中做与不做的具体变化和原因。概念本身没有“采用”动作时，用它在项目中出现/不出现或不同条件下的行为对照，不强造技术选型。

不要求背定义、固定字数或复述所有实现细节。发现实质误解时，只指出那个偏差，结合项目补一个例子，再请用户重新解释相关部分；当前名词保持“待复述”。不能只因用户照抄 Agent 的整段回答就认定理解，可追问一个对应项目的小变化。意思准确且能联系场景时明确反馈通过，不反复考试。

## 完成后写入

先在 glossary 对应 TERM 标题下写入：**名词与别名、简短客观定义、用户实际复述、项目实例及做/不做的区别、纠正的误区（如有）、资料路径/来源、完成日期**。用户复述保留相关原话；如作摘要必须标注，不润色成用户没有表达过的理解。项目假设仍标假设，来源涉及已删除项目则注明历史来源，不冒充当前可验证实现。不记录密钥或无关个人信息。

写入成功后，才将 index 对应行改为“已完成”、附 glossary 锚点，并清除当前学习项。有排队且用户已要求解释的下一词时继续；没有则结束，不自动布置新名词。写入失败要说明“复述通过但记录未完成”，保留当前项，先补存，不能虚报已沉淀。

复习已完成名词时复用编号和旧条目，保留历史完成记录；本轮复述通过后追加日期与复述，不覆盖先前用户原话。当前复述过程及尚待澄清的问题只更新 index 当前学习区。

用户明确暂停、取消学习或调整学习方式时遵循新指令，未完成项如实保留；不把这一学习顺序扩展成阻断其他工作任务的门禁。每次写入后简短告知本次记录的名词和文件路径，不自动提交或推送 Git。
