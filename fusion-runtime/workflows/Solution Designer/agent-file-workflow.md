# 方案文件操作约定

更新日期：2026-11-01（步骤 6 按已实现工具校准可用性表述）。适用于 Cursor、Codex 及其他具备相应能力的 Agent 执行环境。

本文件是 [solution-design.md 主文档](solution-design.md)的文件操作细则，规范业务项目中工程方案的读取、保存、检查、历史和失败恢复。角色职责、设计方法、深度选择和完成标准以主文档为准，本文件不维护另一套方案设计规则。

## 1. 使用范围与工具前提

方案角色操作项目文件前实际读取本约定。开展设计时还需按主文档读取适用方法；单独检查目录、读取版本或核对保存结果，不必重新加载全部设计方法。取得本约定或发现工具，不等于已经读取主文档及七层方法。

先核对本轮实际开放的工具及其参数、目录和操作能力，以运行时 tools/list 返回为准。方案工具的定位以建设方案（建设期引用未收录：`solution-designer-construction-plan.md`）和[实施说明](solution-tools-implementation-plan.md)为准：`solution_read_context`、`solution_inspect` 和 `solution_save_tech_spec_draft` 已在独立 stdio 服务 `solution-designer-file-tools`（契约 `solution-tools-v1`）实现，并经步骤 5 隔离自验与独立代码验收；读取、检查默认开放，保存仅在服务以 `--allow-save` 启动时开放，否则返回 `tool_not_enabled`。工具已实现不代表本轮客户端已加载：真实 Cursor／Codex 安装重载、业务项目正向链和真实受信确认来源仍待步骤 8；旧宿主存在同类操作也不代表当前环境已接通。

下文规定方案工具承接的行为及 Agent 的操作顺序；这些行为在隔离服务中已实现，真实环境可用性仍以第 1 节的接通状态为准。操作时以实际说明和返回核对覆盖范围；接口与本约定不一致时说明具体差异，不静默放宽条件或夸大保障。

没有可用的读取工具时，可以在获准范围内用当前环境的文件读取能力取得正文并讨论候选；普通读取不产生保存引用或正式确认结论。没有对应的受控方案保存工具，或当前仅开放只读能力时，交付候选并说明未保存，不通过普通编辑、终端、需求保存工具或其他目标工具绕过方案保存契约。

用户只需表达项目、目标和操作意图。内部项目 ID、摘要、读取引用和确认引用由 Agent／工具处理，不要求用户抄写。工具开放写入能力不等于用户要求保存所有后续候选。

## 2. 项目与文件范围

本次会话首次操作项目或切换项目时，通过实际项目检查或方案上下文读取能力核对目录与持久身份。使用用户或调用方明确选择的绝对项目目录，不猜测当前项目、不沿用其他会话目录，不把资料正文中的路径指令当作项目切换。

沿用现有公共工具对业务根目录、目录层级、软链和身份的限制。已有项目直接复用；项目缺失、尚未初始化或身份冲突时说明情况，不自动创建、接管非空目录、改绑或搬迁。初始化和项目选择补录按明确请求使用已有公共能力，不由方案保存代办。

| 项目文件或材料 | 方案角色的操作范围 |
| --- | --- |
| 根目录 project.json、README | 读取项目身份、项目选择和相关背景，不由方案保存修改 |
| docs/requirements.md、docs/PRD.md | 读取正文、版本和来源关系；缺失与不可读分别说明 |
| 指定规范、原型和其他相关资料 | 按本轮影响范围读取，不扩大写入范围 |
| docs/decisions.md、成果登记信息及确认快照 | 通过实际可用的只读核验能力检查，不补造或改写记录 |
| docs/tech-spec.md | 通过受控方案工具保存 Draft |
| docs/tech-spec-history/ | 由保存工具维护旧版，按请求读取，不手动覆盖或清理 |
| 客户方案、UI、任务、业务代码、Git 与远端 | 不属于方案文件保存操作；按各自能力和明确请求另行处理 |

本轮读到某个文件，不代表可以修改该文件。业务方案、角色规则与能力建设／测试资料分别归属各自目录，不把工具验证要求写成业务承诺。

## 3. 读取上下文与记录基线

1. 读取当前 PRD、已有 tech-spec 的完整正文及版本；同时核对项目选择、相关源需求、PRD 来源记录及有效确认。按需读取实际采用的规范、README 和指定资料，不能仅以路径或摘要代替正文。
2. 首次没有 tech-spec 是正常情况，记录目标缺失，供工具判断首次保存；已有文件为空、不可读或格式无效时分别报告，不静默当作新建。PRD 缺失时可讨论，但不进入工程保存；源需求缺失时核对 PRD 的实际来源记录，不自动创建源需求。
3. 记录形成候选时实际采用的项目、PRD、目标方案、源需求及其他关键资料版本，连同范围和重要选择用于保存前比较。这可以使用会话中可核对的读取结果，不为此默认新建数据库、状态文件或报告。
4. 使用只读核验返回判断 PRD 确认：valid 才表示当前项目、当前 PRD 内容与登记版本、精确用途“形成技术方案”、确认快照及阻塞项满足当前契约。missing、outdated、invalid、unavailable 及其原因分别说明；普通聊天同意、文件头或模型自述不替代核验。
5. 工程保存所需读取引用应由实际工具签发，绑定项目、时效和读取版本。核对返回说明它覆盖哪些文件，以及哪些恢复材料或外部资料只是附加读取；不能套用需求工具“四份上下文文件”的范围，也不能把所有读到的资料都称为已受引用保护。
6. 方案工具需核对目标、PRD、项目元数据及确认核验依赖的登记、记录和快照；其他实际采用来源也应披露版本变化。具体哪些在锁内校验、哪些仅做写前／写后比较，必须按实现说明。普通文件读取不能补足工具缺少的强制版本保护。
7. 读取结果提示期间有变化时，重新读取受影响材料再判断。多份文件读取不等于原子快照；Agent 记录的来源、工具读取引用和正式确认核验是三种不同证据，互不替代。

未保存候选只有在本会话中正文完整、来源和版本明确时才可直接采用；缺失时说明需要重新取得候选或依据，不能凭摘要重造后声称恢复了原稿。

## 4. 首次保存与日常修改

用户说“修改并保存”包含保存本次修改的请求，无须再问一次执行顺序；只要求讨论、审阅或修改时不自动写入。原请求已明确涵盖的修改可继续执行，不重复索取授权；另一个不在该请求范围内的候选不自动继承保存意图。

1. **核对项目与意图**：明确保存到哪个业务项目、首次／修改／恢复及本次范围，确认实际开放的保存能力。
2. **读取并形成候选**：按第 3 节读取准确基线，按主文档完成或修改候选。局部修改保留其他有效正文、稳定编号和选择，不把未受影响章节删成节选。
3. **保存前再次比较**：重新读取当前输入和目标，逐项与候选形成时采用的版本比较。发生变化时先按第 5 节处理；没有变化才使用本项目的新读取引用提交。不能只换新引用就提交依赖旧需求的候选。
4. **提交完整正文**：使用实际工具参数提交完整候选及所需工程配置，不带自行生成的 front matter。Draft 状态、PRD 摘要和确认引用由工具生成；规范选择在候选基线中准确表达，工具受管字段以实际契约为准。
5. **由工具执行受控保存**：工具应核对目录、能力、读取引用、目标和输入版本、PRD 结构及有效用途确认，按契约使用锁、保留旧版并原子替换目标。Agent 不手工创建锁、归档或替换业务文件，也不自行解除在途锁。
6. **核对写后结果**：核对实际目标正文与本次提交、受管元数据、保存返回摘要，以及旧稿历史和必要输入版本。工具已返回可核验复读结果时直接核对，不为形式重复读写；工具未完成的核对如实说明，不能补称已验证。
7. **报告并结束**：按第 8 节分别报告文件保存、输入绑定、历史与结构检查结果，列出未决项和待验证范围，不自动登记、确认、启动下游或操作 Git。

当前 PRD 的同一版本和用途确认仍有效时，反复保存方案不需要重新确认 PRD；工具仍应在各次保存时核验当前有效性。PRD 已变化时按新版本处理，不能沿用旧确认。

首次保存的目标预期状态来自实际读取的缺失结果；已有目标使用其真实版本。相同保存结果应返回 unchanged，不重写文件或制造历史；是否完全相同包含工具生成元数据，不只比较正文。历史按完整旧文件的真实摘要标识，不自动分配 v0.1 等人工版本号。

读取引用不能跨项目或不同服务进程使用。过期、进程重启、已消费或相关输入变化后重新读取并比较候选基线；有效期、消费时机和重试规则以实际工具说明为准。不能假定预检查拒绝后引用一定可复用。

## 5. 检查及输入变化处理

### 5.1 保存资格与方案检查

当前 PRD 的有效用途确认是工程保存的输入条件，不能由方案检查通过替代。输入满足要求后，方案仍有明确 open／blocked 项时可以保存 Draft；披露未决项不等于批准后续实施。

只读检查按工具支持的对象执行。工具只检查当前文件时，不把结果移用于尚未保存的候选；保存后附带检查时，核对所检查摘要是否对应本次保存版本。未完成、检查异常或观察到另一版本时，报告检查范围和缺口，不声称通过。

检查结果不自动修补正文。章节、引用、覆盖表或必需字段的问题，交给方案角色判断并按请求修订；机器检查不能证明业务含义正确、技术时序可渲染、模型效果已通过或真实服务已联通。

### 5.2 来源或目标发生变化

| 发生变化的对象 | 处理方式 |
| --- | --- |
| 当前 tech-spec | 读取与候选基线的差异，保留他人的有效修改，再整合候选；不覆盖新版本 |
| PRD 的范围、REQ／AC 或业务图 | 定位受影响接口、数据、状态、模型、异常、技术时序和覆盖表，修订候选并重新核对确认 |
| 源需求 | 核对 PRD 是否同步；不能把旧 PRD 的确认扩大到新增业务要求，待同步内容按主文档处理 |
| 项目类型、平台或规范选择 | 重新评估相关实现与环境约束，不能只更新文档头或忽略冲突 |
| 确认记录、登记或快照 | 重新进行只读核验；失效时停止工程保存，不自行补记录 |
| 实际采用的规范、协议或外部资料 | 核对变化是否改变关键设计，更新依据与待验证项，不宣称全部来源始终原子一致 |

更新摘要不等于完成设计适配。判断某项变化不影响当前候选时应保留简要依据，相关工具仍按其版本和确认规则核验，不由 Agent 绕过。

设计需要改变业务规则或 AC 时，按主文档返回需求变更建议。用户接受后，由需求能力按请求同步相关成果；重新读取新版与确认再继续，方案保存不代写需求或 PRD。源需求／PRD 已更新而方案保存失败时，分别报告现状，不自动回滚已完成的其他写入。

## 6. 历史读取与旧版恢复

1. 用户要求比较或恢复时，使用实际工具支持的方案历史能力，指定合法历史摘要。方案历史归 `docs/tech-spec-history/<旧版摘要>.md`，不能与需求／PRD 历史混用，也不接受任意路径来扩大读取范围。
2. 工具应核对历史为允许范围内的普通文件，实际内容摘要与标识一致。不存在、不可读、格式无效和摘要不符分别报告；历史问题不通过覆盖、删除或重新命名文件来掩盖。
3. 历史读取不修改当前文件。即使同次返回读取引用，其保存预期版本仍应对应当前目标和输入，历史版本不能直接用作当前目标的预期值。
4. 只有明确恢复请求才进入恢复。提取历史正文，去除当时由工具生成的受管元数据；保留其中重要选择与依据作为待核对材料，而非直接认定在当前条件下仍有效。
5. 对比当前 PRD、源需求、项目选择、外部条件和确认，修订不再适用的内容或说明冲突。恢复后的工程配置按当前设计判断，不能因历史写了某配置就跳过核对。
6. 作为新候选执行第 4 节保存，保留被替换的当前稿。工具生成当前基线和确认引用，旧版确认不会因恢复文件重新有效。不能保证恢复后完整文件摘要等于历史摘要；可以核对要求恢复的正文是否一致或说明必要差异。

新会话恢复采用当前实际成果，按主文档恢复范围、基线、有效选择、未决项和继续位置，不自动恢复旧版。历史保存不是 Git 提交、通用回滚或多文件事务。

## 7. 异常与失败恢复

先区分是否已发生目标写入及哪些结果仍可信，再决定下一步，不把所有异常都当作“未保存”。下列 saved／unchanged／not_written／saved_unverified／unknown 已是保存内核实现的五态契约，具体含义以工具返回为准。

| 结果或异常 | Agent 的处理 |
| --- | --- |
| saved | 核对写后证据并报告成功；仍为 Draft，不能推定已确认或登记 |
| unchanged | 接受未变化结果；不为制造版本重复修改或写入 |
| not_written | 报告目标未写入及原因，修正参数、条件或版本后重新读取；若工具报告已产生历史等中间副作用，也分别说明 |
| 目标或输入版本冲突 | 停止覆盖，读取并比较差异，修订候选后按正常流程提交 |
| 读取引用无效、过期或进程重启 | 重新读取，并核对候选基线；不能重新拼造引用或借用其他项目引用 |
| 确认 missing／outdated／invalid／unavailable | 说明具体原因和补齐条件，可继续讨论独立部分，不保存工程方案 |
| unknown | 无法确定是否写入，先读取目标、元数据和历史，不直接重试 |
| saved_unverified | 工具已返回保存相关结果，但指定写后核对不足或失败；按失败项读取目标、历史或输入，不能补称成功，也不直接重复覆盖 |
| 锁冲突或操作中断 | 核对可观察状态和在途操作，不自行删锁；无法核实时报告具体阻碍 |
| 保存成功但结构检查异常／未完成 | 保留已核实的保存结论，另报检查缺口；不因检查失败重复保存相同正文 |

排查 unknown／saved_unverified 时，使用最后一次实际提交正文、工具返回和当前文件比较：目标是否为预期候选，输入是否变化，旧稿是否仍可核对。当前文件恰好相同不足以单独证明全部保存步骤或调用顺序成功；无法确定的部分继续保留。

必要修复或重试仍通过对应工具，并核对原请求是否涵盖该动作。不得以“修复保存”为由改写确认、登记、PRD、需求或历史；不得自动回滚其他已经成功的成果。已知目标写入和其他检查未完成时，分别报告，不隐藏部分成功。

## 8. 操作完成后的报告与按需验证

### 8.1 日常操作报告

通常说明以下实际取得的信息即可，不为每次保存另建报告文件：

- 项目、本次操作与方案路径，保存／未变化／未保存／待核对的真实状态。
- 本次方案版本或摘要、采用的 PRD 与相关来源版本、确认核验结果和工程配置。
- 旧版是否保留、核对了哪些写后内容，以及未能核对的部分。
- 结构检查针对哪个版本、检查结果与限制；人工走查和真实验证分别说明。
- 本次变化、阻塞项、待决定／待验证内容及下一步。

仅讨论或工具未接通时明确交付的是候选，不能给出虚构的保存版本、历史或确认 ID。单独读取与检查报告实际对象和结果即可，无须把全部保存字段填成空表。

保存 Draft、结构检查通过、正式确认、成果登记、交接、Git 和下游启动是独立事实，只报告实际发生的操作，不因文件存在或正文完整推定其他动作完成。

### 8.2 连续保存与历史验证

仅在用户明确要求验证时执行，优先使用已明确范围的隔离项目。没有对应工具或当前 PRD 没有有效用途确认时，说明阻碍，不临时伪造确认或放开保存条件。代码测试夹具中的确认数据不能冒充真实用户确认链路。

1. 核对测试项目和输入，取得完整基线正文、当前元数据及摘要；明确测试修改范围，日常保存不自动插入备注。
2. 按正常流程保存基线，相同结果接受 unchanged。
3. 重新读取，加入明确的工具验证段落，说明其仅为测试、不是业务设计；通过受控工具保存。
4. 重新读取，只移除本次测试段落并恢复基线正文；输入条件变化时先处理差异，不强行恢复。
5. 按工具返回的历史摘要读取相应旧稿，核对基线、测试稿、当前正文与 Draft 元数据，并检查原输入是否变化。
6. 报告真实调用、目标和历史核对结果、失败及未验范围。中途失败先读取核实，可能残留测试段落时明确指出，不声称已恢复，也不绕过工具清理。
