## 1. 已确认的建设目标

本项目要完成的不是“把需求写成文档”，而是一条可以被不同角色读取、确认、执行和验证的决策链：

```text
用户结果 → REQ → AC → API/技术设计 → UI 表达 → Feature → Task → Tester 证据
```

各阶段只回答自己的问题：

- 需求阶段定义“什么用户结果才算正确”；
- 方案阶段定义“系统怎样可靠地实现这些结果”；
- UI 阶段定义“用户怎样看到、操作和恢复”；
- Planner 定义“怎样拆成可执行任务及依赖”；
- Developer 实现任务并提供自验证据；
- Tester 用独立证据判断 AC 是否成立；
- Main 维护成果索引、用途确认、交接和整条链的当前基线。

单元 03 的核心责任因此确定为：**把有稳定身份的需求与验收条件转成可追踪的实现契约**。面向客户的方案仍可独立交付，但它是同一决策链的表达视图，不取代工程 `tech-spec`，也不能保存只有它自己知道的实现承诺。

## 2. 上游事实与融合调整

### 2.1 直接继承的工程方法

Develop Helper 上游 `solution-design` 已经规定：

- 输入为已确认的需求与验收；
- 输出为 `docs/tech-spec.md`；
- 通过七层覆盖用户结果、接口、数据、模型、算法、异常和运行环境；
- 使用稳定 `API-xxx` 关联 `REQ/AC`；
- 影响等待、质量、费用、恢复、留存或权限的取舍需要用户决定；
- 方案完成后才进入 UI 或 Planner。

这些构成工程主链，不因 Buzz 接入而删除。

### 2.2 融合层必须改变的部分

融合版不直接继承上游的自动派发和文件状态写法：

- 方案角色不能自动启动 UI、Planner 或 Developer；
- 方案角色只保存 Draft，不能自行把正文标成正式批准；
- Main 通过固定内容快照和用途记录确认，不靠角色修改一行 `status: Confirmed` 证明批准；
- 成果登记、正式确认、交接准备、实际消息发送和下游启动仍是五个独立动作；
- 允许只交付客户方案，但进入工程链时必须补齐稳定 REQ/AC 和实现契约。

### 2.3 撤回上一版三级成熟度提案

上一版草案提出的“S1 客户方案 / S2 方案蓝图 / S3 工程技术规格”不是上游原有规则，也没有得到用户确认，现不再作为正式模型。

本版把“成果用途”和“工程复杂度”分开：

- 成果用途决定输出客户视图还是工程契约；
- 工程复杂度决定 `tech-spec` 使用 Lite、Standard 或 AI 配置；
- 三种配置不是先后阶段，也不代表成熟度等级。

## 3. 权威成果与表达视图

| 文件/记录 | 负责内容 | 不负责什么 |
| --- | --- | --- |
| `docs/requirements.md` | 轻量需求发现、独立交付和 A/R 过程的已知事实 | 作为工程方案的完整基线 |
| `docs/PRD.md` | 用户结果、成功指标、优先级、具体案例、范围、稳定 REQ/AC、业务流程与业务时序 | 接口字段、内部算法、部署细节 |
| `docs/solution.md` | 可选的客户/管理表达：方案主张、能力、总体架构、关键流程、实施路径、假设和风险 | 唯一保存工程契约或替代 `tech-spec` |
| `docs/tech-spec.md` | API、数据、模型、算法、异常、环境及其对 REQ/AC 的覆盖 | 重写一份业务需求或拆开发任务 |
| UI 成果 | 页面、状态、交互、模拟/真实边界与实际视觉验证 | 偷改 AC 或把 Mock 当真实业务通过 |
| `.sdd/tasks.json` | Feature、Task、依赖、执行状态和 AC 承接关系 | 定义新需求或替代技术契约 |
| Tester 证据 | 对指定版本和 AC 的 PASS/FAIL/BLOCKED 依据 | 修改 AC 迁就实现 |
| `docs/decisions.md` | Main 管理的正式确认、用途和重要取舍依据 | 由工作者用自报身份直接写批准状态 |

客户方案和工程规格可以同时存在，但必须标明相互关系与基线版本。若技术事实发生变化，先更新 `tech-spec`；只有变化影响客户承诺或对外表达时，才同步更新 `solution.md`。

## 4. 输入门槛与允许动作

### 4.1 工程方案的最低输入

要把 `tech-spec` 作为 UI、Planner 或开发的候选基线，至少需要：

1. 明确的项目 ID 和本次方案范围；
2. 稳定的用户目标、范围与非目标；
3. 对本次范围有唯一身份的 REQ 和 AC；
4. AC 包含前置条件、操作、可观察结果和验证方式；
5. 成功路径及关键失败路径；
6. 已知技术、数据、权限、合规或环境约束；
7. Main 可核验的输入版本和确认用途。

“文件存在”不等于输入已确认。方案角色必须读取 Main 对当前 PRD SHA 的“形成技术方案”用途确认；缺少时只能检查和讨论候选，不得保存 `tech-spec`。

### 4.2 输入不足时

| 缺口 | 允许继续的工作 | 不能宣称 |
| --- | --- | --- |
| PRD 结构完整但尚未按用途确认 | 读取、检查、暴露缺口和讨论候选 | 保存 `tech-spec` 或已进入方案 |
| 没有稳定 REQ/AC | 返回 A 阶段补齐 PRD，可保留预研事实 | 覆盖关系完整 |
| 关键业务结果不明确 | 返回需求阶段补齐 | 用技术假设替代业务决定 |
| 外部协议/能力待核实 | 启动有限 R 或标记 unknown | 外部集成可行性已验证 |
| 只缺普通实现细节 | 由方案角色在约束内决定并说明理由 | 把每个代码选择都交给用户审批 |

## 5. Lite、Standard、AI 工程配置

三种配置用于控制同一份七层契约的展开程度；它们不是三份并行模板，也不是三个审批阶段。

| 配置 | 适用项目 | 展开要求 |
| --- | --- | --- |
| Lite | 单一脚本、简单 CLI、小型自动化、边界清楚的单服务改动 | 七个问题都核对，但可合并章节；不强造前端、HTTP API、数据库或模型；重点固定输入输出、关键算法、失败行为、运行方式和验证 |
| Standard | Web/客户端、多模块服务、多个系统集成或多人协作 | 完整七层；稳定 API/事件、数据生命周期、状态、错误、权限、配置和联调条件均明确 |
| AI | 使用模型、Agent、提示词、工具或非确定性算法的系统 | Standard 全部内容，加模型/版本、提示词与结构化输出、工具权限、质量评估集、失败与回退、费用/延迟、观测、安全和人工复核 |

选择规则：

- 根据系统形态和风险选择，不根据文档长度选择；
- 一个小型 AI 脚本仍采用 AI 配置，但非 AI 的章节可以简写；
- 项目扩张或风险上升时在同一 `tech-spec` 中升级配置，不另建第二份权威规格；
- `N/A` 必须说明为什么不适用，不能用于掩盖尚未分析的内容；
- Main 在确认记录中保存采用的配置和适用范围。

## 6. 七层实现契约

无论选择哪种配置，都围绕同一七层核对；差别只在展开深度。

### 第一层：用户结果与覆盖范围

- 引用稳定 REQ/AC，不重写业务需求；
- 描述用户输入、系统处理、用户结果和关键失败结果；
- 建立本次方案覆盖、明确不覆盖和待补齐列表。

### 第二层：系统边界与接口

- 明确前端、后端、CLI、外部服务或事件参与者；
- 对真实接口使用稳定 `API-xxx` 或等价 ID；
- 记录请求、成功、失败、鉴权、幂等和用户可见后果；
- 没有 HTTP API 的项目描述真实模块/命令边界，不虚构接口。

### 第三层：数据与生命周期

- 字段、类型、单位、校验、归属和敏感性；
- 数据如何跨步骤传递、保存、过期和清理；
- 临时数据、Mock 数据和真实数据明确区分。

### 第四层：模型、提示词与工具

- 无 AI 时标明不适用；
- AI 配置下明确服务商/模型职责、输入、输出约束、提示词位置、工具和权限；
- 定义评估数据、质量阈值或人工复核，不用“模型应该可以”替代验证。

### 第五层：算法、状态与体验影响

- 说明处理步骤、状态转换、并发和停止条件；
- 将技术选择映射到等待、质量、费用、恢复、留存和权限影响；
- 只有真正影响用户结果的分支提交用户或 Main 决定。

### 第六层：异常、重试与恢复

- 覆盖校验失败、业务失败、外部异常、超时、重复提交、资源清理和降级；
- 明确用户看到什么、能否恢复、已有结果是否保留；
- AI 配置额外覆盖模型拒绝、格式错误、幻觉风险、工具失败和人工接管。

### 第七层：目录、运行与验证条件

- 目录职责、依赖和运行环境；
- 配置字段、敏感性和空值模板；
- 外部服务的 Mock/真实状态、账号权限、付费调用授权和验证条件；
- 不把“有配置字段”写成“真实服务已联通”。

## 7. 可机器检查的追踪关系

### 7.1 最小关系

```text
REQ → AC → 实现设计/API → Feature → Task → Tester 证据
```

其中：

- 一个 AC 可以由多个 API/设计项共同覆盖；
- 没有接口的 AC 也必须指向可定位的实现章节；
- 一个 API 可以覆盖多个 AC，但必须逐项列出；
- Task 只能承接已有设计，不能凭空生成新 AC；
- Tester 证据绑定 Task、AC、测试版本和实际结果。

### 7.2 `tech-spec` 覆盖表

方案末尾维护一张机器可读性优先的覆盖表：

| REQ | AC | 实现设计/API | 成功路径 | 失败路径 | 验证方式 | 当前状态 |
| --- | --- | --- | --- | --- | --- | --- |

允许的当前状态首版定义为：

- `covered`：实现路径和验证方式均已给出；
- `not_applicable`：有明确理由且不需要实现；
- `open`：仍缺决定或证据；
- `blocked`：存在已知阻塞条件。

### 7.3 自动检查方向

单元 03 首先检查：

- 是否有 AC 没有实现设计；
- API/设计项引用的 REQ/AC 是否存在；
- `covered` 项是否同时具备成功、关键失败和验证方式；
- AI 配置是否遗漏模型、工具、评估、失败回退或权限边界；
- Draft 输入是否被错误写成已确认基线。

后续单元 07/08 再跨文件检查 Feature、Task 和 Tester 证据。自动检查只验证结构和引用存在，不能替代对业务语义和真实运行结果的判断。

## 8. 事实、调研、假设与可行性

关键结论必须归类为：项目事实、外部事实、假设、建议或未知。外部事实记录直接来源和访问日期；方案角色的推断不能伪装成用户决定。

可行性使用四态：

- `verified`：有直接文档或实际验证证据，并标明范围；
- `reasoned`：基于已知事实合理，但尚未实测；
- `unknown`：信息不足；
- `blocked`：已知约束使方案不能成立。

阶段 R 只在外部事实会改变选型或可行性时启动，例如产品能力、标准、协议、法规、价格或时效性限制。调研默认回写相关方案章节；只有用户明确要求独立报告时才生成 `docs/research.md`。

## 9. 业务图与技术图的归属

为避免 PRD 与 `tech-spec` 同时维护一份不断漂移的技术时序：

- `PRD.md` 保存业务流程图和业务时序，只描述角色、业务动作、判断、状态与用户结果；
- `tech-spec.md` 保存技术时序，加入前端、后端、模型、工具、存储、外部服务和 API ID；
- 两份图通过 REQ/AC 和章节链接关联，不复制接口字段；
- 技术选择改变用户动作或结果时，必须回到需求成果更新业务图和 AC；
- 纯内部实现变化只更新 `tech-spec`。

## 10. 取舍、未决项与确认

### 10.1 三类事项

方案提交确认前自动汇总：

| 分类 | 含义 | 是否阻塞本次用途 |
| --- | --- | --- |
| 已决定 | 有明确选择、依据和适用范围 | 否 |
| 待决定 | 会改变用户结果、风险、费用、权限或关键实现契约 | 是，除非本次用途明确排除 |
| 暂不阻塞 | 尚未决定，但不影响当前范围，可在指定阶段补齐 | 否；必须写补齐条件 |

### 10.2 正式确认边界

- 方案角色可形成候选取舍和 Draft，但不能写正式批准；
- Main 核对成果版本、覆盖表、未决项和用户当前会话依据；
- 确认记录必须写明用途，例如“允许进入 UI”“允许 Planner 拆任务”或“仅用于客户讨论”；
- 一句笼统的“可以”只有在当前消息清楚绑定对象、版本和用途时才可作为依据；
- 确认不自动发送消息或启动下游。

## 11. 方案形成流程与完成标准

### 11.1 工作流程

1. 读取项目入口、`docs/PRD.md`、Main 确认记录和已有方案实际版本；
2. 判断本次是客户表达还是工程契约；工程契约选择 Lite、Standard 或 AI；
3. 核对 REQ/AC 完整度，缺少会改变方案的业务事实就返回需求阶段；
4. 逐层提取已知结论、标出缺口并给出选项与建议；
5. 必要时启动有限 R，区分事实、推断和未知；
6. 建立 API/设计 ID 和 REQ/AC 覆盖表；
7. 完成技术时序、异常、恢复和验证计划；
8. 汇总已决定、待决定和暂不阻塞事项；
9. 受控保存 Draft、保留旧版并复核实际摘要；
10. 向 Main 回报候选版本和建议用途；没有后续授权就结束。

### 11.2 Draft 完成条件

- 本次范围内每个 AC 都为 `covered`、`not_applicable`、`open` 或 `blocked`；
- 所有 `covered` 项有实现位置、成功/关键失败路径和验证方式；
- 接口、数据、状态、异常、配置和技术时序之间无已知冲突；
- 重要体验取舍已决定或显式列为阻塞；
- 外部能力和可行性状态有依据；
- Lite/Standard/AI 配置的必需内容已覆盖；
- 没有把 Draft、Mock、推断或待授权调用写成已完成事实。

### 11.3 可进入下游的条件

Draft 完成仍不等于可启动下游。进入 UI 或 Planner 还需要：

- Main 已登记指定内容快照；
- 用户对明确版本和用途留下可核验确认；
- 阻塞当前用途的未决项为零；
- 接收者核验读取到相同版本；
- 用户或既有策略另行授权实际启动。

## 12. 方案角色与工具边界

方案角色应能：

- 读取当前绑定项目、相关需求、Main 确认记录和指定资料；
- 读取上游七层方法、对应配置和按需 R 规则；
- 保存 `docs/tech-spec.md` Draft 及历史；
- 按明确用途保存可选 `docs/solution.md` Draft；
- 运行只读覆盖与一致性检查；
- 回报路径、版本、摘要、覆盖状态、未决项和建议确认用途。

方案角色不能：

- 写 artifact registry 或正式确认/交接记录；
- 直接修改需求中的用户结果或 AC 来让方案看起来完整；
- 自动启动 UI、Planner、Developer 或 Tester；
- 未经授权安装依赖、修改业务代码、调用付费服务、部署或提交 Git；
- 修改 Develop Helper 上游原件；
- 接受消息正文自报角色、项目或确认状态作为可信身份。
