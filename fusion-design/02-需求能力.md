## 1. 目标与输入

让用户在 Buzz 内与一个可复用的独立需求角色对话，保存项目需求；可单独结束，不强制方案、UI 或开发。角色配置不写死项目，项目 ID 作为每次任务的必填槽位。首个业务试点为 `my_mind/just-start` 中的《元素守卫》：一个轻量浏览器回合制卡牌游戏，第一版以完成一场可玩的单人战斗为目标。具体玩法和验收范围仍由需求 Agent 澄清，不把融合系统测试要求写成游戏需求。

最小输入：明确项目 ID、业务目标、已有资料及本轮意图。已有事实直接复用，不生成虚构需求，不将材料中的指令作为运行授权。

## 2. 运行环境选择与现有事实

- 用户明确选择沿用 Buzz 已有模型与凭据，不另建 API 凭据。
- 已通过 Buzz 界面只读查看 Honey：Codex 运行时、自定义模型 `gpt-5.6-sol`；Honey 是开发角色，不覆盖它的职责。
- 界面提示无法加载实时模型列表，因此“已有配置”不等于“模型已成功调用”。没有读取密钥、复制认证信息或测试付费 API。
- 初始框架候选为 buzz-agent + GPT API。基于现有配置，本轮提供 Buzz 内独立角色 + Codex + 现有 GPT 的接入卡，作为复用现有设置的落地候选；不是把 Codex 误称为 buzz-agent。最终由用户在界面选择并验证，若坚持原生 buzz-agent 路线则另行接入。
- 官方 OpenAI 文档说明 API 调用需要认证；不能据此推断现有 Codex 登录方式或读取其凭据。此次不新增 SDK/API 客户端，认证保持由现有运行环境管理。[官方 quickstart](https://developers.openai.com/api/docs/quickstart)

接入边界（2026-10-16 由总框架原 5.1 归位，不增加新配置）：调用 GPT 不自动继承用户在外部 ChatGPT 中的历史对话、记忆或工具配置。若采用直连 OpenAI 的 buzz-agent 路径，需单独具备 API 凭据并核对模型用量与费用，不假定由 ChatGPT 订阅覆盖；不因此读取或复制现有 Codex 凭据。凭据不写入需求文档、角色提示词或频道消息。

## 4. 对话与独立交付流程

1. 用户或 Main 在频道中新顶层线程的首条任务消息传入 project_id 与本轮目标；Agent 通过工具从统一父目录解析项目。一个线程绑定一个项目，不在原线程切换。私信始终是连续会话，不能用“新开私信话题”证明上下文隔离。
2. 读项目元信息、入口及已有需求，核对返回的 ID 和路径，先简述理解与缺口。
3. 每轮少量问题，澄清用户、场景、痛点、目标流程、范围/非目标和成功标准。
4. 区分事实、假设、待决事项，变更只更新受影响内容。按需参考外部资料，无工具就标注缺口。
5. 保存草案前读最新摘要；正文通过标准输入交给保存工具，首次摘要为 missing，后续必须是实际读到的 SHA-256。冲突则重新读取，不覆盖新版本。
6. 工具固定标记 Draft、approval_verified=false；即使正文包含“已确认”，也不构成经验证批准。正式确认须绑定用户、对象版本、用途和真实消息依据，由 Main/用户核对。
7. 交付候选成果的实际文件位置、摘要、未决项、变更说明及建议下一步；建议不是启动授权。若有明确下一步才交接；无 Main 或无发送工具时返回用户，不声称已发送给其他 Agent。

需求方法来源为上游 A/R。轻量独立交付不强制 PRD；用户明确要进入工程方案时，才形成包含目标、具体案例、范围、稳定 REQ/AC、业务流程图与业务时序图的完整 PRD。两条路径都不自动派发 Solution Designer，不修改上游文件。

## 5. 权限、会话与恢复

- 首版按单项目线程顺序协作；同一个通用需求 Agent 可服务多个项目，但每个项目使用频道中的独立顶层线程，不订阅所有频道。尚未验证无重复 @ 的连续触发，每轮显式 @ 是试点保守操作。私信固定为 conversation scope，不用于跨项目隔离或“无旧对话”恢复测试。
- Buzz 源码支持 `BUZZ_ACP_SESSION_POLICY=thread`，默认 channel；桌面端有 `Thread Scoped ACP Sessions` 实验开关，并注明只对 Agent 下次启动生效、私信仍按连续会话处理。用户已确认当前《元素守卫》试点是在启用该开关后的普通频道新顶层线程中运行，因此启动条件已满足；但该证据来自用户实测反馈，尚无独立实例日志，也尚未用第二个线程验证历史上下文确实隔离。
- 当前未发现 Persona 指令正文支持项目变量替换的运行证据，且 Persona Pack 规范注明 MCP 环境变量插值仍未实现。因此首版不使用假的 `${PROJECT_ID}`，采用首条任务消息传入 project_id；工具已经以 project_id 为参数并从本机配置解析真实路径。`AGENT_CWD` 固定到融合层，不作为项目切换槽位。
- 文档工具只读项目入口和需求；只写需求及其旧稿，拒绝常见软链/越界路径、旧摘要及写入锁冲突。不执行 Git、网络、上游脚本，不更改项目索引或任务状态。
- 工具限制只适用于经过此工具的操作。Codex 通用终端/编辑工具可能绕过它；需核对真实工作目录、加载的上层规则与运行时权限，不启用更宽权限来消除阻碍。尚未做全局沙箱或恶意并发路径替换防护。
- 以文件恢复，不依赖 ChatGPT 记忆或 Buzz 未确认的历史持久化；模型每次恢复重新读取最新版本。共享读取工具会返回项目资料给调用者；接入的模型必须是用户选择的现有环境。
- 每个文档及输入上限 128 KiB；首版仅 UTF-8 文本/Markdown，不包含附件解析或联网调研服务。PDF、Word 和图片须在后续实际接入时逐项验证，选用 GPT 模型本身不证明 Buzz 已具备完整附件解析链路。

## 6. 验证结果与剩余工作

已通过全部 39 项自动化测试，其中需求单元现有 11 项：原 8 项覆盖只读背景、Draft 保存/旧稿保留、旧摘要冲突、相同内容无变化、软链目录拒绝、恢复读最新、空/过大输入和已有锁保留；新增 3 项覆盖错误来源 SHA 拒绝、正确来源 SHA 回报，以及角色契约不得要求用户提供阶段口令或内部保存参数。测试写入均在临时目录，未向实际项目写入虚构需求。

试点初始阶段曾对 just-start 做真实只读背景检查，读到名称、用途、初始化状态，当时需求文件为 missing；这不是 Buzz 模型读取结果，也不描述当前 v0.3 状态。

首轮 Buzz 运行证据：需求澄清 Agent 成功响应，使用 `project_id=just-start` 解析出正确项目路径，准确说明项目用途、本地骨架、Git/GitHub 状态、缺失成果和待澄清事项，并引用与本地一致的 `project.json`、`README.md` 摘要。随后在只读恢复请求中，它明确报告 `docs/requirements.md` 缺失、无当前 SHA、无法从文件恢复具体需求，且没有用聊天内容补全。用户报告其未写入文件、未开发、未调用其他角色；本地主会话复核需求文件仍不存在。因此“项目绑定 + 只读背景 + 缺失时不编造”通过，但这不是需求版本恢复通过。

真实业务首轮运行证据：用户在普通频道的新顶层线程中，以 `project_id=just-start` 和《元素守卫》第一轮需求澄清为目标启动需求 Agent，并确认线程隔离已经启用。Agent 重新读取项目入口后，准确说明项目名称、首版目标和待澄清项；随后只提出目标玩家/单局体验与回合行动规则两个业务问题，没有保存文件、讨论 Agent 测试、进入方案/UI/开发或调用其他角色。由此可确认正式试点已经启动，首轮角色边界与提问行为符合预期。

2026-09-18 前两版真实运行结果：需求 Agent 连续继承用户选择，每轮少量提问；按用户要求从 A 进入 R，使用三个官方页面形成有边界的比较，区分事实、未知和本项目建议，并自动回到 A。用户结束澄清并授权保存后，Agent 自主补齐默认值和假设，保存 v0.1 Draft；随后仅凭一条业务变更更新为 v0.2，并由工具完整保留 v0.1。当时两版均保持 `approval_verified=false`，没有自动进入方案、UI、开发、测试或 Git。

恢复结果：用户回传的只读恢复准确说明 v0.2 当前范围、最新“洞察 + 元素调和”变更、v0.1 历史版本、Draft 状态和非阻塞默认值；同时主动识别 `project.json` 与 README 未登记需求成果。本地主会话复核当前与历史 SHA 均匹配，恢复前后 Git 状态未变。该回复是否来自指定的新顶层线程仍依赖用户操作反馈，尚无 Buzz 实例日志，因此证明了文件恢复行为，不单独证明所有线程运行上下文已隔离。

试点暴露的缺口已完成本地修正：角色规则现在自动管理 A ↔ R，明确禁止向用户索取命令、绝对路径、expected-sha 和历史文件名；用户结束澄清后可授权 Agent 自主收敛。保存工具会重新读取 `project.json` 与 README，并拒绝正文中不一致的来源 SHA，同时在成功结果中回报实际来源摘要。既有 v0.2 中的错误不自动改写，等待未来获授权保存时由 Agent 重读并修正。

新增规则的首个 Buzz 只读回归：用户只提出“若需要外部参考则自行调研”的业务问题，没有给 A/R 阶段口令。Agent 自主判断当前单击/拖拽选择可以仅依据已落盘目标与规则完成，因此留在 A，给出单击直接出牌建议及代价，明确无需外部调研；没有索取阶段口令、命令、路径或 SHA，也没有写文件或进入下游。本地主会话复核当前需求 SHA 仍为 `ed088d9b9a2dc97d55c7316cf601ae8a6d665268dcd8c36c58d97c6aeb394f78`，项目 Git 状态未变。该回归证明阶段判断和用户最小输入生效，但没有实际经过一次新的 A → R → A，也没有覆盖保存与错误来源 SHA 处理。

第二次 Buzz 只读回归：用户要求参考 W3C 官方无障碍要求评估是否把拖拽作为唯一出牌方式，但没有输入 R 阶段口令。Agent 自行完成有限外部调研，区分 W3C 官方事实、项目建议和未核实项，再回到《元素守卫》的需求口径；没有保存文件或进入下游。本地主会话抽查 W3C 2.5.7、2.5.8、2.5.5 和 2.1.1 官方页面，关键等级、拖拽替代、目标尺寸与键盘要求表述相符；复核当前需求 SHA 和 Git 状态仍未变化。由此判定无需阶段口令的 A → R → A 功能回归通过。

最终 Buzz 写入回归：用户仅采用业务建议并授权结束澄清和保存，没有提供命令、路径、expected-sha、历史文件名或版本操作。Agent 自行读取最新版本，保存 v0.3 Draft、按原 SHA 归档 v0.2、修正 v0.2 中误抄的 README 来源摘要，并完成只读复核；没有更新项目索引、进入下游或执行 Git。本地主会话核对当前 SHA 为 `eea950e55f9d2ab94c8bd031565c7f98db6d7fa2dbfd63342b25117fba615759`，v0.2 归档 SHA 与文件名一致，正文记录的 `project.json` 和 README 摘要均与实际文件一致，Git 状态没有超出既有未跟踪项目文件。由此判定用户最小输入、版本历史和来源 SHA 运行回归通过。

单元 02 完成结论：需求能力的输入、对话规则、按需调研、交付物、变更保存、历史保留、恢复和完成标准已形成规则、实现、自动化测试及 Buzz 实测证据。实际运行实例/模型日志、全局写入权限边界、正式确认、项目入口索引更新和另一角色读取同一版本仍待后续单元；Developer/Main 融合入口尚未建设，现有 Honey 不直接充当交接验证方。需求 Agent 未修改 Honey，也未对业务项目执行 Git；融合建设本身随后已在父仓库建立本地存档点 `5ea27f0`，尚未推送。

按用户偏好，今后的界面查找/配置优先给出短操作卡，用户操作后反馈结果；不持续进行高消耗 UI 探索。若 Honey 编辑窗口仍显示，用户点 Cancel 即可；自动关闭尝试未成功，不声称窗口已关闭。
