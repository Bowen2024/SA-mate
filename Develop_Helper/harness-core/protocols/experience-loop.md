# 错误与经验闭环

普通开发返工与独立 Bugfix 共用本协议（路径：`<harness_root>/harness-core/protocols/experience-loop.md`）。发生错误、复验修复或处理经验候选时才加载；不增加 Agent、任务状态或每次必写的报告。

## 一、错误先留事实

- Developer 自验发现错误，或 Tester 判定 FAIL 时，返回触发操作、预期/实际、受影响任务或功能、已尝试修复及证据；根因推测与已证实结论分开。自验中已修好的有效问题也随本轮结果交回，不只记录 Tester 的 FAIL。
- 编排器在任务 `notes`（路径：`<active_project_path>/.sdd/tasks.json`）保留简短错误与轮次记录，后续 PASS 不覆盖此前失败事实。长证据只保存一份并引用：验收报告（路径：`<active_project_path>/.sdd/test-reports/test-<task-id>.md`）或复杂 Bugfix 报告（路径：`<active_project_path>/.sdd/bug_fix/<实际报告名>.md`）。
- 独立 Bugfix 没有 tasks/任务 ID 时，编排器把简短问题与验证摘要记在工作日志（路径：`<active_project_path>/.sdd/work-log.md`），长证据仍按需引用单份报告；不为沉淀创建假任务或重建计划。实际写入时替换报告名，并返回绝对路径。
- FAIL、BLOCKED、未复验或根因未证实的部分只留在错误记录中，不作为“已验证的有效修复”写入经验。缺 Key 等环境缺项不等于代码缺陷。

## 二、复验后判断并落盘

1. Developer 修复后返回：根因与证据、有效修复、适用条件、下次如何避免，以及“建议沉淀/无需新增”的简短理由。普通无错误任务不输出这套字段；同轮琐碎试错合并描述，不逐个记录拼写修正。
2. Tester 复验原问题及直接影响路径，并核对经验候选的事实依据，区分已验证修复、推测根因和未经验证的推广。功能 PASS 不自动证明全部根因推断；候选证据不足不影响已满足 AC 的功能结论，只暂缓该经验。不得为验证跨项目推广扩大测试范围。
3. 每次有效修复经过 Tester 复验后，由编排器判断复用价值。已证实的技术限制、易重复的契约/配置错误、有效诊断或预防办法可沉淀；一次性输入失误、重复条目或证据不足则不新增。在原错误记录简注“已沉淀＋条目标题 / 已合并 / 不新增＋原因”，不建立第二份沉淀任务清单。
4. 由编排器唯一写入项目经验（路径：`<active_project_path>/.sdd/experience.md`），Developer、Tester 只提交建议和证据。缺文件时按模板结构创建；旧条目保留，触及相关项时逐步补齐，不批量迁移历史。
5. 独立 Bugfix 同样交 Developer/修复者提供结果、Tester 复验、主智能体作为编排器落盘；平台不支持子 Agent 时按开发循环的角色降级方式执行并注明实际验证方式，不能把自验称作独立验证。尚未完成必要复验时只记录事实。

## 三、条目结构与去重

每条以可检索的标题组织，包含：

- 关键词、适用条件（技术栈/版本/触发场景，已知才写）。
- 错误现象与已证实根因；有效修复；下次如何避免。
- 来源任务或无任务的 Bugfix 描述、复验日期、证据的项目相对路径与具体章节；交付时给出实际绝对路径。证据在 notes/工作日志时直接定位，不强制另写报告。
- 后续更新：同类复发时补充原因、调整及新的复验证据。已失效结论明确标注并指向替代条目，保留旧来源。

写入前用关键词定向检索这一个经验文件，按“相同原因＋适用条件”去重。同类复发更新原条目，核对是未读取、适用条件遗漏、未执行还是原结论错误；不能仅凭复发就断定 Agent 没读。修正条件和预防办法，不重复复制整段报错、日志或完整测试报告。不记录密钥和敏感原始数据。

## 四、下一次如何使用

- 编排器在首次派发任务或独立 Bugfix 定位前，按任务模块、接口、工具或错误关键词，在项目经验文件中检索相关标题并读取命中条目；文件不存在或无匹配就继续，不扫描目录或全量加载历史。同一任务后续派发复用已核对条目，任务范围或条目实际变化时再查。
- 将适用的条目标题、实际路径及简短提醒放入派发上下文；必要时作为 `context_files` 的真实章节，不放进 `rules_files`。Developer/Tester 沿用这些定位，不重新查整个经验库。
- 只有当前问题明确涉及跨项目规则、框架行为，或项目条目指向全局来源时，才定向检索全局经验（路径：`<harness_root>/memory/harness-experience.md`）。先核对条目的状态和适用条件；经验不能覆盖当前用户要求、确认的项目契约或所选规范，不把历史文案自动升级为强制规则。

## 五、从项目经验到全局经验

编排器发现跨项目价值时，在原项目条目中附上简短“全局候选”：可复用结论、适用范围、源项目/条目和证据、需要排除的项目特例；向用户提出具体候选，不自动复制。

用户授权后，由编排器定向去重并更新全局经验（路径：`<harness_root>/memory/harness-experience.md`），注明授权依据、来源、验证范围和适用条件；在项目原条目回链全局标题。已有明确授权沿用。未验证的跨项目推广不得写成普遍事实。

写入全局经验不等于修改 Skill 或规范。需要反哺框架时，提出具体目标文件和变更，按用户授权范围执行，保留经验到规则的来源关系。旧规则冲突时先标明已被取代或仅作历史参考，不静默覆盖当前流程。
