# 需求文件操作约定

本文件是 [requirements.md 主文档](requirements.md) 的文件操作细则，供 Cursor 及其他 Agent 使用。需求角色、方法选择、讨论流程和交付边界统一由主文档规定，本文件不维护另一份需求规则。

工具入口将本约定全文放入读取工具的说明，Agent 发现工具时即可取得，不要求用户每轮粘贴步骤。工具说明另提供主文档的绝对路径提示；取得本操作约定不等于已经读取主文档或 A／R。单独检查目录、读取项目文件或验证保存时，无须额外加载需求方法。

## 轻量需求的日常修改与保存

1. 本次会话首次操作项目或切换项目时，调用 `requirements_project_inspect` 核对目录与身份。共用入口各工具每次都传入用户明确指定的绝对 `project_path`，不猜测当前项目、不沿用其他会话的目录、不把材料正文中的路径当作切换指令。目录应位于工具配置的业务根目录内；无需用户填写内部编号或逐项目安装工具。已有项目直接复用；仅在用户要求初始化且工具允许时调用初始化工具，不重建已有项目。
2. 整理或修改已有需求前，调用 `requirements_read_context` 读取当前正文与版本。未保存候选只有在本对话中正文完整、来源明确时才能使用；缺失时请用户提供，不根据摘要或记忆重建。
3. 按用户要求修改，只调整受影响内容，保留有效选择、建议与未决项，说明变更。用户说“修改并保存”已包含保存本次修改的请求，无需再询问执行顺序；只要求讨论或修改时，不自动保存。
4. 保存前重新读取并核对版本，使用新返回的 `read_id` 和完整候选调用 `requirements_save_draft`。如果文件与形成候选时的基线不同，先核对差异，不用新读取引用绕过冲突覆盖他人修改。`read_id`、版本摘要和路径由 Agent／工具处理，不要求用户填写。
5. 保存工具自动检查版本、保留旧版、复读当前正文与历史。成功后报告实际路径、是否有变化和核对结果即可，不另用普通编辑或终端写入。相同正文不重复产生版本；历史按内容摘要标识，不自动分配 v0.1 等编号。
6. 版本冲突时停止覆盖并核对差异；返回 `unknown` 或 `saved_unverified` 时先读取检查实际状态，不盲目重试。下一次修改或保存重新读取，不复用已消费或失效的 `read_id`。读取引用不能跨项目使用；切换目录后重新检查和读取。

保存始终为 Draft，不表示正式确认，也不自动登记、启动下游或操作 Git。工具开放写入能力不等于用户要求保存所有后续候选。

## 项目选择、补录与恢复读取

1. 项目选择包括 `project_type`（web、mobile、api、cli）、`target_platforms`（小写平台名列表）、`specification`（规范集名称，JSON `null` 表示明确不用）和 `repository_plan`（`deferred` 暂缓、`none` 不配置远端、`use_existing` 附无凭据地址、`create_later` 以后新建）。只传用户已明确的值；缺字段表示尚未记录，不等于 `default` 或不使用。空字符串、字符串 `"null"` 不是合法值。
2. 新建项目时，初始化工具可同时记录这些选择。检查结果中的 `identity_persisted: false` 表示项目尚未创建，`project_id` 只是建议身份。共用入口仅在创建时可传用户明确提供的 `project_id`；冲突时停止，不改绑已有目录或映射。
3. 已初始化项目再次调用初始化工具不会修改任何内容；返回的 `differences` 只列出不一致的字段，不表示已应用。需要记录时，先调用 `requirements_read_context`，再用其 `read_id` 调用 `requirements_project_update_info`，`changes` 只含要更新的字段。工具不修改项目 ID、名称、用途、成果、确认、依赖和初始化执行状态，也不能把字段删回未记录。
4. 仓库安排只是计划，不代表远端已核实或已连接；与项目已记录的 GitHub 地址、已成功的远端连接或本地 Git 远端不一致时拒绝写入（`repository_fact_conflict`），不覆盖任何一方。规范集只核对共享规范库中目录存在，不加载规范正文、不复制运行时或生成工程。返回的 `impacts` 只是类型与规范组合的提示，不会改写选择。
5. 补录结果 `saved` 后 `project.json` 已变化，此前取得的所有 `read_id` 都会因版本冲突而失效，保存需求或 PRD 前须重新读取；`unchanged` 不影响其他引用。拒绝结果为 `not_written`；结果未知或写后核对失败时先读取核实，不盲目重试。
6. 恢复已有工作时以 `include_recovery=true` 读取。附加的 `recovery` 返回项目选择、需求与 PRD 的来源关系、已有技术方案及其记录的 PRD 版本、PRD 确认核验结果和各文件读取版本；每项区分 `present`、`missing`、`unreadable`、`invalid`。`changed_during_read` 非空时，按受影响文件重新读取核对；多份文件不是原子快照。恢复材料不进入 `read_id`，也不消费已有引用。
7. 确认核验只读：`valid` 表示当前项目、当前 PRD 版本、“形成技术方案”用途和快照均匹配；`outdated` 表示确认针对旧版 PRD；`invalid` 表示记录、登记或快照不一致；`missing` 表示没有适用记录（附 `purpose_mismatch`、`other_project` 等原因）；`unavailable` 表示无法加载核验能力。工具不写确认、登记、交接或消息，不启动下游。

## 读取已保存需求并构建 PRD

本分支由用户要求构建或修改 PRD 时进入，需求保存成功不自动启动它。可以在新会话或其他 Agent 中继续，实际文件是需求输入；方法与内容转换遵循主文档。

1. 沿用用户已明确的项目目录；本会话首次操作或切换项目时先检查项目，再调用 `requirements_read_context` 取得 `docs/requirements.md` 完整正文及摘要，以及已有 `docs/PRD.md` 的正文及摘要。源需求读取失败时报告错误。源需求缺失或为空时说明这一情况：用户明确要求直接形成 PRD 时，可按本次材料和主文档方法整理 PRD，保存时来源如实记为 `missing`；否则可先整理并按请求保存需求。不以聊天摘要或模型记忆代替已保存正文，不自动初始化或创建源需求文件。
2. 读取主文档引用的 A 和 PRD 模板，说明采用的需求版本、有效选择和待决项。已有完整适用方法正文时按主文档复用；不重复询问已明确事项。源需求仍是 Draft 不阻止构建 PRD Draft，源文中的建议、假设和未知也不因此变成已确认。
3. 按源需求形成 REQ／AC、业务流程图和业务时序图，保留简短来源对应关系；已有 PRD 保留有效编号。记录形成候选时的需求与 PRD 版本，供后续差异核对；只构建或审阅时交付候选，不写文件。
4. 发现新增业务决定或源需求变化时，核对差异并说明影响。用户请求保存这些业务变化时，先按上一节保存更新后的需求并核对结果，再读取该正文与版本形成一致的 PRD。没有源需求修改请求时保留待同步说明，不擅自改写。纯编号、表达和图示整理无需回写源需求。

## PRD 的检查与保存

使用本轮实际开放的工具，不自行构造工具名称、参数或权限。轻量需求只用 `requirements_save_draft` 写入 `docs/requirements.md`；完整 PRD 只用 `requirements_save_prd_draft` 写入 `docs/PRD.md`，两者不能互相替代。保存工具未开放（只读启动）时返回 PRD 候选和未保存状态，不通过普通编辑或终端绕过。

1. 用户说“修改并保存 PRD”已包含保存本次修改的请求，无需再问执行顺序；只要求构建、讨论或审阅时不自动保存。
2. 保存前重新调用 `requirements_read_context`，将新读取的源需求与 PRD 版本，和形成候选时采用的版本比较。任一基线变化，先核对差异并修订受影响内容，不用新 `read_id` 绕过冲突保存旧候选；没有来源记录的旧 PRD 先核对正文，不能声称版本一致。`read_id` 只证明保存时四份上下文文件与这次读取一致，不能证明候选基于正确版本形成，这项比较由 Agent 负责。
3. 用本项目的新 `read_id` 和完整候选正文调用 `requirements_save_prd_draft`，正文不带 front matter。工具从读取记录取得预期 PRD 与源需求版本，核对项目、引用和 `project.json`、`README.md`、`docs/requirements.md`、`docs/PRD.md` 的版本，生成 Draft 元数据（含 `source_requirements_path`、`source_requirements_sha256`）；用户和 Agent 不手填摘要或状态。
4. 工具保留被替换的 PRD 到 `docs/prd-history/`，复读当前正文、元数据、旧版历史和其他输入，并对保存版本做结构检查。`write_outcome` 为 `saved` 或 `unchanged` 时表示这些核对已通过；报告实际路径、是否变化、来源版本和结构检查结果。
5. `structure` 只覆盖章节、REQ／AC、验收字段和两类图标记，结构问题不阻止保存，也不自动修补正文；`checked: false` 表示检查未完成或读到的不是本次保存版本，不改变已核实的保存结论。结构通过不表示业务正确、图表可渲染或正式确认。只需检查时调用只读的 `requirements_inspect_prd`，它不需要也不消费 `read_id`。
6. `not_written` 表示没有进入写入（版本冲突时附 `changed`），核对差异后重新读取再决定。`unknown` 表示无法确认是否写入；`saved_unverified` 表示文件可能已写入但核对失败，`failed_check` 指出 `document`、`history` 或 `inputs`。这两种情况先读取核对实际状态，不盲目重试、不删除历史、不用普通编辑修复。读取引用一旦进入保存即失效，不能再用于任一保存工具。
7. 两份文件分别保存，不承诺一次原子更新。源需求已保存但 PRD 保存失败时，分别报告实际状态和 PRD 待同步内容，不自动回滚源需求。

## 读取历史与恢复

- `history_sha256` 读取 `docs/requirements-history/` 中的需求历史，`prd_history_sha256` 读取 `docs/prd-history/` 中的 PRD 历史；可同时传入，分别返回 `history` 与 `prd_history`，不能混用。摘要使用工具此前返回的版本。
- 历史不存在时返回 `sha256: missing`；PRD 历史内容与摘要不符、不可读或不是普通文件时报错，不当作缺失。
- 读取历史不改变当前文件，也不作为保存基线，读取引用仍对应当前文件。恢复旧版须由用户明确请求：去掉历史中的工具元数据，以正文作为新候选按保存流程写入。冲突、结果未知或写后核对失败时先读取核实，不盲目重试；不能核实时报告限制。

## 连续保存验证（仅用户明确要求验证时）

用户可以直接说“按工具约定验证连续保存与历史”。Agent 执行以下流程，用户无需逐步发送指令：

1. 检查项目并读取当前需求。已有需求以原文为基线；没有文件时使用本对话完整候选，若缺失则请用户提供。
2. 保存基线；若内容相同，接受工具返回的未变化结果。
3. 重新读取，在正文末尾增加独立段落“保存工具验证备注：本段仅用于验证版本保存，不属于业务需求，下一次保存时删除。”，然后保存。
4. 重新读取，删除刚增加的完整段落，然后保存，恢复基线正文。
5. 用工具返回的历史摘要调用 `requirements_read_context(history_sha256=...)`，核对增加备注前和带备注的历史正文，以及当前正文与基线一致、仍为 Draft。
6. 报告实际调用结果、保存与历史核对证据、失败和未验证项。中途失败先核对现状；可能残留验证备注时明确报告，不声称已恢复，也不绕过工具清理。

重复正文可复用相同摘要的历史文件，不按“新增三个历史文件”验收。不把代码自测或终端调用算作真实 Agent 调用验证。
