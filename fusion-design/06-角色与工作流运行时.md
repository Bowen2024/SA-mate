# 单元 06：角色与工作流运行时

> 发布副本：来源为本地设计文档。状态、验收和授权按各段原日期与任务范围理解；本机路径已用占位符表示。[本批发布边界](../docs/fusion-design-publication.md)。

## 1. 职责、适用范围与单元关系

本单元说明角色如何取得准确任务和最小权限，工作流如何持久执行、等待确认、恢复并回收结果，以及 Buzz、Workflow Runtime、Runner 与领域工具各自承担什么。

日期：2026-10-15。当前状态见 总索引 §1 当前状态（建设管理材料，本批不收录），恢复按 总索引 §4 固定恢复顺序（建设管理材料，本批不收录）。三道门、具名金丝雀 P01–P05 与限定业务工具链在各自记录的范围内已独立验收通过。来源与计数见 P01–P05 验收索引（`fusion-runtime-lab/tests/reviews/2026-10-14/README.md`，未随本批发布） 和 业务工具链计划第 12 节（`fusion-runtime-lab/BUSINESS_TOOLCHAIN_PLAN.md`，未随本批发布）。历史“未授权/尚未通过”限定当时范围。新任务按 PROJECT_STATE.md（`PROJECT_STATE.md`，未随本批发布） 及总索引完整冷启动，不能沿用旧文档摘要全 match 的声明。生产入口的现状以总索引 §1 为准。第 8.4 节是未确认、未实施的 Runner 待决入口，正文在[设计门禁与历史依据](06-设计门禁与历史依据.md)的 C 部分。

本单元解决 Buzz × Develop Helper 融合中缺失的“工作流运行时”责任：把长期执行、暂停恢复、人工确认、角色调度、幂等与结果回收从 Buzz 宿主中分离，使 Buzz 回到消息、身份、线程和可见协作界面的位置。

已有结果分成两类。前两项是建设试验的角色分工，操作边界见 Fizz 手册 §1 与 §12（建设管理材料，本批不收录） 和 Honey 手册 §1 与 §11（建设管理材料，本批不收录）。后四项是本单元的运行时目标。各轮实施计数留在开头所列验收索引与业务工具链计划第 12 节。

1. Cursor 可以按明确任务和写入范围实施代码；
2. Codex 可以依据同一设计与验收契约独立审查；
3. 两个 Agent 的进度可以投影到 Buzz Channel，但普通对话不能直接改变权威状态；
4. 一个持续十分钟甚至跨进程重启的工作流，不依赖某条入站消息的短期凭证继续有效；
5. 先让 LangGraph 原样通过共同考卷和三道门；MAF 保留为由明确硬条件触发的后备原型，而不是默认必做对照；
6. 现有 Buzz 融合提交在替代路径通过之前保持冻结，可作为行为对照和回退依据。

第 5 项保持 2026-10-05 已确认的选型策略。三道门的通过记录和生产入口现状都以总索引 §1 为准。

本单元只建设平台中立契约、运行时原型、Buzz 薄接入和相应验收。需求、方案、UI、Feature、Task、Developer、Tester 的业务规则仍由各自单元负责；本单元不改写它们的产物语义。

本次完成标准分三道门：

- 第一门：工作流运行时在 Buzz 外完成持久化、暂停、重启、恢复、错误拒绝和幂等测试；
- 第二门：Buzz 入站事件可安全创建或恢复工作流，运行结果可准确回到原线程；
- 第三门：现有项目/线程/角色/工具边界获得等价或更强的运行证据。

三道门全部通过前，不宣称 Buzz 已经可以退成纯界面，不删除或回滚现有对照实现。

## 2. 角色、执行环境、身份与责任链

2026-09-26 记录的故障背景，范围是完整 PRD 生成超过宿主事件信封的短有效期：写入工具会拒绝调用。这不是需求能力本身的问题，而是当时把“入站消息认证凭证”同时当作“长时间工作流授权”。当时已经证明 Buzz 能承载逐事件项目绑定、角色工具裁剪、线程重启恢复和宿主回复发布。其后的运行时记录见 总索引 §1.1 历史建设记录（建设管理材料，本批不收录）。

当时叠进 Buzz ACP 的责任是：

- 认证入站作者、频道、线程和事件；
- 选择并持久化项目；
- 决定角色和工具面；
- 保存工作流上下文；
- 维持人工确认等待；
- 在模型完成后发布结果；
- 处理重启、重放、重复调用与迟到结果。

其中第一项和最后的 Channel 发布天然属于 Buzz；中间的工作流状态、授权快照、暂停恢复和角色路由应由独立运行时负责。领域成果、SHA、确认和写入冲突继续由 `buzz-develop-helper` 的确定性工具负责。

目标责任链为：

```text
Buzz Channel
    ↓ 已认证入站事件
Buzz Adapter
    ↓ IngressEvent
Workflow Runtime
    ↓ ExecutionContext + 节点任务
Agent Runner / Domain Tools
    ↓ 结果、证据、待确认请求
Workflow Runtime
    ↓ WorkflowProjection
Buzz Adapter
    ↓ 原频道、原线程中的可见消息
Buzz Channel
```

Buzz 消息是交互和审计载体，不是工作流状态库；Agent 文本是候选输出，不是权限、项目绑定或正式确认。

四种身份不要并成同一种权限。[设计门禁与历史依据](06-设计门禁与历史依据.md) C 部分「16.3 Runner Buzz 必要适配」已写明：业务角色 requirements／solution、提供执行能力的 Codex／Cursor、Buzz Agent 身份是三种不同维度，不直接画等号；Fizz／Honey 是融合建设分工，不是业务需求／方案角色的默认映射。Buzz 继续负责可信入站与展示，角色运行环境不接管频道路由、发布身份或用户确认。该部分「16.8 Runner 来源追踪表」将“Buzz 身份与 Runner 角色／运行环境分离”记为已确认原则，具体映射仍待确认。这里只复述这些原则，不新增角色，也不改第 5 节的授权项和工具表。

宿主接入和身份事实要同时看两处：[05 §9 验收框架与建设顺序](05-项目成果索引与确认交接.md) 的建设顺序第 8、9 条和该节停点，以及 [05 §2 恢复事实与设计起点](05-项目成果索引与确认交接.md) 里对 Buzz 宿主接入点的只读核对和 `just-start` 绑定事实。05 第 9 节单独读完仍只是部分事实。

### 2.1 建设试验中的两个身份

下表是当前建设试验使用的两个 Buzz 身份。业务 Developer、Tester 的职责方向仍在总框架第 5 节；Fizz、Honey 的操作边界在各自手册，不在这里改写成未来业务角色。

| Buzz Agent | 运行时 | 首版职责 | 写权限 |
| --- | --- | --- | --- |
| fusion-developer | Cursor `cursor-agent acp` | 按已授权 task 和 write_scope 实现、运行自验、回报证据 | 仅实验目录当前任务范围 |
| fusion-verifier | Codex ACP | 核对设计契约、diff、测试和拒绝边界，返回判定 | 默认只读；不得修业务代码取得通过 |

两者使用不同 Buzz 身份、不同运行记录和受限 author allowlist。当前 Codex Desktop 主会话仍负责设计拍板前的核对；Buzz 中的 `fusion-verifier` 从文件恢复，不冒充本会话的连续记忆。

## 3. 领域模型与状态归属

领域对象彼此独立，不把所有状态塞进一个不断变化的 `ExecutionContext`。

首版持久对象只有下面七个。操作 Command、pending approval 只读视图和“已验证确认恢复”是端口值，不列入领域对象，也不增加字段。

### 3.1 IngressEvent

Buzz Adapter 认证后形成的一次外部输入：

```text
provider
authority
principal_id
channel_id
root_event_id
event_id
content
received_at
```

`content` 仍是不可信业务输入；身份和路由来自验签事件，不从内容解析。一个 `IngressEvent` 最多触发一次工作流推进，重复事件由稳定 `event_id` 去重。

### 3.2 WorkflowRun

一条可持久恢复的工作流实例：

```text
workflow_id
workflow_type
project_id
state
current_node
created_from_ingress
created_at
updated_at
revision
```

`project_id` 创建后不可变。切换项目必须新建工作流，不复用旧线程或旧授权。

### 3.3 AgentRun

某个角色执行某一步的一次尝试：

```text
run_id
workflow_id
step_id
attempt
assigned_role
runner_kind
status
input_digest
output_digest
started_at
finished_at
termination_reason
```

同一个任务可以有多次 `AgentRun`，但同一 attempt 的幂等键保持稳定。Agent 停止不等于任务完成，必须核对输出和证据。

### 3.4 ExecutionContext

不可由 Agent 修改的单次调用边界：

```text
schema_version
workflow_id
run_id
step_id
attempt
project_id
principal
ingress_ref
capability_grant
idempotency_key
```

它不保存 PRD 正文、artifact 当前版本、审批状态或可变工作流状态。调用时由运行时根据持久状态重建，提交副作用前再次校验。

### 3.5 ArtifactVersion

领域工具实际核对的成果版本：

```text
project_id
artifact_id
artifact_type
version_label
relative_path
content_sha256
status
created_by_role
```

路径和 SHA 必须来自真实文件读取。Agent 回复中声称的路径、版本或 SHA 只能作为候选，不直接进入权威记录。

### 3.6 ApprovalDecision

用户对明确成果和用途作出的决定：

```text
decision_id
project_id
artifact_id
content_sha256
purpose
decision
principal
evidence_ref
created_at
```

只有明确对象、SHA、用途和受信依据齐备才可记录。普通 Agent 认可、模糊同意或 Channel 中的自由文字不能直接构成决定。

### 3.7 WorkflowProjection

面向 Buzz 的可见投影：

```text
projection_id
workflow_id
source_revision
channel_id
root_event_id
message_kind
body
dedupe_key
```

投影不是权威状态。发布失败或结果未知时，可根据 `dedupe_key` 和签名事件 ID 查询、重试或确认，不能重跑领域副作用。

## 4. 运行时端口、操作命令与领域适配

### 4.1 端口签名

领域层和端口不能导入 LangGraph、MAF、Buzz 或具体模型 SDK 类型。

```text
RuntimeDriver
  start(request) -> workflow_id
  resume(workflow_id, input) -> status
  status(workflow_id) -> WorkflowRun
  cancel(workflow_id, reason) -> status

AgentRunner
  run(agent_request, execution_context) -> AgentResult

DomainTools
  inspect_project(...)
  inspect_artifact(...)
  save_draft(...)
  register_artifact(...)
  record_approval(...)

MessageTransport
  receive(...) -> IngressEvent
  publish(WorkflowProjection) -> PublishResult
  lookup(dedupe_key) -> PublishResult | missing
```

两个框架适配器只实现 `RuntimeDriver`，不能让框架 checkpoint、interrupt 或 request 类型穿透到领域层。

### 4.2 操作 Command

以下四类名称和字段均为**已确认新增建议**。Command 是一次确定性操作的不可变输入值，不是新的持久状态库，也不加入七个核心领域对象：

| Command | 绑定节点 | 必须冻结的字段 |
| --- | --- | --- |
| `SavePrdDraftCommand` | N04 | `body`、`expected_prd_sha256`、`expected_requirements_sha256` |
| `RegisterArtifactCommand` | N06 | `artifact_id`、`kind`、`version`、`producer_role`、`purpose`、`summary`、准确内容引用、`set_current`、`expected_project_sha256`、`expected_readme_sha256` |
| `RecordApprovalCommand` | N08 | 准确成果 ID、版本、内容 SHA、permitted use、confirmed scope、non-authorizations、blocking open items、已验证证据引用、`expected_project_sha256`、`expected_readme_sha256`、`expected_decisions_sha256` |
| `SaveTechSpecDraftCommand` | N10 | `body`、`expected_tech_sha256`、`expected_prd_sha256`、`profile` |

共同约束：

1. `project_id`、角色、节点、attempt、principal、grant 和幂等键只来自 `ExecutionContext`；Command 不得覆盖它们。若为序列化审计重复携带项目或节点，必须与 context 精确相等。
2. 首次不存在的目标基线使用显式 `missing`，不能使用 `None`、空串或“读取最新值”。
3. 所有 SHA、用途、profile、版本和路径在进入适配器前完成类型与格式校验；字段缺失直接拒绝。
4. Command 不包含 Buzz event、host context、MAF/LangGraph checkpoint 或具体模型 SDK 类型。
5. Agent 只能产生候选正文和证据；运行时根据已冻结基线组装 Command，确定性节点复核后调用领域内核。

调用链如下。

```text
ExecutionContext + CapabilityGrant + Operation Command
    ↓ 节点、项目、工具、路径、成果类型、attempt 与幂等复核
DevelopHelperDomainTools
    ↓ 平台中立确定性入口
既有 requirements / solution / main_artifacts / main_collaboration 内核
    ↓ 锁、journal、前置 SHA、原子替换、历史与恢复
临时项目成果
```

- `DevelopHelperDomainTools` 拟位于 `fusion-runtime-lab/src/fusion_runtime/adapters/develop_helper.py`；它只能从受信配置解析 foundation 和项目路径，不能接受 Agent 提供的绝对路径。
- `requirements.py` 与 `solution.py` 已有平台无关函数入口，优先直接复用，不为适配器复制保存实现。
- `main_artifacts.py` 与 `main_collaboration.py` 保留现有 `authorization_from_host_context`、`*_from_host_context` 和 `HostToolSurface` 行为；新增运行时入口只能把已验证 `ExecutionContext + CapabilityGrant` 转换为确定性内核所需授权，不得调用测试私有签发钩子，也不得放宽生产宿主校验。
- `project_state.py` 的项目锁、journal 与恢复逻辑继续是单一实现；适配层不自建第二种事务格式。
- Phase 1 不创建 handoff、不发送消息、不启动下游，也不接入真实 Buzz Agent。

方案里的“单一事务内核”只是简称，指上面调用链中 `project_state.py` 的项目锁、journal 与恢复继续作为单一实现、适配层不自建第二种事务格式，以及 Phase 1 验收第 6 项：journal 中断后的既有恢复逻辑仍有效，不产生第二种事务格式。它不是新的命名组件。

### 4.3 已确认的端口补充与确认恢复

原七项已确认建议的原文在[设计门禁与历史依据](06-设计门禁与历史依据.md)的 A 部分，用词和顺序保持迁出时的样子。已确认的端口补充是下面这一句：

精确写入范围仍见 业务工具链计划第 4 节（`fusion-runtime-lab/BUSINESS_TOOLCHAIN_PLAN.md`，未随本批发布）。

主文继续保留这些边界：

- 确认信任策略为请求级且受 Runtime 排他边界保护，不在并发调用之间共享可覆盖的可变信任状态。
- N08 成功后停止，N09/N10 需要显式续行。第 8.1 节已指向计划第 3.3 节第 5 项和第 5 节第 5 项。

## 5. 权限、信任与副作用检查

### 5.1 CapabilityGrant

`CapabilityGrant` 由运行时服务端策略生成，至少约束：

- 项目；
- 角色；
- 允许工具；
- 允许读写路径；
- 允许的成果类型；
- 当前节点和 attempt；
- 可执行副作用；
- 生效状态和撤销状态。

模型看见 grant 的说明不等于模型持有授权。真正的工具入口必须使用运行时注入、模型不可覆盖的上下文。

### 5.2 写入前六项检查

每次写入前检查：

1. 工作流仍处于允许该动作的节点；
2. 项目与创建时一致；
3. 角色和工具在 grant 内；
4. 输入 artifact SHA 与当前期望一致；
5. 幂等键未完成过等价副作用；
6. 用户决定仍有效且用途匹配。

### 5.3 工具分配

| 角色/节点 | 允许能力 | 禁止能力 |
| --- | --- | --- |
| 需求 Agent | 读取项目背景、生成 PRD 候选 | 登记、确认、交接、方案保存、Git |
| Main/确定性节点 | 读取真实成果、登记、记录确认 | 生成业务正文、替用户确认 |
| 方案 Agent | 读取已确认 PRD、生成 tech-spec 候选 | 登记、确认、交接、需求保存、Git |
| Cursor Developer | 当前任务 write_scope、测试命令 | 改工作流状态、批准自己结果、跨范围写入 |
| Codex Verifier | 读取指定基线、运行验收、返回判定；在已确认 standing authorization 与运行手册围栏内发布同任务有限返工请求 | 修改业务实现以取得 PASS、写权威任务状态、启动新任务/下一 Phase、越界或超额返工 |
| Buzz Adapter | 收取/发布消息和解析线程 | 写业务成果、决定角色、改变审批 |

### 5.4 权限类停止条件

出现以下情况立即停止当前阶段。这些是原 14 条停止条件中的权限类，条目号保持原编号。

- （原第 2 条）需要在 checkpoint 中保存密钥或完整认证凭证；
- （原第 3 条）模型可以改变项目、角色、allowlist 或工具授权；
- （原第 7 条）无法指出安全边界由哪段自有代码强制；

## 6. 执行生命周期、暂停恢复与协作闭环

### 6.1 暂停、恢复与异常边界

入站认证只发生在 Buzz 边界；工作流创建后持久保存来源引用和授权事实。运行时间不由入站信封的短 TTL 限制。每次写入前执行第 5.2 节的六项检查。

已确认的受信恢复见第 4.3 节：确认信任保持请求级，并受 Runtime 排他边界保护，不在并发调用之间共享可覆盖的可变信任状态。这不增加第 5.2 节的六项写前检查。

出现以下情况立即停止当前阶段。这些是原 14 条停止条件中的恢复、去重与异常边界，条目号保持原编号。

- （原第 4 条）短期事件凭证再次覆盖长时模型运行；
- （原第 5 条）重放能产生重复写入、重复确认或重复消息；
- （原第 11 条）第一门关键失败已命中 Phase 3B 硬条件，却通过降低 journal 绑定、持久化、重放或跨进程恢复标准继续推进 Phase 4—7；

### 6.2 五类事件与载荷

已确认的五类语义事件为 `DEV_STARTED`、`DEV_BLOCKED`、`DEV_READY_FOR_REVIEW`、`REVIEW_CHANGES_REQUIRED`、`REVIEW_ACCEPTED`，与[设计门禁与历史依据](06-设计门禁与历史依据.md) A 部分已确认清单相同。它们统一包含：

```text
workflow_id
task_id
attempt
project_id
base_revision
changed_files
test_commands
test_results
artifact_or_diff_digest
summary
```

自由文字放在 `summary`，不能覆盖结构化字段。`REVIEW_ACCEPTED` 只是独立验收结果；是否推进下一任务仍由运行时和用户授权决定。

`REVIEW_CHANGES_REQUIRED` 要求自动返工时，还必须携带：

```text
review_event_id
source_attempt
next_attempt
finding_ids
violated_conditions
minimum_fix
required_tests
write_scope
prohibited_scope
rework_index
max_retries
disclosure_scope
dedupe_key
```

`next_attempt` 在过渡协议中是受 standing authorization 约束的协作指令；它不是 Honey 写入的权威工作流状态。Runtime 接管后，必须核对当前 revision、attempt、返工额度与去重坐标后才能创建新 `AgentRun`。创建 `AgentRun` 的责任仍在 Runtime。

### 6.3 关联、去重与结果回收

- 每个事件具有稳定去重键；
- 同一 Agent 不处理自己发布的投影；
- 最终架构中只有 Runtime 可以把 review 结果转成新 `AgentRun`；过渡期 Honey 只能按第 6.4 节发布同任务有限返工指令；
- 达到返工上限或缺少必要输入时进入 blocked；
- Honey 的结果接收者只能是 standing authorization 已固定的 Bowen 和 Fizz；Agent 不能通过正文 `@mention` 增加其他接收者；
- 重放旧事件只返回既有结果，不创建新 attempt。

### 6.4 同任务两轮返工

Honey 只有在下列条件全部成立时，才可向 Fizz 派发下一修复 attempt：

1. 用户已授权准确 `task_id` 及其独立验收/有限返工闭环；
2. 当前判定为 `REVIEW_CHANGES_REQUIRED` 且 finding 有独立证据；
3. `task_id`、Phase、目标、完成条件和原 `write_scope` 不变；
4. 修复是唯一明确的最小路径，不需要新设计决策；
5. 不需要安装依赖、修改外部项目、重启服务、Git 操作或真实业务写入；
6. 向 Fizz 发送的信息已脱敏且在当前披露授权内；
7. `rework_index < max_retries`，且没有重放过同一去重键。

初始实施不计入返工轮数。Honey 每次自动派发只能将 `rework_index` 增加一，并使用 `task_id + source_attempt + finding_ids` 的稳定去重坐标。发布结果未知时先核对实际消息，不直接重发。

以下任一情况必须停止并交回 Bowen：

- 需要扩大 `write_scope`、修改设计/验收标准或新增生产端口/领域字段；
- 存在两个以上会显著改变实现方向的修复方案；
- 需要启动下一段、下一 Phase、Git、重启、依赖安装或真实业务写入；
- Guardian 或发布工具阻止 Fizz 修复所必需的最小证据；
- 无法确认下一 attempt 或消息是否已发布；
- 已达当前任务的返工上限。

达到上限时，Honey 仍判定当前实现“失败”，将自动化状态报告为 `blocked_by_rework_limit`，不创建第五种验收判定，不重置计数，不自动进入 B/C 或下一 Phase。详细执行和报告格式见 Honey 手册第 8 节与第 9 节（建设管理材料，本批不收录） 和 Fizz 手册第 8 节（建设管理材料，本批不收录）。第 6.2—6.4 节的五类事件、两组载荷、关联、去重、结果回收、两轮返工和停止边界仍留在主文。

### Phase 0：平台中立契约

Cursor 只在 `fusion-runtime-lab/` 建立领域对象、端口、策略、状态转换验证和纯内存测试。禁止安装或导入 MAF、LangGraph、Buzz SDK；禁止修改现有融合实现。

通过条件：项目不可变、角色不能自报、工具由策略分配、消息不能直接成为确认、Artifact/Approval/Workflow 分离、幂等键稳定、领域层无平台依赖。

Phase 0 的通过不包含持久 checkpoint、进程重启、长于 100 秒执行、真实 Agent、真实领域工具或 Buzz 双向适配，因此不等于第一道门或三道门通过。`FRL-P0-01-R2` 的测试计数没有独立 Phase 计划，保存在伴随资料 B。

### Phase 1：Develop Helper 领域适配

把 `requirements.py`、`solution.py`、`project_state.py`、`project_init.py` 作为领域能力适配；把 `main_artifacts.py`、`main_collaboration.py` 的核心事务与 `*_from_host_context` 分离。当前 Buzz 适配保持可用。

通过条件：既有融合层全量测试保持通过，新适配只通过平台中立 context 调用；不修改 Develop Helper 上游或真实业务项目。

#### Phase 1 设计事实

当前 `DomainTools` 只接收 `ArtifactVersion`、正文、`ApprovalDecision` 和 `ApprovalEvidence`，不足以表达现有确定性工具已经强制的全部前置条件：

- `requirements.save_prd_draft` 需要当前 PRD SHA 与输入 requirements SHA；
- `solution.save_tech_spec_draft` 需要当前 tech-spec SHA、输入 PRD SHA 与 `Lite / Standard / AI` profile，并在保存时复核准确确认；
- `main_artifacts.apply_registration` 需要成果元数据、内容定位、用途、摘要以及 `project.json / README.md` 前置 SHA；
- `main_collaboration.confirm_current_session` 需要已验签会话证据、准确成果版本和用途，以及 `project.json / README.md / decisions` 前置 SHA。

如果适配器在执行时自行读取“当前最新值”补齐这些参数，旧 Agent 结果或迟到结果就可能在新基线之上被错误提交。因此 Phase 1 必须先冻结端口命令，再实现适配器。

#### Phase 1 操作 Command

四类 Command 的名称、冻结字段、五条共同约束和调用链已与第 4.2 节逐字段核对，正文相同。原小标题「Phase 1 调用链」对应第 4.2 节的「调用链如下」。旧重复不再留在本节。第 4.2 节同时说明「单一事务内核」只是简称，并指向原验收第 6 项：journal 中断后的既有恢复逻辑仍有效，不产生第二种事务格式。

原 write scope、验收十条和 `FRL-P1-01-R3X`／`FRL-P1-01-H4` 计数没有独立 Phase 计划，完整保存在伴随资料 B。那些范围是当时的实施授权，不是当前写入许可。

Phase 1 通过只证明领域适配成立，不证明持久运行时、Buzz 双向适配或第一道门通过；完成后停止，Phase 2 需另行授权。

### Phase 2：共用一致性测试

先用 Fake AgentRunner 构建全部正常、错误、重启、重复和迟到场景。该套测试是两个运行时原型的共同契约，不能为某框架单独降低条件。

Phase 2 的实施顺序已确认为三次独立授权：`FRL-P2-01A` 先建立共用 factory、test-only checkpoint 与第 1/3/4 项跨实例恢复探针；A 独立验收后，`FRL-P2-01B` 才补齐剩余 9 项及进度/返工边界；B 独立验收后，`FRL-P2-01C` 才执行 mutation 与最终加固。完整范围、停点和命令以 `../fusion-runtime-lab/PHASE2_CONFORMANCE_PLAN.md` 为唯一实施计划。A/B/C 不是新阶段，任一段完成均不自动授权下一段，也不等于第一道门通过。

当时的 A／B／C 通过计数，以及该结论不等于第一道运行时一致性门，见伴随资料 B。

本单元的有限自动返工只能在已授权的 A、B 或 C 单段内创建后续修复 attempt。A 验收通过不自动授权 B，B 通过不自动授权 C；验收失败也不得通过扩大修复范围偷偷实施下一段。

### Phase 3A：LangGraph 原型

使用真本地持久 checkpointer、稳定 `workflow_id/thread_id` 映射、`interrupt` 与显式恢复命令实现相同节点。进程退出后必须能只凭持久状态恢复；任何会在恢复时重跑的节点，在 `interrupt` 之前不得执行不可安全重放的副作用。Phase 3A 只能为现有 factory/fixture 提供 LangGraph 实现，不得修改、复制、删减或放宽 `tests/conformance/`。

Phase 3A 的权威实施计划是 `../fusion-runtime-lab/PHASE3A_LANGGRAPH_PLAN.md`。计划落盘不等于实施授权；安装依赖和编码仍须用户针对准确任务另行派发。

分段、授权门和第一门完成标准见 Phase 3A 计划（`fusion-runtime-lab/PHASE3A_LANGGRAPH_PLAN.md`，未随本批发布） 第 6 节和第 8 节。

### Phase 3B：Microsoft Agent Framework 原型

MAF 是条件触发的后备原型，不默认建设。只有以下任一硬条件有独立证据成立，且不能在不破坏平台中立契约的前提下合理修复 LangGraph 路径时，才交回用户决定是否启动 Phase 3B：

1. LangGraph 无法原样通过 Phase 2 共用考卷；
2. 跨进程 checkpoint 或稳定 `workflow_id/thread_id` 恢复不可靠；
3. crash-after-effect 无法绑定既有 journal 或权威领域结果；
4. LangGraph 类型必须泄漏进 domain/ports 才能实现；
5. 重放会产生重复领域写入、重复确认或重复消息；
6. 真实 AgentRunner、取消、并发或 checkpoint 清理无法达到确定性边界；
7. Buzz Adapter 必须修改 Buzz 核心才能继续；
8. Phase 6/7 暴露无法合理修复的 LangGraph 特有边界；
9. 依赖成熟度、升级风险、本地调试或运维成本达到不可接受的明确证据门槛。

若触发并获授权，MAF 使用持久 checkpoint storage、人工 request/response 和与 LangGraph 完全相同的考卷、端口及幂等边界实现，不得以另一套验收口径补救。

任何后备原型不得与 LangGraph 路径并行修改共享领域文件；共用契约与考卷始终先冻结，再由框架适配层实现。

这九项留在本节。对应表述同时见 Phase 3A 计划第 9 节（`fusion-runtime-lab/PHASE3A_LANGGRAPH_PLAN.md`，未随本批发布） 与 Phase 4 ADR 第 5 节（`fusion-runtime-lab/PHASE4_LANGGRAPH_ADOPTION_ADR.md`，未随本批发布）。

### Phase 4：LangGraph 暂定采用与 MAF 条件触发记录

只有 Phase 3A 完成且第一门通过后，才创建暂定采用 ADR。记录 LangGraph 的行为通过率、恢复语义、自定义代码责任、依赖成熟度、本地可调试性、模型适配、升级风险、预计 Buzz 接入厚度和失败可解释性；同时明确 MAF 尚未评估、暂缓及上述触发条件。该 ADR 只授权继续 Phase 5—7 的 LangGraph 集成验证，不声称完成双框架比较，也不永久取消 Phase 3B。

已落盘文本是 Phase 4 ADR（`fusion-runtime-lab/PHASE4_LANGGRAPH_ADOPTION_ADR.md`，未随本批发布）。第 1 节写暂定采用边界，第 4 节写当时的维度证据，第 5 节写 MAF 状态。证据记录不代替本节评估表必须回答的问题。

### Phase 5：Buzz 公共接口勘察

只读核对事件订阅、签名读取、线程标签、发布、精确事件回读、身份/密钥所有权和去重能力。优先使用公开协议/CLI/SDK；若原型必须继续修改 `buzz-acp` 核心，先停止并重新评估“Buzz 薄界面”的成立程度。

Phase 5 勘察计划（`fusion-runtime-lab/PHASE5_BUZZ_SURVEY_PLAN.md`，未随本批发布） 是实施计划。Phase 5 接口清单（`fusion-runtime-lab/PHASE5_BUZZ_INTERFACE_INVENTORY.md`，未随本批发布） 是清单和结果。两份文件分别引用。

实施分段与第二门标准见 Phase 6 计划（`fusion-runtime-lab/PHASE6_BUZZ_ADAPTER_PLAN.md`，未随本批发布）。

### 十项框架维度

Phase 3A 与后续三道门按同一组维度记录 LangGraph 证据；如果硬条件触发 MAF，后备原型必须按相同维度补齐证据。下表是稳定架构约束。LangGraph 当时对这些问题的记录见 Phase 4 ADR 第 4 节（`fusion-runtime-lab/PHASE4_LANGGRAPH_ADOPTION_ADR.md`，未随本批发布）。LangGraph 为暂定采用。MAF 未评估，只在本节 Phase 3B 的九项硬条件成立并另行获授权后才建设。暂定采用不完成双框架比较，也不永久取消 Phase 3B。

| 维度 | 必须回答的问题 |
| --- | --- |
| 持久化 | 本地进程退出后能否从明确 checkpoint 恢复？ |
| HITL | 是否能固定请求对象、SHA、用途并拒绝错误 resume？ |
| 重放语义 | 节点重执行时怎样防止重复写入？ |
| 模型接入 | 是否可以复用现有 Codex/Cursor AgentRunner，而不是强迫改用框架聊天客户端？ |
| 调试 | 能否从一个 workflow_id 还原节点、attempt、输入和副作用？ |
| 依赖与升级 | 当前版本成熟度、破坏性升级和本地安装成本如何？ |
| Buzz 适配 | 入站/出站是否只需 MessageTransport，而不侵入领域层？ |
| 权限 | 项目、角色和工具由哪段自有代码强制？ |
| 测试 | 删除关键 guard 后，共用测试是否会失败？ |
| 运维 | checkpoint 清理、失败恢复、取消和资源上限怎样实现？ |

任何框架如果不能在不泄漏框架类型的前提下通过共用端口与测试，直接淘汰，不通过添加 Buzz 专属旁路补救。

出现以下情况立即停止当前阶段。这些是原 14 条停止条件中的框架与端口约束，条目号保持原编号。
