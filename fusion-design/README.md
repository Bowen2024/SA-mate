# SA-mate 融合设计

这里说明怎样把 Develop Helper 的 SDD 方法组织为可独立调用的能力，以及角色、成果、确认交接与运行时的责任边界。

本目录是面向项目读者的设计发布版。当前收录总体设计、项目与能力设计、Main 角色、必要的设计依据及单元设计模板。建设期文档整理计划、Agent 操作手册和本地任务恢复索引不在本批范围内。

## 先理解两条路线

- **独立交付**：需求、客户方案或 UI 演示可以单独完成，已有材料足够时直接复用，没有继续指令即结束。
- **工程衔接**：需要实现时，再补齐相关 PRD/AC、技术契约、必要界面与确认，进入规划、开发和独立验收。

保存、登记、确认、交接、消息发送与下游启动分别判定；某一步成功不自动证明其余步骤已经发生。

## 角色与执行组件

| 角色或组件 | 职责 |
| --- | --- |
| Main | 理解意图、协调项目和角色、展示真实结果、收集明确决定 |
| 需求角色 | 澄清业务，形成轻量需求或工程 PRD 候选 |
| Solution Designer | 形成适用当前用途的方案和技术契约 |
| UI 角色 | 页面、原型、演示说明及实际交互验证 |
| Planner | 工程输入就绪后拆分 Feature、Task 与依赖 |
| Developer | 在授权范围内实现和自验 |
| Tester / Verifier | 对指定基线独立验证，返回判定与证据 |
| Workflow Runtime | 持久执行、授权分配、等待恢复、关联去重和结果回收 |
| Agent Runner | 把准确任务交给具体执行环境，返回候选与证据 |
| 确定性领域工具 | 校验项目、权限、版本及用途，执行获授权写入并恢复事务 |

角色、执行环境、模型分别配置。建设中使用的 Fizz、Honey 等名称是历史分工，不要求贡献者沿用，也不自动授予权限。

## 设计状态怎样阅读

原文保留“已确认”“待确认”“已否决”、历史日期与验收范围。它们的含义分开：设计决定说明准备怎样建设；源码与测试说明实现了什么；实例证据说明具体入口实际启用了什么。

本批只发布设计文档，不新增角色权限、业务阶段、默认流程或验收结论，也不将后续未发布的实现和证据视为已经交付。Main 主文包含角色设计和后续候选契约；各段的状态按其原文与范围理解，不能整篇作为可直接配置的提示词。
