# 开发推进模式

本协议管理开发循环的推进节奏。模式与当前门禁保存在项目 `.sdd/tasks.json`（路径：`<active_project_path>/.sdd/tasks.json`），只由编排器维护；Developer、Tester 不自行改模式、放行或续派。

## 字段与选择

```json
{
  "execution_mode": "step_by_step",
  "step_gate": {
    "kind": "task_review",
    "task_id": null,
    "status": "pending",
    "user_confirmation": null
  }
}
```

- `automatic`：在依赖、授权、资源及前端门禁允许时并行；不逐任务要求确认。
- `step_by_step`：一次只推进一个任务的 Developer → Tester → 有限返工闭环，Tester PASS 后等待用户确认，再推进下一任务。首次开始开发仍须有用户开发意图，不因字段存在就视为授权。
- 首次规划前沿用已有模式选择；未选择时，主智能体用一句话说明两种方式并询问，课堂建议逐步模式。向 Planner 传入用户选择；Planner 不从模板示例或沉默推定模式。
- 新计划显式记录模式及空的 `step_gate`。旧计划缺少 `execution_mode` 时兼容原有自动行为，不批量修改历史项目；字段存在但值非法时阻止派发。
- `task_id` 是当前任务 ID，`null` 表示尚未选定；`status` 为 `pending / awaiting_user / changes_requested / passed`。`passed` 需要任务已通过 Tester 且 `user_confirmation` 有真实用户确认摘要，其他状态该字段为 `null`。
- `step_gate` 是可复用的当前任务检查点，不替代任务状态，也不替代前端任务里的 `user_gate`。每次确认、拒绝、切换或重选任务先把依据写入相关任务 `notes`；无相关任务时写现有工作日志（路径：`<active_project_path>/.sdd/work-log.md`），不另建状态文件。

## 每次派发

1. 编排器串行维护状态并回收已返回成果，执行 `scripts/sdd_dispatch.py --tasks <active_project_path>/.sdd/tasks.json`（路径：`<harness_root>/scripts/sdd_dispatch.py`）。将真实运行中的 Developer/Tester 对应任务 ID 去重后，以重复的 `--running-task <task-id>` 参数传入；Tester 运行时任务仍为 testing，不能仅凭任务状态判断是否有空位。
2. 检查脚本输出的 `gate_phase`、`step_phase` 和角色候选；空候选不派发。脚本只计算资格，不启动智能体、不修改状态、不验证用户确认的真实性。实际放行由唯一编排器结合真实调用记录、用户消息、授权与资源冲突决定。
3. 逐步模式返回 `step_phase=ready` 时最多有一个候选。派发前先归档旧确认，将 `step_gate` 设为该任务、`pending`、确认 `null`，再检查并派发；取得实例 ID 后写任务状态。不能在记录当前任务前启动第二个任务，也不能由多个编排器并发分配。
4. 当前任务的开发、自验、Tester 验收及原返工额度内的修复可连续进行，不逐角色询问用户；其他任务不派发。已有 Developer 成果仅缺测试时优先交 Tester，不重写实现。BLOCKED、重试耗尽或缺必要授权时报告具体原因，不能偷偷改选下一个任务；用户可以明确指定另一个独立任务，记录决定后重设检查点。
5. Tester PASS 后将任务置 `passed`，门禁置 `awaiting_user`，立即展示成果访问方式、改动、已验/未验范围及下一任务；结束本轮自动推进。即使尚未写回 awaiting_user，脚本也根据当前任务 passed 拦截。最终交付任务同样需要用户确认，不能仅因没有下一任务省略。
6. 用户认可当前成果并要求继续后，记录确认并置门禁 `passed`；下次调度才选下一个任务。用户要求修改则清空旧确认，置 `changes_requested`，将任务重开为 `fixing` 或需要重新验收时置 `testing`；只修复/复验指定任务。重试计数不清零，范围变化仍需更新方案。修改后再次 PASS 仍等待用户，不把原确认用于新代码。

## 切换与前端门禁

- 用户可说“切到逐步模式”或“切到自动模式”，也可编辑 JSON；编排器在下一次派发前重新读取，不沿用过时模式。已有授权继续有效，切换不增加 Git 或付费调用权限。
- 自动 → 逐步：先回收调用状态，记录切换前已完成成果及在途任务 ID；已有要求修改的检查点必须保留，否则从在途任务中选一个作为 pending 检查点（没有在途任务才初始化为空）。停止新派发，让正在运行的任务收尾，不强杀、不重复派发。脚本在其他任务仍运行时输出 `draining`，当前任务也不会重复派发。当前任务通过后，连同本批已验收的在途成果一起交用户确认，notes 明确覆盖哪些成果；其余未验成果再逐个交 Tester、逐项确认。切换前已通过的历史任务不补造确认、不重跑。直接编辑模式字段时，编排器在派发前同样执行这一交接，不只改字段就续派。
- 逐步 → 自动：明确切换可解除普通逐步等待；先保存原门禁与用户决定，再更新模式，保留确认历史，不伪造 passed。若用户已要求返工，继续仅放行该任务修复和复验，直至明确认可或明确撤销该修改要求；切换本身不撤销已提出的修改。
- 前端 `user_gate` 在两种模式下均优先：等待 Mock 验收或必要配置时，整个项目停止新 Developer、Tester、修复派发；已运行者只收尾。切成 automatic 也不能绕过。
- 同一任务同时触发逐步和前端门禁时，合并交接与提问；用户认可页面可记录逐步确认，但前端门禁仍须配置等全部条件满足才放行。用户提出前端返工时，按前端 rework_task_ids 逐个选择当前任务；先记录旧检查点，再重设 step_gate，不让普通逐步等待阻止用户已明确指定的返工。

任务通过、用户确认与 Git 操作分别记录。只有用户授权提交时才由编排器按 Git Skill 精确存档；“继续”“自动模式”不自动授权提交、推送或合并。
