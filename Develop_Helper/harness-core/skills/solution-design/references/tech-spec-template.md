# 七层技术方案结构

生成 `docs/tech-spec.md`（路径：`<active_project_path>/docs/tech-spec.md`）时采用下面七个标题。每层写本项目实际需要的决定；不适用项说明原因。接口可复用的类型在第三层定义，其余通过类型名引用。

文档头部写项目名称、`status: Draft`、`specification: <实际名称或 null>`；项目元信息是规范选择的唯一依据。涉及改动时维持 REQ / AC / API 编号，旧项目沿用原 ID；不在此划分开发 Feature。

## 一、用户要完成什么

- 引用 PRD 的需求编号、验收编号和对应章节；概括用户输入 → 系统处理 → 用户结果。
- 标明涉及的页面或入口；有原型时链接实际页面锚点。业务规则以 PRD 为准，不在这里重写一份。

## 二、前后端怎么分工，接口怎么拆

确定前端、后端、外部服务分别承担什么，以及采用的语言、框架与必要依赖。后端基础 URL、前端请求顺序或事件交互方式都要明确。CLI 或纯后端项目说明实际模块边界，不强造前端。

先列接口索引，再为每个接口保留可独立读取的标题，例如 `### API-001 上传文件`：

| 项目 | 写明内容 |
| --- | --- |
| 关联需求 | REQ 编号与覆盖的 AC 编号 |
| Method / URL | 如 POST /files；路径参数、查询参数分别说明 |
| 请求 | Content-Type、headers 中的必要项、字段名、类型、必填/可空和含义；无请求体明确写无 |
| 成功响应 | HTTP 状态、完整负载的各字段及类型；文件/流响应说明内容类型与消费方式 |
| 失败响应 | 本接口可能返回的 HTTP 状态、错误代号与负载结构；处理规则引用第六层 |
| 请求响应示例 | 一组完整成功交互和关键失败交互，能直接用于联调，不只展示包装内的局部字段 |

统一响应结构根据本项目需要和已选规范确定；引用到的类型要可定位。鉴权、数据可见性和幂等仅在相关接口说明，不能漏掉 PRD 已有要求。外部服务接口与本地接口分别标识。

自有接口可设计字段；外部服务已有协议应核实后适配。字段最终须与处理方式一致，例如返回任务编号不代表已经执行成功；执行中、完成或失败怎样区分要在第五、六层说明。

## 三、接口请求数据的类型选型

- 选择 JSON、multipart、文件、流等格式，说明适用接口；按项目需要选择客户端，不统一强制某种语言库。
- 定义共享字段或结构的类型、单位、可空性和校验；文件上传说明大小、格式、时长等实际限制。
- 说明数据如何跨请求传递：直接传值、临时编号、会话还是持久记录；边界与释放时机要明确。
- 涉及数据库或其他存储时，写必要的实体字段、关系、约束、归属和生命周期；不需要持久化时写明临时存储方式。

## 四、模型选型与提示词设计

无模型调用时标明“不适用”。AI 项目按调用职责说明：

- 服务商、模型、地域或接入方式、所需能力和选型依据；可配置项引用第七层。
- 每次调用的系统提示词与动态输入结构，输出格式、限制、解析和校验方式。
- 提示词的独立维护位置；用户请求是运行时输入，不写成固定演示问题。
- Agent 使用的工具名称、参数结构、观察结果和权限边界；工具描述不增加用户未要求的能力。

## 五、接口逻辑算法设计

按第二层的 API 编号描述：读取与校验 → 调用服务或执行算法 → 更新数据/状态 → 返回结果。跨接口共用逻辑只定义一次，其余引用。

- 说明计算公式、排序/过滤规则或关键状态转换；算法使用的数据必须来自已定义字段。
- Agent 项目说明模型如何接收用户输入、发出工具调用、收到真实工具结果、再判断下一步，直到完成或达到明确的停止条件。单次计划后固定执行不算完成此循环。
- 需要并发、长任务或重复提交处理时说明相应机制；简短同步任务不自动增加队列、轮询或流式进度。

按 [接口体验分析](interface-experience-review.md) 对每个 API 做一次简短筛选；只展开与当前接口相关的影响项，按以下格式写在该 API 标题下：

| 技术选择与触发场景 | 用户可见结果或代价 | 当前处理与依据 | 验收或验证 |
| --- | --- | --- | --- |
| 填实际问题，如执行超时 | 用户看到什么、能否继续、结果是否保留 | 已确认选择及 D 编号；普通实现说明理由；未定项标明待确认 | 关联 AC，或具体输入/操作与预期结果 |

没有新增重要取舍时写一句说明即可。选项比较和确认历史按需存入 `docs/decisions.md`（路径：`<active_project_path>/docs/decisions.md`），本节保留当前处理与精确章节引用，不为每个接口另建报告。

## 六、接口失败异常设计

按 API 编号列出：触发条件 → HTTP 状态/错误代号 → 响应字段 → 用户提示 → 是否停止或恢复。共享错误结构集中定义，本节解释第二层失败示例的行为。

明确实际需要的校验失败、业务失败、外部异常、超时、重试次数、降级及资源清理；有副作用的请求说明重复提交的处理。不要无限重试付费调用。模型输出格式错误、工具失败等在 AI 项目中分别处理。

把关键失败行为与 PRD 的 AC 关联；前端保留什么信息、能否重新提交等要与界面约定一致。

客户端断开、请求超时、任务执行失败与结果获取失败要按实际链路区分；明确服务端是否仍在执行、重试是否重复产生副作用，以及已有结果是否保留。只对项目相关情况展开，不仅列错误码。

## 七、项目本地层级设计

- 用目录树标注各目录/关键文件职责，包括前后端、提示词、配置、测试和临时数据的实际位置。
- 列出运行环境、依赖版本约束、本地端口、必要启动/验证方式；服从已选技术栈，不固定要求 Python、Vue 或 PyCore。
- 配置表只写字段名、类型、默认值、用途和敏感性；密钥保存在项目配置机制中，仓库提供空值模板。注明临时数据和依赖目录的忽略及清理规则。
- 外部服务清单记录名称、用途、依赖的 API、配置状态、Mock/真实调用模式、真实验证所需账号/权限与付费调用授权状态。授权不足时标明受影响范围，不阻塞无关开发。

方案末尾仅列仍影响开发的待确认事项及相关决策记录引用。完成时检查每个 REQ / AC 都有实现或明确“无需接口”的对应关系，重要体验选择已确定并落实到相关字段、算法、异常、目录和验证方式；执行顺序和任务状态交给 Planner。
