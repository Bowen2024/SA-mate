# 06 从一句需求到最终交付：完整实例

[阅读目录](README.md) · [上一篇](05-existing-projects.md) · [下一篇：原文地图](07-source-map-and-notes.md)

以下“文件处理助手”为教学假设。本次没有创建该项目，示例中的确认、状态和证据均不是已发生事实。

## 1. 用户提出目标

> 我想新建网页工具，让同事上传文本型 PDF，转换成 Markdown 后下载。先不做账号、历史记录和 OCR。项目名“文件处理助手”，ID 用 file-helper，采用 default，暂不配置远程仓库。

AI 识别新建，确认类型和规范适用范围，检查 ID/目录，再创建登记。此时只有元信息、模板和选定底座，不能宣布功能做好。

## 2. 先把验收说清楚

AI 可能询问“扫描件明确拒绝，还是允许用户取得缺少正文的结果？”这会改变用户结果，需要在 A 确定。

假设双方确认仅支持可提取正文的 PDF：

| 需求 | 验收示例 |
| --- | --- |
| REQ-001 提交并下载转换结果 | AC-001：支持文件成功转换，可下载包含正文的 Markdown |
| 同一需求的失败边界 | AC-002：不支持格式有明确提示，不显示虚假成功 |
| 同一需求的失败边界 | AC-003：无可提取正文时说明原因，不交付伪造正文 |

真实 PRD 还需完整前置条件和验证方法。AI 补业务流程图与时序图，整体交用户确认，明确认可后记 Confirmed。

## 3. 方案阶段解释实现选择

Solution Designer 提出上传/转换和下载契约，确定格式、校验、提取、结果编码、失败清理与目录。无需模型时第四层写不适用，不为演示框架引入 LLM。

若“刷新后是否保留结果”有分歧，主智能体说明方案对操作、成本和恢复的影响。决定后写 D-001，并同步接口、数据与异常章节；用户结果改变则同步 PRD/AC。

技术方案和图文核对完成后整体确认。接口返回编号不等于转换已成功，成功、处理中和失败应按约定区分。

## 4. B 阶段检查页面状态

UI 设计明确文件选择、提交状态、结果、下载、错误、长文件名与窄屏表现。需要原型时，用户可实际操作主要流程。

原型确认回答“设计方向是否正确”；正式前端 Mock 验收回答“实际做出的页面是否符合设计且可用”。两者发生在不同阶段。

## 5. Planner 给出任务图

假设选择 automatic，形成下面的示意安排。真实计划仍需完整字段、章节和逐项检查，不能把此表直接当 tasks.json。

| 任务 | 类型 | 依赖 | 能证明什么 |
| --- | --- | --- | --- |
| T-001 上传和结果页 Mock、前端整体收口 | frontend | 无 | 页面、交互、错误和 Mock 契约；真实 AC 后交 T-003 |
| T-002 校验、转换和下载后端 | backend | 无 | 技术检查，完整承接 AC-002/003 相应失败行为 |
| T-003 真实用户链路验收 | integration | T-001、T-002 | AC-001～003 完整操作和真实结果 |
| T-004 功能与实现导航 | delivery | T-001、T-002、T-003 | DEL-001～005，来源、交互与刷新机制 |

T-001～003 属于 F-001 文件转换能力；T-004 属于 F-DELIVERY。共享文件明确唯一写入者，例如前端 API client 由前端/联调任务负责，后端不同时改。

本例无外部服务，external_services 为空；仍有前端门禁，配置确认记录“不适用”，不索取不存在的 Key。

## 6. 自动模式怎样运行

编排器可优先派 T-001，同时派不冲突的 T-002。每个 Developer 返回后，名额和门禁允许就安排对应 Tester。

- 后端先通过：保存 T-002 passed，但 T-003 仍等前端门禁。
- 前端先通过：立即交用户验收 Mock，停新派发。在途后端可收尾，成果保存；不能因此继续补派 Tester。

用户检查上传、错误、结果和下载展示并认可 Mock，无服务配置确认也已记录，user_gate 才 passed。随后复用已有后端成果，补齐剩余验收，再进入 T-003。

若选择 step_by_step，依赖表可以完全相同，只是每个任务 PASS 后等用户确认；无需新增虚假依赖来强制串行。

## 7. 测试失败怎样处理

假设不支持格式仍显示成功：Tester 记录 AC-002、动作、预期、实际与证据；编排器按原任务定点返工并增加 retry_count。修复后复验原问题及直接影响路径。

若只是浏览器不可用而无法实测，属于验证条件缺失，不应假称发现业务缺陷。记录未验项和恢复条件。

有效修复复验后再判断经验价值。例如“只通过按钮禁用做校验，真实提交没有再次校验”若被证实且可能重复，可记录原因、预防与证据。小拼写错误不一定值得新增经验。

## 8. 真实验收与交付

T-003 用真实文件完成上传、转换和下载，验证正文产物与关键失败路径；接口返回 200 本身不能证明全部 AC。

T-004 从实际页面事件追到请求、接口、服务、算法、参数和异常，生成 project-console.html。Tester 检查导航、展开、窄屏、来源及刷新时的变更提示。README 给运行和刷新方法。

最后你应能知道：怎样启动；哪些需求已验；哪些仍有限制；功能实现在哪；以后修改应回哪一层。

## 9. 下一轮怎么说

| 你的下一句 | 框架应做什么 |
| --- | --- |
| 下载按钮挪到结果标题旁，功能不变 | 调相关设计/页面，验证受影响视觉和交互 |
| 增加转换历史 | 补 PRD、方案、界面和相关任务 |
| 中文下载文件名乱码，与原要求不符 | Bugfix，不重开项目 |
| 先暂停 | 保存状态，停止新派发 |
| 继续 file-helper，上次代码已写完没测试 | 核对成果，优先 Tester，不重做编码 |
| 只告诉我进度 | 读状态和证据回答，不自动开发 |

这些是表达意图的例子，不是必须逐字输入的固定指令。
