# 技术解释与项目对照

按“技术是什么 → 用户项目怎么做 → 做与不做有什么区别”解释。沿用用户提供的材料和已有结论，不用路由过程播报代替回答。

涉及技术名词学习时，先按 [复述与学习记录](references/term-learning.md) 定向核对当前待复述名词，再执行下面的讲解；讲解后等待用户用自己的话解释，理解到位并记录后才进入下一个名词。普通报错排查或框架修改不套用术语复述门槛。

## 一、先解释技术本身

载入本 Skill 后，先向用户给出简短、客观的定义：它是什么、解决什么问题、基本如何工作；必要时说明不属于它的职责。先给出这段解释，再查项目，不让用户等待项目探索后才得到定义。若术语有会改变解释的歧义，只补问该歧义。

使用准确而易懂的语言，不先套生活比喻、不堆术语、不固定套输入/处理/输出模板。涉及会变化的模型、SDK 或接口限制时，用可用网页搜索/页面读取工具核对官方资料；不能确定的内容明确标注。

## 二、定向查找用户自己的项目实例

1. 优先使用用户明确提到的项目和对话中的相关项目；路径已知则直接使用，不重复定位或切换活动项目。
2. 没有合适实例时，直接 read 注册表（路径：`<harness_root>/project-registry.json`），根据项目名称和已有用途选择相关候选。可从活动项目开始，但不能认为它必然相关；不进入项目管理或开发流程。
3. 在候选项目中先定向读取相关 README、PRD 或技术方案章节，判断该技术涉及哪个功能。要说明“已经实现”，再沿该功能查到接口、代码或配置定义；有明确关键词时，仅在相关文件或子目录中检索。不要先于 Skill 阅读业务资料，不通读所有项目文档，不使用无目标的全仓 Search files。
4. 若当前候选不相关，再查有明确相关线索的其他项目；找到足够解释的实例就停止。区分“代码有实现”“设计中计划采用”“明确不采用”“本次查阅未找到”，不把 PRD 当成已实现证据，也不因没搜到关键词就断言整个项目没有该能力。
5. 没有项目或未找到真实采用实例时如实说明。优先选用户已有项目中的相关功能做假设对照，并标明“如果引入”；没有可用项目才使用明确的假设示例。不要为了举例创建项目，也不自行读取框架外备份或真实 .env、用户数据。

## 三、在同一项目里对比做与不做

先交代项目里哪个页面、功能或接口与该技术相关，以及查到的现状和依据。然后固定同一用户目标和场景，对照：

- **不采用时**：用户如何完成操作，系统用什么方式处理，会遇到什么限制。
- **采用时**：哪些操作、处理步骤或结果发生变化，又新增了什么依赖、成本或限制。
- **区别的原因**：将变化对应回技术机制，让用户知道这项技术具体改变了哪一步；它不负责的能力不要一并算进去。

可用简短并排表格或两条流程呈现，不要求每次画图。真实实现引用实际文件与函数/章节，未落地的一侧注明是假设；比较时保留其他条件不变，不把可选配套方案当成该技术必然带来的效果。例如解释统一登录时，不把角色授权、数据隔离或隐藏页面自动归为它本身的功能。

最后点明该概念在这个项目中的具体作用及适用条件，不把“有/没有”简化成“先进/落后”，不自动建议重做项目。围绕用户仍不理解的地方继续解释，不追加整套需求问卷。

讲解完成后按复述流程收尾，不把讲解结束当成学习完成。只维护约定的学习索引和名词文档，不额外创建过程文件、不执行待解释命令、不安装环境或修改业务项目。用户明确要求实施时，将已有结论和执行要求交给 [项目管理](../project-management/SKILL.md)，不重新询问已确认信息。
