总框架已获用户确认，按单元建设。本文件记录总体目标、能力划分、责任分层和跨单元原则；具体业务契约由对应单元展开，不在总纲重复维护实例配置、实施计划或逐轮验收记录。

恢复、当前进度、生产路径与下一步以 总索引（建设管理材料，本批不收录）及其指向的计划、交接与验收证据分别核对。历史阶段限制按其日期和任务范围理解；设计已确认、局部实现、测试通过与生产启用分别判定，不能互相替代，也不因整理文档获得新实施或旧实现拆除授权。

## 1. 目标与当前范围

本项目面向解决方案工程师的日常工作：需求澄清、输出方案和构建可展示的 UI。目标是将 Develop Helper 拆解为在 Buzz 中可以按需调用、独立交付并复用的能力；需要工程实现时，再衔接规划、开发、独立测试和恢复，而不是每次都启动完整软件开发流程。

### 1.1 两条使用路线

- **独立交付**：按本次目标澄清需求、形成客户方案或制作 UI 演示；已有材料足够时直接复用，只补本次用途必需的信息。成果可以单独交付并结束，不强制补齐无关文档或启动下游角色。
- **工程衔接**：用户明确需要实现时，核对已有成果，补齐相关 PRD/AC、工程技术契约、必要界面与确认，再进入规划、开发、独立验收和交付。轻量成果、演示与局部测试不能冒充工程基线或完整业务验收。

成果保存、登记、正式确认、交接、消息发送和下游启动是不同动作，按用途和授权发生，不因 Agent 回复或结构检查自动推进。确认与交接服务于两条路线，不额外成为每次调用的必经审批阶段。

### 1.2 项目归属与复用边界

- 每个项目使用专属本地目录和对应 GitHub 仓库，需求、方案、UI 及后续成果统一归属该项目；已有项目核对后复用，不重复创建或覆盖。具体目录、仓库授权和共享规则见 [单元 01](01-项目初始化与共享资料.md)。
- Develop Helper 原目录保持不动，通过显式软链读取上游资料，在独立融合适配层编写必要的新入口和协作规则。“拆解”是拆分使用方式，不是拆改原框架源码；软链不等于技术只读保护。
- 业务项目、上游、融合实现与融合测试资料分别保存；融合系统的测试要求和进度不写成业务需求。

### 1.3 范围与有效性判断

十一单元描述总体建设范围，不代表每次调用必须走完全部单元，也不代表相关能力已经全部实现。当前 PRD→技术方案参考流程只是限定建设与验证范围，不替代独立需求、方案、UI 或未来工程闭环的总体目标。具体单元的建设与启用须按相应设计、验收和授权执行。

融合是否有效，看独立成果能否完成和复用、用户协调是否减少，以及进入工程后任务是否可追踪、验收是否有独立证据、暂停与中断后能否正确恢复；不以角色数量、在线数量、文档存在或模型调用成功作为完成标准。

## 2. 三层职责

| 层次 | 职责 | 承载方向（不代表生产已启用） |
| --- | --- | --- |
| 能力与规则层 | 独立的需求、方案、UI 能力；按需启用的规划、开发、验收与恢复规则 | 软链引用 Develop Helper 上游资料，独立融合层组织适用方法和必要差异规则 |
| 编排与确定性执行层 | 将可信入站转换为不可变执行上下文；持久化工作流、暂停点与尝试次数；按服务端策略分配角色和工具；执行幂等的权威写入 | 独立 LangGraph Runtime + `buzz-develop-helper` 确定性领域工具；MAF 条件触发，当前生产接线范围见总索引 |
| 协作界面层 | 用户对话、项目频道、可信身份、消息线程、确认入口与状态投影 | Buzz + 实际配置的智能体运行环境；消息是输入与投影，不是工作流数据库 |

Buzz Main Agent 负责面向用户的协调，不逐句中转用户与需求角色的讨论，也不单独保存长工作流的权威执行状态。Workflow Runtime 持有执行事实，确定性节点持有获授权的权威写入权限；角色返回候选成果和证据，不能用自报身份或普通消息取得权限。具体执行契约见 [单元 06](06-角色与工作流运行时.md)。

消息成功发送、Agent 启动、运行节点完成、领域写入成功和业务交付完成必须分别判定。

跨单元的共同追踪主链为：`用户结果 → REQ → AC → API/技术设计 → UI 表达 → Feature → Task → Tester 证据`。需求定义正确结果，方案定义可靠实现契约，UI 定义用户可见行为，Planner 才拆任务，Tester 用独立证据验证。客户方案可以是同一决策链的独立表达视图，但不能替代工程契约或保存无法回溯到 REQ/AC 的唯一实现承诺。

### 3.1 独立交付与确认交接的调用边界

需求、方案、UI 是三类独立交付。确认与交接是跨这些成果和角色的机制。Main、Planner、Developer、Tester 的分工仍见第 2 章和第 5 章。

| 板块 | 可接受的起点 | 本次可独立交付 | 后续按需衔接 |
| --- | --- | --- | --- |
| 需求 | 客户材料、访谈纪要、已有需求或一个业务问题 | 场景、现状痛点、目标流程、范围、成功标准、待澄清事项；进入工程时再补齐所需 PRD 结构与编号 | 方案、UI，或结束本次工作 |
| 方案 | 需求成果，或用户直接提供且足以支撑方案的业务材料 | 面向客户的业务/能力方案、架构说明、关键流程、实施路径、假设与待决取舍；工程级接口和数据契约按需深化 | UI、工程设计/规划，或结束本次工作 |
| UI | 已有需求、方案、页面说明、参考界面或明确的演示场景 | 可展示页面/原型、打开方式、演示步骤、模拟数据说明和实际验证范围 | 展示、修改、需求反推、工程开发，或结束本次工作 |
| 确认与交接 | 任意已有产物及本次希望确认或交接的用途 | 对象与版本、确认者及依据、未决项、模拟/真实边界、下游必需补齐项 | 记录后结束，或在用户要求下交给指定能力 |

独立调用仍要求本次目标所必需的信息；缺少会改变结果的事实时定向澄清，草案中的假设明确标注，不伪造已确认需求。已有材料可直接使用，不强制重新执行其产生阶段。

“确认与交接”是统一处理产物版本及用途的能力，不额外设置每次都要执行的审批阶段。确认用于客户展示，不等于批准真实接口实现、外部调用或发布。

### 3.2 轻量化与按需深化

深化程度取决于本次用途，而不是强制增加阶段：需求成果可以单独结束；客户方案不必每次展开完整七层工程契约；UI 演示可使用明确标注的模拟数据，不等待真实后端。只确认或交接指定成果时，不自动启动下游。

进入工程开发时，再核对已有成果覆盖的范围，只补相关 PRD/AC、技术契约、必要设计确认和环境缺口。轻量需求、客户方案与 UI 演示不自动等于已确认工程基线或前端 Mock 门禁通过。

上述解耦是本次融合的目标变化：原框架的 A → 七层方案 → 必要 B → Planner 顺序作为工程路线保留参考，独立交付路线需要新增入口和适用规则；原源码尚未实现这些入口。

### 3.3 项目初始化与共享资料

**创建项目即建立资料归属和版本管理，不必等到开始开发。** 一个项目对应一个专属本地根目录和一个 GitHub 仓库；仅澄清需求或制作演示也使用该项目目录，但不因此生成完整工程模板、开发任务或启动后续角色。继续已有项目时复用已确认目录与仓库，不重复创建或覆盖原有内容。

共享背景依赖“资料落盘 + 入口索引 + 版本约定 + 读取与同步机制”，不是加入同一频道或关联同一仓库就自动成立。跨单元保留以下原则：

1. 根 `project.json` 保存项目身份与映射，项目 README 只作共享入口和投影，不另建任务状态来源；本机绝对路径按运行环境映射。
2. Agent 接任务或恢复时实际读取相关背景与指定版本，核对工作区和授权；版本一致且内容可读才算共享，不能用收到路径或聊天记忆代替。
3. 本地保存、Git 提交和远端同步分别记录。跨工作区优先核对已获准同步的提交，同机未提交草案可以固定摘要标明 `local-only`；worktree 不会自动共享未提交内容。
4. Main 协调写入与 Git，同文件修改串行、共享文件明确归属；建仓不隐含后续提交、推送或合并授权，不覆盖脏工作区或已有历史。失败保留成果，重试先核对既有结果。
5. 资料按敏感性和授权决定是否上传；密钥及未获准客户原件不进入远端，私有仓库也需检查。大型素材可用受控本地或获准存储引用，不要求所有资料进入 Git；文件与仓库权限分别验证。
6. 业务文件按需建立，工程代码沿用实际结构，不为示例重排已有项目；进入工程后才按需建立 `.sdd/tasks.json`。需求变更保留历史并识别受影响的确认和下游任务，旧结果不能覆盖新基线。

目录骨架、初始化输入与步骤见 [单元 01 第 3—6 节](01-项目初始化与共享资料.md)；版本登记、确认和接收核验见 [单元 05](05-项目成果索引与确认交接.md)。本章只保留共同原则，不重复维护目录树和操作配方。

### 4.1 从单平台主会话编排，调整为 Buzz 界面与独立运行时协作

原 Develop Helper 由平台主会话依规则组织工作，再调用实际可用的设计、规划、开发和测试角色；不是一个智能体亲自完成全部工作。融合版保留角色分工，但按第 2 章把用户协调、持久执行与权威写入分开，具体运行时契约见 [单元 06](06-角色与工作流运行时.md)。

平台薄入口只负责发现和引用适用规则：每个角色保留一个核心职责来源，兼容内容引用上游，必要差异只在融合层维护并注明采用范围。配置目录存在或读过角色文件，不证明角色实际启动、成果已经回收或权限已被隔离。

用户新请求与已派发的角色任务分别处理，工作者不重新进入完整 Router。接入时核对自动加载的 AGENTS、平台规则与角色提示词，通过入口加载范围避免冲突；不修改上游入口，也不要求工作者忽略已加载的冲突规则。项目通用工程约束继续适用。

### 4.2 软链复用与独立融合适配层

采用“上游原件不动 + 软链引用 + 独立融合适配 + 项目成果独立保存”的结构。目录映射、本机配置与初始化细节见 [单元 01 第 2／7 节](01-项目初始化与共享资料.md)，总纲保留以下保护原则：

1. **定位不等于采用规则。** 显式读取上游资料，不整体自动加载其根入口、Router 或 Skill；直接兼容才作执行规则，耦合部分只作方法依据，在融合层写清适用范围与差异。
2. **软链不提供只读隔离。** 经链接写入仍会改动原件；先核对真实权限及脚本是否间接写注册表、活动项目、日志或经验。不直接执行无法保证不写上游的脚本，不擅改原目录权限。
3. **引用和输出位置分别验证。** 保留必要目录关系，核对 Markdown 链接、脚本定位和真实路径；输出只指向获准的融合层或业务项目，不从上游脚本位置推定输出目录。
4. **记录版本不等于锁定版本。** 指纹覆盖所用来源及未提交差异；漂移时暂停相关能力并评估，不自动换源或刷新基线。需要可复现环境时另行准备固定版本只读副本，不切换或重置用户原工作区；上游升级先验证适配差异再更新记录。
5. **跨机器显式恢复映射。** 仓库保存软链不等于携带目标内容；各环境按声明的依赖来源与版本重建、验证映射。断链、权限不足或不支持时明确失败，不静默回退其他版本。
6. **成果保持独立。** 模板只作来源，项目成果是可编辑的真实文件，不软链回上游；记录所用融合／上游版本，按第 3.3 节验证成果共享，不能以规则共享代替。

方法复用不自动继承全流程前置条件或下游派发；例如使用 A/R 方法不等于每次必须生成完整 PRD，软链原脚本也不自动获得任意项目目录或 GitHub 建仓能力。

## 5. 角色方案与用户工具偏好

下表保留职责方向和既有工具偏好，不表示生产配置已经就绪；“优先评估”仍是候选，不在文档清理中替用户确定模型或运行环境。

| 职责 | 首选方式 | 参与时机与边界 |
| --- | --- | --- |
| Main Agent | Buzz 中面向用户的协调会话 | 判断本次交付目标、展示成果与收集明确决定；不作为长工作流数据库，不直接写权威执行状态 |
| Workflow Runtime | 平台中立运行时；LangGraph-first，MAF 条件触发 | 持久化工作流和暂停点，签发服务端角色/工具授权，驱动确定性节点，回收与去重 Agent 结果 |
| 需求澄清 | Buzz 内独立需求 Agent，优先采用 buzz-agent + 可用 GPT 模型；外部 ChatGPT 可选 | 与用户直接多轮澄清并形成候选；确定性节点保存需求成果，可单独交付，不与方案角色强制合并 |
| Solution Designer | 优先用户与 ChatGPT 讨论 | 输出适合当前用途的方案与取舍；工程深化时核对仓库事实及接口契约 |
| UI 制作 | 优先评估 Codex 使用提取后的 UI 方法 | 生成可展示页面并验证实际交互；不默认承担真实后端实现；工具选择是候选建议 |
| Planner | 按阶段启动独立规划会话，优先评估 Codex | 设计确认后形成完整计划；执行后只提出计划调整 |
| Developer | 由运行时按任务选择隔离环境；当前融合运行时建设使用 Fizz/Cursor | 开发并自验；需要并行时拆分独立实例；不改验收口径、权威状态或下一步路由 |
| Verifier / Tester | 由运行时按任务选择隔离环境；当前融合运行时验收使用 Honey/Codex | 独立形成用例、执行验证、返回证据；不修改业务实现和需求以取得通过 |
| 用户 | Buzz 中的项目参与者；方案讨论可暂留 ChatGPT | 确认需求、重要取舍、必要界面与规定的成果门禁 |

角色、运行环境、模型分别配置：角色定义工作职责，运行环境提供会话与工具执行，模型负责推理和生成。角色不等于软件，也不等于永久在线进程。同一种工具可以承载多个隔离的角色会话。

需求的模型／工具配置、材料格式、对话与文件恢复见 [单元 02 第 2—6 节](02-需求能力.md)；成果定稿、确认与交接见 [单元 05 第 5／6 节](05-项目成果索引与确认交接.md)；执行上下文、授权与持久恢复见 [单元 06 第 3—5 节](06-角色与工作流运行时.md)。总纲不再维护单角色配置表或逐轮对话步骤。

外部讨论成果可以保存为文件后进入同一版本与交接机制，不以聊天自动同步为前提。角色返回候选成果、变更、未决事项与建议；结果回收和获授权的状态／写入由 Runtime 与确定性节点处理，没有明确续行请求即结束，不替用户批准方案、开发或发布。

## 6. 状态与交接的设计原则

本章只保留跨单元的状态归属、交接与安全原则。项目目录、仓库与同步见第 3.3 节；成果登记、确认和交接记录见 [单元 05 第 4—6 节](05-项目成果索引与确认交接.md)；执行对象、授权和端口见 [单元 06 第 3—5 节](06-角色与工作流运行时.md)。下列原则不表示相关能力已经实现。

1. 项目专属目录、对应 GitHub 仓库，以及本地保存、Git 提交与远端同步的分别记录，见第 3.3 节。单独的需求、方案或 UI 工作只维护本次所需产物、索引、版本和必要记录，不强制创建完整工程目录或 `.sdd/tasks.json`。进入工程开发后，`.sdd/tasks.json` 是业务任务权威：Planner 提供初始计划，执行字段由 Workflow Runtime 驱动的确定性节点维护。Buzz 的 Issue 或频道只展示投影或提交变更请求，不成为另一套任务状态来源。
2. 工程路线保留 REQ → AC → Feature → Task → 验收证据的关联。项目身份和所选规范以根 `project.json` 为准。轻量成果进入该路线时补齐必要映射，不能冒充其此前已经通过工程验收。
3. 一次派发必须绑定可信、且不可由模型覆盖的项目、工作流、任务、服务端角色、执行轮次、目标身份、工作区、代码基线、输入章节、修改范围、工具授权和验收要求。Agent 自报的项目、角色或工具不能覆盖这些字段。执行上下文与服务端授权见 [单元 06 第 3、5 节](06-角色与工作流运行时.md)。工作区、代码基线、输入章节和验收要求尚未在该两节逐项列成同一绑定，未承接部分仍以本条为准。
4. 一次结果必须关联原派发和对应的 `AgentRun`，并包含输入／输出摘要、修改产物、验证证据和未完成事项。`WorkflowRun`、`AgentRun`、去重记录和暂停点的对象含义见 [单元 06 第 3 节](06-角色与工作流运行时.md)；这些执行记录不能替代项目成果、业务任务或确认记录。成果与确认的归属见 [单元 05 第 4、5 节](05-项目成果索引与确认交接.md)。Buzz 消息只是输入和投影。
5. 相同任务重复送达不重复实施；旧轮次结果不覆盖新轮次；运行状态未知时先核对，不直接重派。
6. 角色提示词中的修改范围属于工作约定，不等于工具或文件权限已经强制隔离；是否强制限制要单独设计并验证。工具授权与路径约束见 [单元 06 第 5 节](06-角色与工作流运行时.md)。本条不取消 Developer 在已授予范围内修改代码。
7. 真实确认必须能够核对确认者、对象、准确版本、用途和可信事件依据。普通回复、其他智能体认可或模糊表情不能自动放行。用户对已展示版本和明确用途作出、且能按 [单元 05 第 5、6 节](05-项目成果索引与确认交接.md)核验的确认仍然有效；记录字段、快照和接收核验以该两节为准。
8. 原框架的前端门禁、逐步模式和有限返工用于相应工程路线。独立 UI 演示交付不自动触发全项目后端配置门禁。独立路线的适用范围是本次明确的解耦目标，与实际验证分开，具体实现后再验证。

## 9. 最小试点与通过条件

本章说明融合是否有效的总体验证目标，不指定当前试点项目，也不派发任务。具体项目、资源、工具、执行步骤、验收范围和权限，由对应计划和明确授权确定。当前建设停点见 总索引（建设管理材料，本批不收录），本章不复制接入顺序。

参考场景仍要观察到：连续多轮澄清，并在途中变更一项已讨论的要求；候选由确定性工具保存为准确版本，需要确认时绑定该版本及用途；重启后从持久成果与运行状态恢复；仅在明确请求下交给下游，接收者实际读取并正确复述关键范围、最新变更和未决项，而不只是收到路径。关键事实不丢失，旧要求不混用，确认对象明确，文档实际可读取，不自动启动方案或开发。模型调用成功或仓库创建成功，只是接入检查，不等于共享需求工作流通过。已有项目核对后复用；本章不构成自动建仓、提交或同步授权。

验证前核对融合层依赖：来源可读，引用解析正确，上游版本匹配，自动加载入口不触发原全流程；比较运行前后的上游文件状态，确认没有由融合操作产生的写入。保护原则见第 4.2 节、第 7 章和 [单元 01 第 7、8 节](01-项目初始化与共享资料.md)。foundation 通过不等于这些保护已经成立。断链或版本漂移时，停止受影响调用，不自动换源或修改原目录。故障模拟须另获明确授权，不得为此改动真实上游。

独立交付看解决方案工程师的日常工作，用同一业务场景分别观察独立调用与成果复用。下表八项是总体覆盖维度，不要求每次独立请求执行整张表。表内条件是授权验证时应看到的行为；沿用既有 GPT 偏好，不把尚未接通的角色写成已经可用。

| 场景 | 通过条件 |
| --- | --- |
| 项目初始化 | 专属本地目录、Git 仓库、GitHub 远端与 Buzz 项目映射正确；敏感资料不被收录；已有项目核对后复用、不重复建仓，失败时状态如实保留 |
| 共享项目背景 | 需求 Agent 与接收角色实际读取同一版本的项目入口及成果；跨工作区时核对已同步提交，未提交文件不冒充已共享 |
| 只澄清需求 | 在 Buzz 中由 GPT 需求 Agent 连续澄清并形成候选，确定性节点保存可读取的需求成果；无需外部 ChatGPT 中转，不自动启动技术方案、UI 或开发 |
| 需求变更与恢复 | 修改要求后，文档与确认状态同步反映变更；重启后能从已保存成果恢复，不混用其他话题或旧要求 |

| 只构建 UI | 使用现成页面说明生成可展示页面，实测展示和关键交互，明确模拟范围，不要求先重做需求与方案 |

工程衔接的参考场景是：复用已有成果，补齐必要工程契约后，观察小型 Web 业务中的前端 Mock、一个真实后端能力与联调。这是既有参考形态，不要求现在选定项目或开工，也不把该形态强加给全部业务项目。所需角色按阶段参与，先顺序执行，再在既有模式允许的范围内验证前后端并行；本章不新增并行授权。下表是该参考场景的通过条件。

| 场景 | 通过条件 |
| --- | --- |
| 正常交付 | 确认方案 → 规划 → 开发自验 → 独立测试 → 联调 → 交付，产物可追溯 |
| 缺陷返工 | Tester 给出可复现证据，Developer 定点修复，Tester 复验，保留重试次数 |
| 前端门禁 | 必须等用户确认当前 Mock 与必要配置；暂停期间不新增未经允许的派发 |
| 中断恢复 | Workflow Runtime 与 Agent 进程重启后从持久状态、冻结输入和真实成果恢复，不重复开发或重放副作用。该恢复不保证底层模型调用恰好一次 |
| 重复与迟到消息 | 同一派发只实施一次；过期回报不覆盖新结果 |
| 验证条件缺失 | 标明具体未验 AC、环境缺口与恢复条件；不用 Mock、角色自报或消息发送成功冒充真实通过 |

独立交付比较从材料输入到可用成果的耗时、不必要的确认／文档数量、跨板块复用情况和用户介入次数；工程衔接再比较交付耗时、有效缺陷数及模型／工具消耗。相似任务的对比用于判断是否继续扩展，不把一次试点当作普遍效率结论。
