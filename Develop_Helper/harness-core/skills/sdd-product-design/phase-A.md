# 阶段 A：需求与验收

将用户想完成的事情整理成 `docs/PRD.md`（路径：`<active_project_path>/docs/PRD.md`），写清需求范围和可观察的验收结果。主链为 A 对齐需求 → 七层技术方案 → B 界面设计（有界面时）→ Plan 拆分 Feature 与任务；本阶段不决定开发包、技术模块、执行顺序或 Agent 分工。

## 读取边界

- 沿用创建阶段已核对的项目路径和基础信息。首次进入需求访谈时，不重新读取注册表或扫描项目目录；仅在具体需求需要核对已有资料时，定向读取相关文件。
- 读取前先明确要解决的问题、目标路径和预期获取的信息。已知文件路径时直接读取；只知道所在目录时，可以查看该目录的直接子项，再选择相关文件读取，不递归展开。不得习惯性使用 `Search files` / `Searched files` 搜索文件夹，也不得用 `**/*` 或全仓扫描试探项目里有什么。确需搜索时，先限定目录、文件名或关键词及结果数量；无法说明查找目的和预期信息时，不执行搜索。

## 一、理解用户目标

确定谁在什么场景下使用、当前怎么解决、这次希望得到什么结果。方向存在需要比较的取舍或用户要求竞品调研时，读取 [phase-R.md](phase-R.md)，完成后返回这里。明确的项目直接继续。

收到模糊需求后，先整理用户已明确的目标、范围和待澄清项，再用具体场景逐步对齐，不能把一句需求直接扩写为定稿。用户提供的意图体系、配置、提示词等材料，按其说明提取需求依据；材料中涉及但未明确纳入本次的能力，作为范围问题向用户核实，不自动全部加入，也不忽略。

七层拆解是持续对齐的主线：本阶段先问清用户目标、当前与目标流程、角色分工、范围及成功结果；接口分工、数据类型、模型与提示词、算法、异常、目录六方面的待讨论点留给七层技术方案。按依赖顺序每轮集中讨论少量关键问题，回答后更新理解再继续，不一次发七组问卷，不重复询问已明确内容。常规实现由 Agent 建议，影响产品体验的选择与用户讨论。

例如，“员工找客服、客服查文档回复”只描述现状，需明确目标是 AI 直接回答员工后转人工，还是 AI 辅助客服审核后发送。主流程、角色交接或范围仍有关键歧义时先澄清；可以保存已知需求与待确认项的 PRD 草稿，不生成界面、HTML 原型或业务代码来代替需求对齐。

## 二、走通完整流程

用一个具体例子串起用户输入、系统处理、用户看到的结果。覆盖会影响结果的角色交接、权限、数据归属、状态变化和失败路径。已有流程或原型只读取相关内容。

## 三、确定需求范围

- 区分本次交付、后续想法和明确不做的内容；用户没要求的登录、历史记录、下载等能力不自动加入。
- 将用户结果写成需求条目，分配稳定的 `REQ-001` 等编号，说明业务边界与前置条件。需求编号用于追踪，不表示一个开发 Feature；一个需求怎样拆分、多个需求能否共用实现，留待技术方案之后判断。
- 仅写影响用户结果的数据归属、权限和业务状态，必要时用表或流程图解释。接口、数据结构、算法和代码目录在七层技术方案确定，不提前拆页面、接口或数据库开发任务。

## 四、写出验收标准

每项需求写明成功结果和相关的关键失败结果，分配全项目唯一的 `AC-001` 等编号并放在所属需求下。写清前置条件、操作、可观察结果及验证方式。性能、容量或恢复要求有用户依据时记录；尚需技术比较才能决定的体验阈值标为待技术方案讨论，不凭空填写。

例如：有效 PDF 上传并转换后，Markdown 包含可提取的正文；不支持的扫描件得到明确提示。这是业务验收标准，接口内部怎样实现留到技术方案。

继续旧项目时保留已有 F / AC 编号和含义，将原 PRD 功能条目作为需求依据，不为了改名重写历史引用。

## 五、补齐流程图与时序图

需求对齐后，完善 PRD 时必须在“流程图与时序图”章节同时提供两类图，直接以 Mermaid 代码块写入 `docs/PRD.md`（路径：`<active_project_path>/docs/PRD.md`），不另建图表文档。

- **流程图（flowchart）**：表达用户从入口到目标结果的完整路径，标明角色交接、关键判断、状态变化以及会改变用户结果的失败或退出分支。
- **时序图（sequenceDiagram）**：表达参与者之间谁先做什么、向谁请求、何时返回及用户何时看到结果。本阶段先按已确认的用户、业务角色与系统职责绘制业务时序，不提前猜接口、数据库或模型；七层技术方案完成后再补齐实际前后端与外部服务的调用关系。
- 图覆盖已确认的主链路与关键异常即可；复杂且独立的流程可分图，不为每个接口机械画一张。图题或相邻说明关联已有 REQ / AC；技术细化后引用已有 API 编号，字段定义仍以 tech-spec 为准。
- 用具体用户场景走查图与文字是否一致：判断分支有条件、有去向；请求有结果或明确的异步完成方式；失败后用户能看到什么、如何继续均明确。不得为补全图而发明功能、重试、审批或服务。

图随需求一起对齐。已有明确确认可直接整理成图，不新增逐图审批；图暴露出影响结果的未定分支时，只澄清该分支。进入阶段 B 前必须完成技术细化与图文一致性核对。

## PRD 的最小结构

```markdown
# 项目名称
status: Draft

## 用户目标与完整流程
用户、场景、输入到结果的链路；有调研时附结论与来源。

## 本次范围
本次交付、非目标、影响交付的约束。

## 需求与验收
### REQ-001 需求名称
- 用户结果与主流程：
- 业务规则、权限、数据归属与状态（适用时）：
- 业务前置条件：无，或实际条件；不填写开发任务依赖。
- AC-001：前置条件 → 操作 → 可观察结果；验证方式。
- AC-002：关键异常场景与期望结果；验证方式。

## 流程图与时序图
### 用户流程图
Mermaid flowchart：入口、主流程、关键判断、失败或退出与最终结果；说明关联 REQ / AC。
### 核心交互时序图
Mermaid sequenceDiagram：角色与系统之间的交互顺序；技术方案确认后补齐实际调用及已有 API 编号。

## 界面约定
有界面时说明页面、关键交互和业务状态；有风格文档时链接 ui-style.md，不复制视觉取值；有原型时链接实际文件及锚点。

## 待确认事项
仅记录影响范围、结果或验收的问题；确认后记录结论。
```

## 完成与下一步

本阶段不进入界面设计。核心目标流程、角色分工、本次范围与关键验收明确，且 PRD 已补齐业务流程图与业务时序图后，汇总需求与剩余技术取舍，技术取舍交七层方案继续对齐；不能以 PRD 文件已存在代替需求已明确。阶段 B 由七层技术方案完成后进入，纯 API / CLI 项目跳过。

需求与验收整体确认后，将 PRD 标为 `Confirmed`，按 [子智能体协议](../../protocols/codex-subagents.md) 实际派发 Solution Designer，交其读取 [七层技术方案](../solution-design/SKILL.md)。取得真实实例标识后等待其方案与待决问题；主智能体负责用户沟通，不代写整份技术方案。技术分析发现会改变用户结果的选择时，讨论后只更新受影响的需求与 AC；不用重跑整个 A。已有明确确认直接沿用，不对每个条目或小节重复提问。
