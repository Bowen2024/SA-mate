# 接口逻辑如何影响用户体验

设计七层方案的第五层时读取一次，逐个 API 使用。目标是发现技术选择背后的产品取舍；简单接口简写，不增加固定报告或逐接口审批。

## 1. 从执行过程找到分歧

先写输入检查 → 实际处理 → 状态与数据变化 → 返回结果，再走一次耗时、失败与用户再次操作的情境。沿执行节点问：同一个请求响应结构下，不同处理方式会让用户经历什么差异？

| 检查维度 | 要回答的问题 |
| --- | --- |
| 能力与输入边界 | 哪些文件、操作或依赖可用？超过边界时拒绝、部分处理还是要求补充？是否改变需求承诺？ |
| 等待与反馈 | 何时表示已接收、执行中和完成？耗时超过预期时用户看见什么，能否继续其他操作？ |
| 结果与质量 | 怎样判断真正完成？部分结果、格式损失或输出截断是否告知用户？ |
| 失败与恢复 | 超时、断连、取消后执行是否继续？重试会否重复操作？用户需要从哪一步重来？ |
| 状态与生命周期 | 刷新或再次进入能否找回任务与结果？文件保留、过期与清理怎样影响用户？ |
| 并发与资源 | 同时提交时排队、拒绝还是并行？资源限制怎样影响等待、成功率与费用？ |
| 权限与用户控制 | 程序可访问哪些文件、网络或操作？限制如何告知？涉及用户数据或副作用时用户有什么控制方式？ |

每个相关点写成“技术选择 → 用户可见后果 → 当前方案或候选 → 验收方式”，放入 tech-spec 对应 API 的分析表。已有需求已定的行为直接引用；没有重要分歧时说明沿用依据即可。

## 2. 哪些问题与用户讨论

存在不同合理选项，且会明显改变交付范围、操作或等待方式、结果质量、恢复方式、数据留存、权限或费用时，必须让用户知情并取得选择。内部函数、命名、未改变约定行为的代码分层等由 Agent 决定。

沟通前先整理具体情境、通常 2—3 个可行选项、用户能感知的差异、建议与代价。问题用“用户能做什么、要等待什么、可能失去什么”表达，不让用户在未解释的术语之间选择。相互关联的取舍一起讨论，不一次抛出所有接口的问题。

技术可行性与产品选择分开：性能、资源消耗、供应商限制等先查可靠资料或提出最小验证；没有实测的数据标为估计或待验证，不让用户承担本应由 Agent 查清的技术事实。仅授权方案设计时，不能为验证自行安装或执行业务代码。

主智能体负责沟通；子智能体返回选项、推荐及需决定的后果。已有明确选择直接复用；用户明确委托 Agent 决定时，在授权范围内选择并说明理由。缺少回答不等于同意，待决定期间只继续不依赖该选择的工作。

## 3. sandbox 执行接口示例

假设接口接收指令和文件编号，交给执行环境处理 PDF。不能止于“调用 sandbox 执行 Python”，还要说明文件和指令校验 → 准备执行环境 → 运行 → 收集状态、输出与文件 → 检查结果 → 返回真实观察；Agent 据观察决定继续、修复或结束。

以下是检查示例，不是所有项目都要实现的功能，也不是预设用户选择：

| 执行节点 | 需要讨论或验证的体验问题 |
| --- | --- |
| 准备环境与依赖 | 首次启动与再次执行的等待是否不同？只支持预装依赖还是允许扩展，会限制哪些用户任务？ |
| 读取 PDF | 扫描件、加密文档或复杂排版怎样处理？允许部分内容还是要求完整结果？先明确支持范围，不自动增加 OCR。 |
| 运行与超时 | 请求结束后程序是否仍在运行？继续等待、限制任务规模或后台执行各有什么操作与实现代价？按项目需要选择，不默认引入队列。 |
| 用户再次操作 | 用户刷新、取消或重试时，原执行怎样处理？是否产生重复任务或丢失已有结果？取消不能只描述前端停止显示。 |
| 收集与验收 | 进程结束是否真的生成了可用 Markdown？日志截断、空文件或部分结果如何传给模型与用户？ |
| 文件与权限 | 每次执行复用还是新建状态？结果何时清理、清理后能否恢复？目录、网络与进程的实际访问边界如何实现和验证？ |

执行边界必须与实现一致，不把工作目录或虚拟环境直接当作操作系统级隔离；也不在本流程预选 Docker 或任何沙盒产品。输出中的能力与安全承诺以实际方案和验证为准。

## 4. 留下可追溯的选择

出现重要取舍时才读取 [决策记录模板](decision-record-template.md)，在项目 `docs/decisions.md`（路径：`<active_project_path>/docs/decisions.md`）维护 D 编号。一个记录可以覆盖多个相关 API，不每接口建文件；常规实现理由留在 tech-spec 即可。

确认后把用户可见结果写入 PRD / AC（路径：`<active_project_path>/docs/PRD.md`），实现方式写入 tech-spec（路径：`<active_project_path>/docs/tech-spec.md`），必要的界面变化回写风格文档（路径：`<active_project_path>/docs/ui-style.md`）或原型（路径：`<active_project_path>/docs/prototypes/` 下的实际文件）。实际取值在技术方案统一维护；决策记录保存为什么这样选、当时的依据与被放弃的选项。Plan 只引用相关记录章节，不让每个开发任务重读整个决策文件。
