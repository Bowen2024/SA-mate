# 重要体验取舍记录模板

首次出现重要取舍时才创建项目 `docs/decisions.md`（路径：`<active_project_path>/docs/decisions.md`）。同一文件按 D 编号追加记录，未确认的选项也可暂存；不能将建议标成用户决定。没有重要取舍时不创建空文件。

每个记录使用以下结构，按实际内容填写，不机械复制示例值：

## D-001 决策主题

- **日期与状态**：实际日期；待确认 / 已确认 / 已替代。
- **关联**：REQ、AC、API 编号与实际章节；旧项目使用原 ID。
- **问题与体验影响**：触发场景、用户会遇到什么，以及已有需求或限制。

| 可选方案 | 用户体验与代价 | 技术依据或待验证项 |
| --- | --- | --- |
| 方案 A | 用户如何操作、等待、恢复，质量/费用等实际影响 | 已查资料的直接来源、已验证结果或明确的未知项 |
| 方案 B | 同上，仅写有差别的部分 | 不编造性能或能力保证 |

- **建议及理由**：为什么适合当前用户与约束，放弃了什么。
- **最终选择与确认依据**：待确认时留待定；确认后记录实际选择、日期、用户原话或准确摘要，以及确认发生的上下文。沿用已有决定时链接实际记录；由 Agent 决定时记录用户委托的范围与依据，不假装用户逐项选过。
- **落地与验收**：受影响的 PRD / AC 和 tech-spec 章节，以及验证已选行为的场景与预期结果；测试尚未执行时明确标注。
- **复议条件（需要时）**：什么需求变化或验证结果会使该选择需要重议。

同一议题确认前可更新候选；确认后发生实质改变时新增 D 编号，将旧记录标为“已替代”并互相引用，保留原选择、理由与确认依据。当前实现以已确认 tech-spec 为准，决策文件用于追溯，不维护第二份接口契约。不记录密钥、私人文件内容或未经脱敏的用户数据。
