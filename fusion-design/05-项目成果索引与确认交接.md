## 1. 本次目标与适用范围

让已保存的需求、方案和 UI 成果可被发现、按指定用途确认，并按用户意图交给指定角色。

保存、登记、确认、交接、消息发送和下游启动分别发生，可以只做其中必要的部分。交接内部仍分开准备、实际发送和接收核验，不把这三步记成同一次成功；下游启动也不从交接记录或消息已发送推导出来。一次清楚的用户授权可以覆盖其中必要的几项，本章不因此增加逐项审批。

最小输入是项目 ID、本次动作与用途、实际成果及可核对版本；确认时还需要用户依据，交接时还需要接收角色、授权范围与输出要求。路径和 SHA 由角色与工具取得，用户只需表达业务意图，不要求用户抄写内部参数。外部 ChatGPT 或其他工具的成果也使用相同机制；先保存真实文件，不把聊天摘要当作已存在的成果。

独立交付物：项目成果索引、按需形成的正式确认记录、指定版本交接记录及接收回执。没有确认或交接请求时不预建空记录，不生成工程任务表。确认客户展示、方案讨论或 UI 演示，不自动等于批准开发基线、发布或外部调用。

## 4. 成果登记与事实归属

### 4.1 一个事实只在一个位置维护

事实归属以下表为准。一行一个权威来源，其他位置只做摘要、导航或投影。

| 事实 | 权威来源 | 其他位置的用途 |
| --- | --- | --- |
| 业务内容与假设 | 指定成果版本的实际文件 | README 仅摘要；索引只定位 |
| 项目身份与成果入口 | 根 `project.json` | README 提供可读导航，不成为第二套可独立维护的索引 |
| 谁确认何物、允许什么用途 | `docs/decisions.md` 中按 ID 保存的确认记录 | 索引引用记录 ID；批准显示由记录及版本校验推导 |
| 某次交给谁、用哪个版本、读到了什么 | `docs/handoffs/<handoff-id>.json`，拟定 | 消息只是通知/回报载体，不以“消息发送成功”替代读取成功 |
| 工程执行状态 | 后续工程机制 | 不放入成果索引、确认记录或 README 另建状态机 |

登记表示“文件存在且入口可核对”，不表示已批准。最新草案可以是 v0.4，而某用途仍只有 v0.3 的确认；必须分别展示，不用单一“已确认”标签覆盖全项目。

交接路径一格中的「拟定」保留原词，表示写入该表时的说法。第 6 章另有后来的实现记录。本节不把这一格改成当前实例已接通，也不修改第 6 章。

兼容结构如下。不新增成果 kind，也不把路径字段改成不兼容对象。

首版 schema 已收敛：保留现有 `schema_version: 1` 和 `artifacts` 的相对路径/null 语义，新增 `artifact_registry.schema_version: 1`。registry 包含 `confirmations_path`、`handoffs_directory` 和按成果 ID 组织的 `entries`；每个 entry 区分 `current_version` 与版本列表。版本记录绑定内容路径/清单、字节 SHA、大小、文档状态、生产角色、用途、摘要、未决项、确认引用、可见范围和登记身份。完整字段与示例以 `../buzz-develop-helper/capabilities/artifact-registry.md` 为当前实现契约。

本章不复制 `artifact-registry.md` 中的 JSON 示例。引用它不表示其中的状态句就是当前实例已接通。

旧项目先做只读预览，不直接把现有路径字段改为不兼容对象或运行初始化覆盖文件。同一版本标签不能绑定不同摘要；历史版本不自动成为当前入口；`local-only` 不能声称 Git 提交。UI 等多文件成果使用项目内清单固定入口及每个成员 SHA。README 是 registry 当前入口的投影，使用托管标记；首次迁移只删除初始化器的固定空索引占位，保留其他手写内容。

每个成果登记至少包含以下信息组：

| 信息组 | 必要内容 |
| --- | --- |
| 身份 | project_id、成果 ID、类型（需求/方案/UI）、生产角色、登记者与时间 |
| 版本定位 | 人可读版本号、项目内相对路径、原始文件字节的 SHA-256、保留版本的路径；版本号不代替 SHA |
| 集合成果 | UI 等多文件成果的清单路径、清单 SHA、每个文件的相对路径和 SHA；清单包含演示入口及必要依赖说明，不只散列目录名或截图 |
| 内容边界 | 交付用途、范围与非目标、模拟/真实边界、实际验证证据引用 |

### 4.2 登记过程与中断处理

写入和恢复仍是下面六步。每步都要复读真实文件，核验路径和版本，保住 README 托管块以外的手写内容，并保留公共锁、乐观摘要、事务日志前滚、外部编辑停止和写完后的复核。详细步骤不改成只留链接，因为这些恢复条件没有整段搬到别处。

1. 成果角色保存后回报登记材料；Main 重新解析项目，读取实际成果、索引和 README，并记录修改前摘要。来源角色自报的路径、SHA 和角色名不能直接作为可信写入参数。
2. 核验项目内真实路径和文件类型，拒绝越界、软链绕行及不支持的文件对象；缺失、摘要不符或版本混杂时只报告冲突，不猜测“最新”。保留已存在的历史文件和用户编辑。
3. Main 预览精确变更：登记路径、版本与记录引用，同步 README 中受影响的成果索引、过时缺失说明和状态摘要，保留其他手写内容。没有记录的确认显示“未正式确认”。
4. 已实现共同的 `.project-state.lock`：需求保存、索引写入和 Git 初始化元数据更新先取得该锁，再使用各自局部锁。Main 在锁内重新读取并校验 project.json/README 的预期 SHA，再重新生成预览；摘要变化即停止，不覆盖迟到编辑。未知锁不自动删除。
5. 写入内核先持久化包含两文件写入前后字节和 SHA 的事务日志，再以临时文件、`fsync` 和原子替换依次写权威索引与 README 投影。中途失败保留日志；Main 恢复时只对仍等于事务前或事务后摘要的文件前滚，发现事务外编辑即停止并保留日志。全部一致后才删除日志。该机制已用失败注入测试验证，但尚未在真实业务项目或进程级故障中验收。
6. 全部完成后重新读取路径、SHA 和引用并回报。重复登记相同版本不重复创建记录；迟到的旧版本只可登记为历史，不抢占当前入口。锁来源未知时核对在途工作，不自动删除。

第 5 步是先持久化两文件写入前后的字节和 SHA，再依次原子替换索引和 README。这不是两份文件天然一次原子提交。失败注入已经验证的范围，以及尚未在真实业务项目或进程级故障中验收的边界，仍以第 5 步原句为准。

来源 SHA 和成果自身 SHA 用途不同。后来登记索引不反向改写已有需求正文。

需求文档中的项目入口来源 SHA 表示“生成当时读到的版本”。后来登记索引会改变 project.json/README 的 SHA，不应反向重写既有需求或否定旧版事实，也不能为追求摘要一致反复生成需求。新保存的草案才重新读取当时的来源；确认和交接校验目标成果自身 SHA。

第 6 步已经写明：迟到的旧版本只可登记为历史，不抢占当前入口。这是登记规则，不是另一次当前入口。

## 5. Draft 怎样形成正式确认记录

对象和用途仍是：指定版本、明确用途、未决项和模拟或真实边界。确认写在外部记录里，不改写成果正文。

采用“保留成果字节 + 外部确认记录”的首版建议。`requirements.py` 的 Draft 标记描述该文件由草案工具生成且未认证批准，不改成 `true` 来制造确认。确认后，项目入口可显示“v0.3 的指定内容已获某用途确认（C-…）”；是否可用由确认记录、对象摘要和用途共同决定。

这与上游直接把 PRD 头部改为 `Confirmed` 有意不同。现有需求 `context` 的固定 false 仍保留其原语义；未来增加独立确认解析接口，并在接收适配器中区分“草案工具未验证”与“外部确认有效”。接收角色若无法理解该契约，应停止相应交接，不凭一个文件头或索引标签放行。工程工具需要 Confirmed 格式时另设计转换，不偷偷改写已确认对象导致 SHA 改变。

上一句里的独立确认解析接口仍是未来事项，不是当前可调用接口。一般 D- 取舍记录和受管 C- 确认记录分开。待确认建议或普通手写文字不能自动变成正式确认。写入 `docs/decisions.md` 受管块时，保留块外已有手写内容。入口展示里的 C- 只标识某条确认记录。

确认步骤：

1. Main 汇总用户要确认的具体版本、用途、关键范围、未决项及模拟/真实边界。若已有清晰且可核验的确认，直接沿用，不重复逐条提问。
2. 固定确认对象：单文件保留其原始字节快照；多文件成果固定成员清单及全部字节，包含相关演示说明。快照位置和 SHA 必须能重新读取，不能只留一个将来会被覆盖的当前路径。首版可在交接资料下使用按摘要命名的快照区，具体目录在 schema 中确定。
3. 核对用户消息的身份、项目/线程、时间、明确对象和使用意图。只有“保存一下”、一般赞同、角色自述“已确认”或零散需求选择，不构成整个 Draft 的正式批准。
4. 已有确认事件缺少版本关联时，不把它追溯绑定到刚生成的新 SHA。可回收当时展示的确切版本则核验；无法核验则保留为待核对线索，只澄清缺少的对象或用途。
5. Main 追加正式确认记录，复读并校验后将引用登记到索引。正文无需重新保存。对确认后新增/改变的内容生成新版本及必要的新确认，不继承旧版批准。

第 2 步的「具体目录在 schema 中确定」是设计说法。下面的实现记录把快照写在 `docs/confirmations/snapshots/`。两处都保留。

当前实现：`scripts/main_collaboration.py` 接受 Main capability 与宿主签发的 `current-session` 用户依据，按项目、会话、消息、成果版本、内容 SHA 和用途生成确定性确认 ID。记录写入 `docs/decisions.md` 受管块，快照写入 `docs/confirmations/snapshots/`；单文件成果的登记版本改指向内容寻址快照，原工作文件保留为后续新版本入口。确认、索引和 README 使用共同项目锁、乐观摘要与持久事务，失败可前滚。实现不修改正文 Draft 状态。

已确认快照保持当时的字节和 SHA。原工作文件仍可产生新版本。确认记录不改写正文的 Draft 状态。

写入、复核，以及已有确认的直接沿用，分别以这段实现原句和第 1 步为准。

受信确认由 Runtime 的确定性节点执行。严格协议和内部字段不在这里复制，也不要求用户填写内部参数。见 [06 第 4.3 节与第 8.1 节](06-角色与工作流运行时.md)，以及 业务工具链计划（`fusion-runtime-lab/BUSINESS_TOOLCHAIN_PLAN.md`，未随本批发布） 第 3.3、5.1、5.2 和 12 节。N08 成功后停止，其后的步骤需要显式续行。这只覆盖该计划的临时项目限定边界，不外推为生产 provider-read、通用确认界面或真实业务交接。

每条确认记录至少绑定：

- `confirmation_id`、项目、确认人、确认时间、记录人和核验方式；不能由请求正文中的 `role=Main` 或 Agent 名字证明身份。
- 成果 ID、版本、路径、SHA/集合清单 SHA、稳定快照位置和此次覆盖的章节/范围。
- 明确允许的用途、非授权事项、模拟/真实边界、相关未决项及针对该用途的处理。非阻塞项可随批准保留，阻塞项未解决时不能把该用途标成已确认；换成可讨论用途不能暗改用户原请求。
- 原始事件的系统、项目/频道/线程/消息标识、用户原话或准确摘要、关联的展示版本，以及实际核验结果。只存在事件 ID 或 SHA 不能证明消息来源可信。
- 替代/撤销关系及原因。首版建议按确认 ID 追加记录；撤销和替代追加新事件，保留旧证据，当前有效性通过关系解析，不悄悄改写历史。

重复、变更和撤销以第 4 步、第 5 步和第 5 组为准。第 5 组的撤销和替代追加仍是首版建议。本节不把撤销或替代写成已经可调用的写入 API。

确认依据读取分为三档：`provider-read` 通过 Buzz 受控读取接口取得并校验签名事件；`current-session` 由运行时绑定当前用户和会话，只支持记录用户针对已展示版本作出的这次新确认；`reported-unverified` 是用户、Agent、文档或截图转述，只作线索。后者不得把 Draft 提升为正式确认，必须由平台回读或当前用户重新确认。

`current-session` 只覆盖当前会话里、针对已展示版本的这次新确认，不追溯证明其他线程。

Buzz 源码中的论坛消息结构已包含 `event_id / pubkey / sig / content / created_at / channel_id / tags`，线程回复另含 parent/root event ID，且转换代码把签名事件作者视为权威身份；这说明平台有承载依据所需的数据，不证明当前实例已有可供融合层调用的受控接口。正式依据仍须同时绑定成果路径、SHA 和用途。证据副本可以按摘要固定用于追溯，但内容摘要或事件 ID本身不是身份认证。具体接入契约见 `../buzz-develop-helper/adapters/main-artifact-registry.md`。

## 6. 指定版本怎样安全交给下游

正式确认不是所有复用任务的前置门禁：用户可明确要求把 Draft 用于讨论或探索，该交接必须标出 Draft 和用途限制；需要已确认输入的任务才检验对应确认。确认本身也不自动产生交接或启动授权。

当前内核只接受用途匹配的有效确认 ID。当前实现段的原句是“交接首版只接受用途匹配的有效确认 ID”。本节不增建接口来消除 Draft 讨论和已确认输入的差别，也不把讨论用途改成强制审批。

交接过程：

1. Main 根据已有明确请求选择接收角色、目的与范围；未要求继续就结束。确认与启动可在同一条清晰用户指令中授权，不机械增加重复审批。
2. 固定输入包：成果版本/快照、必要来源、确认记录及未决项。`decisions.md` 后续会追加内容，交接绑定具体记录 ID 及当时记录的快照摘要，不要求可变文件永远保持旧的全文件 SHA。UI 包还需说明启动方式、环境/依赖和已验证范围；SHA 相同本身不证明界面可运行。
3. 同机未提交成果标为 `local-only`，接收者须能读取固定快照；跨工作区优先使用已获准同步的仓库提交，并校验提交中的实际文件内容。若无可达提交，也没有另获授权的传输方式，则停在待交接，不自动提交/推送，不把共享路径当作已同步。
4. 写交接记录，再通过实际可用且获授权的机制发送。发送后只记“已发送”，未发送仅记“已准备”；没有工具就交回用户，不声称已派发。可靠消息、实例与重试机制由单元 08 细化。
5. 接收者先核对项目映射、版本 SHA、用途、确认有效性与写入范围，读取原文后回报目标、关键范围、最新变更和未决项。Main 核验回执，才能记“接收核验通过”；回复“收到”或实例已启动都不等于交接成功。
6. 接收核验通过也只允许执行此次明确授权的任务。若本次只是交接检查则停止；工程开发仍检查后续门禁，不把一次读取回执视作业务验收或开工批准。

交接记录字段组：交接 ID、项目与发起者、接收角色及实际接收身份/实例（未知则为空）、用户任务授权依据、输入版本集合、用途与确认引用、未决项、工作区映射、允许读写范围、预期输出与回报要求、状态及发送/接收证据。下游回执须引用同一交接 ID 和实际读到的 SHA，不能让其他项目/旧轮次的回报完成本次交接。

准备、发送和接收核验各有证据。准备以第 4 步未发送时记“已准备”，以及当前实现“准备交接需要当前会话用户授权”为准。发送以第 4 步发送后记“已发送”，以及“标记已发送需要受信发送依据”为准。接收核验以第 5 步的读取、回报和 Main 核验为准。指定 principal/authority 回报每个确认 ID 与实际 SHA，并复述目标、范围和未决项，原句在当前实现段。SHA 相同本身不证明界面可运行，原句在第 2 步。回复“收到”或实例已启动都不等于交接成功，原句在第 5 步；这也不等于已经读到原文。

建议交接状态为“已准备 → 已发送 → 接收核验通过”，异常为“受阻/取消/已替代”；这些只描述交接，不跟踪业务任务执行。超时或发送结果未知时先查询实际结果，不直接重派；去重和在途运行处置的技术实现留给单元 08。

受阻、取消和已替代仍是建议中的异常方向。它们和当前实现保存的 `prepared / sent / received-verified` 分开。本节不把这三项异常写成已经实现的状态，也不补成新的序列化状态。

当前实现：交接首版只接受用途匹配的有效确认 ID，并在 `docs/handoffs/<handoff-id>.json` 保存 `prepared / sent / received-verified`。准备交接需要当前会话用户授权；标记已发送需要受信发送依据；接收核验需要指定 principal/authority 回报每个确认 ID 与实际 SHA，并复述目标、范围和未决项。错误身份、用途或版本均拒绝。内核不发送消息、不创建角色、不启动执行，所有状态都保留 `downstream_started=false`。

实际授权和已经启动仍然分开。确认不自动产生交接或启动授权，原句在本章开头。第 6 步只允许执行此次明确授权的任务；本次只是交接检查则停止。内核不发送消息、不创建角色、不启动执行，所有状态都保留 `downstream_started=false`。记录成功不能推出真实消息、角色或执行已经完成。本节不把当前实现没有写出的字段名补进交接 JSON。

工作区可达、固定输入包，以及 `decisions.md` 按记录 ID 绑定，分别以第 3 步和第 2 步原句为准。不自动提交/推送，不把共享路径当作已同步。

版本在途变化时，旧快照仍保留，旧确认只对旧版本有效。Main 标出受影响交接并暂停其后续使用，核对继续旧版还是改用新版的授权；不能默默让接收者读“最新”。若用户明确要求继续旧版可按原用途核验后继续。确认撤销后，保留历史回执但不得用于新的放行；已运行任务的通知、停止与重新派发由 Main 衔接单元 08/10。下游输出回报输入版本，旧结果不得覆盖新版入口。

可靠消息、去重和在途运行处置仍指向单元 08。已运行任务的通知、停止与重新派发仍指向单元 08/10。这些都是纯文本。上述单元尚未建立独立文档，本节不补文件链接，也不补状态机。
