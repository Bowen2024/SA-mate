本单元负责项目归属和共享资料。设计约定、已实现的本地能力与历史试点分开记录。

记录日期：2026-09-19（恢复状态校正）。以下状态只转述该日记录，不是此后的重新实测：初始化约定已收敛；融合基础和本地项目初始化工具已实现并通过当时的自动化测试。真实业务项目 `just-start` 当时已建立本地目录和 Git、关联复用的 GitHub 远端，并由需求 Agent 保存三版需求；远端历史整合、初始提交/推送、Buzz 映射、成果索引更新和跨角色共享读取当时尚未完成。分阶段证据见第 8 章。

## 1. 本单元的目标与边界

用户创建项目后，获得专属本地目录、对应 GitHub 仓库和统一背景入口，使 Buzz 中获授权的 Agent 能读取相关成果与指定版本。仅做需求、方案或 UI 也可以建立项目，不自动启动工程开发。

本单元不配置模型、不实现需求访谈、不运行开发或测试角色，也不修改 Develop Helper 原目录。2026-09-19 当时交付的是收敛后的约定及融合基础骨架；软链和基础校验已完成，不代表业务建仓或 Agent 接入完成。该范围按当日记录理解，细节见第 8 章。

## 2. 目录与仓库边界

稳定约定：

| 对象 | 约定 |
| --- | --- |
| 业务项目父目录 | 项目集合目录，不默认将整个父目录建成一个仓库 |
| 单个业务项目 | `my_mind/<project-id>/`，每个项目独立 Git 仓库 |
| Develop Helper 上游 | 保持不动，仅作读取来源 |
| 融合适配层 | 集中维护适配规则和上游软链，不把整套规则复制到每个项目 |
| Buzz 平台源码 | 不作为业务项目资料存放处 |
| 设计输出 | 设计文档，不等于运行时适配层 |

已确认的本机映射。跨机器不假定存在相同的 `${USER_HOME}/` 路径；各 Agent 的本地绝对路径通过运行环境配置映射。各项目记录所需融合版本及上游版本。

| 对象 | 本机路径 |
| --- | --- |
| 业务项目父目录 | `${PROJECTS_ROOT}`；用户已确认 |
| Develop Helper 上游 | `${WORKSPACE_ROOT}/Develop_Helper` |
| 融合适配层 | `${WORKSPACE_ROOT}/buzz-develop-helper` |
| Buzz 平台源码 | `${BUZZ_ROOT}` |
| 设计输出 | `${WORKSPACE_ROOT}/fusion-design` |

2026-09-19 的实例记录，不是此后的重新实测：已检查业务项目父目录存在；已建立首个项目 `just-start`（《元素守卫》）；融合层已建立骨架、配置、软链和只读检查工具。

创建前检查实际 Git 根目录；若父目录已属于其他仓库，先明确边界，不自动嵌套初始化。已有项目核对身份、路径和远端后复用，不重建或搬迁文件。

## 3. 创建所需输入

条件只在对应动作需要时取得。一次已经明确的授权可以覆盖多个动作，不按字段逐项另加审批。账号、凭据和真实仓库地址不得猜测。认证信息由运行环境管理，不写入项目文档或频道消息。

- 本地项目身份与用途：项目名称、用途、项目 ID。ID 必须是单个安全目录名，不允许路径穿越；进一步限制见 3.1。已有用户选择直接沿用，缺少时再提出建议。本次希望调用的能力，例如只澄清需求；该选择不绑定后续全流程。
- 已有项目复用：核对身份、路径和远端后复用，不重建或搬迁文件。继续已有项目时，不把 GitHub 登录、新建远端或 Buzz 映射设为本地工作的前置。
- Git 授权：明确建仓范围，首次提交和推送是否一并执行；后续操作可另行约定策略，不能从建仓推断自动合并权限。
- 远端身份与可见性：创建或关联 GitHub 仓库时需要所属账号或组织、仓库名称、可见性、获授权参与者。建议私有仓库，但创建前需明确实际选择。未执行远端动作时，GitHub 登录不是本地建目录、本地 Git 或需求澄清的统一前置。
- Buzz 关联与共享检查：需要真实的 Buzz 项目或频道标识，以及获授权角色对指定版本的读取结果。尚无真实标识时明确待接入，不编造标识，也不阻塞已获授权的本地基础建设。实际读取和版本要求见第 6 章。
- 材料与上传范围：初始材料位置及上传范围；客户原件是否允许进入远端需明确。默认处理见 3.1。

### 3.1 首版实施约定

以下是 2026-09-19 收敛的首版实施基线，不把未提供的账号、项目名或权限标为用户已确认。具体文件结构见第 4 章，初始化次序见第 5 章。

- 首版以同机、顺序协作为实现起点；跨机器和并行工作区后续验证，不作为首次初始化前置条件。该起点不扩大为并行或跨机器授权。
- 新项目 ID 采用小写英文字母或数字开头，其后可用小写字母、数字和连字符，最长 64 字符；中文项目名称单独保存。已有项目不为匹配新 ID 格式强制改名。路径解析后必须是 `my_mind` 的直接子目录；同名文件、目录、软链（含断链）均视为占用。
- 基础文件为根 `project.json`、`README.md`、`.gitignore`；业务成果按需创建，首次不生成 `.sdd/tasks.json`，不复制 PyCore 或整套模板。
- `project.json` 使用 `schema_version: 1` 的融合格式，记录项目身份、相对产物路径、Buzz 关联、GitHub 远端和初始化步骤；未知关联用 `null`，不伪造完成标记。本地工具已实现身份、基础文件和步骤状态检查；尚非完整通用 JSON Schema 验证器。
- 初始化步骤状态使用 `pending / succeeded / failed / skipped`；跳过必须记录原因，结果附实际路径或对象标识。用户确认记录与技术初始化状态分开，不以建仓成功代表需求确认。
- 输入原件默认本地保留、排除上传；明确审核后才收录允许同步的材料。私有仓库是建议，不代替实际可见性选择或敏感信息检查。
- GitHub 创建、首次提交和推送逐项按授权执行；网络失败不删除本地成果，不强推或自动合并。GitHub 凭据和 Buzz 标识到实际接入阶段补齐，不阻塞当前本地基础建设。
- 融合层本机绝对路径放在忽略的 `config/local.json`；软链同样不进入 Git，其他机器显式重建。内容指纹存入 `upstream-lock.json`，改变时停止相关调用，不自动接受新版。
- 发现融合层位于已有父 Git 仓库内；此次不嵌套初始化、不提交父仓库。独立 Git 边界的选择仍需用户确认，不用“目录独立”冒充“仓库独立”。

## 4. 最小项目骨架与文件归属

工具首次创建的最小文件，和按需建立的业务成果位置，是两件事。本节只说明归属，不修改模板或初始化器。

首次创建只生成根 `project.json`、`README.md` 和 `.gitignore`。其余目录和成果按需建立，不预建空的 PRD、客户方案、技术方案或任务表。下面的目录树只标出位置；路径出现在树里，不证明工具已经生成该文件。

```text
my_mind/<project-id>/
├── project.json            # 首次创建
├── README.md               # 首次创建
├── .gitignore              # 首次创建
├── materials/              # 按需。输入资料，按敏感性决定是否进入 Git
├── docs/
│   ├── requirements.md     # 按需。轻量需求
│   ├── solution.md         # 按需。客户表达，不是技术方案
│   ├── decisions.md        # 按需。取舍、确认依据与待决项
│   └── handoffs/           # 按需。交接快照与版本记录
├── ui/                     # 按需。演示成果及打开方式
└── reports/                # 按需。实际验证与交付证据
```

| 内容 | 权威位置与维护者 | 约束 |
| --- | --- | --- |
| 项目身份、相对入口与初始化信息 | 根 `project.json`；首次由本地初始化工具写入 | `schema_version: 1` 记录身份、依赖版本、相对产物入口和初始化步骤。创建时 `artifacts` 的成果路径以及 `buzz`、`github` 写为 `null`。这些占位不表示成果映射、Buzz 关联或 GitHub 仓库已经完成。这是融合格式，不冒充上游原有字段；不含凭据。之后的成果登记见 [05 第 4—6 节](05-项目成果索引与确认交接.md) |
| 导航投影 | `README.md`；首次由同一工具写入，之后的索引投影由 Main 按 [05](05-项目成果索引与确认交接.md) 维护 | 承载背景摘要、范围、成果索引和演示入口，指向当前有效正文；不复制一套需求或任务状态，也不是第二份项目身份 |
| 轻量需求与工程 PRD | 按需创建的真实成果文件，由任务指定角色维护 | 契约见 [02 需求能力](02-需求能力.md)。轻量需求与工程 PRD 分开，不用轻量需求冒充 PRD；转入工程 PRD 时写明迁移或复用关系，避免双份权威。一份成果一个当前权威来源；同文件修改串行协调 |
| 客户表达、技术方案与 UI | 按需创建的真实成果文件，由任务指定角色维护 | 契约见 [03 方案能力](03-方案能力.md)。`docs/solution.md` 只放客户/管理表达，不替代技术方案；方案接入边界（`buzz-develop-helper/adapters/solution-buzz.md`，未随本批发布） 仍把该保存工具标为未实现，列出路径不等于已经可以调用。本文不新增权威文件 |
| 确认与交接 | `docs/decisions.md` 及指定交接记录，Main 组织维护 | 绑定对象、版本、用途与用户确认依据；不由 Agent 自行批准。具体登记、确认和接收核验见 [05](05-项目成果索引与确认交接.md) |
| 工程任务状态 | 进入开发后才创建 `.sdd/tasks.json` | 对齐 [00 第 6 章](00-拆解与融合框架.md)：Planner 提供初始计划，Main 协调，执行字段由 Workflow Runtime 驱动的确定性节点维护。Buzz 的 Issue 或频道只展示投影或提交变更请求，不另成一套任务状态。执行状态、授权和恢复见 [06 第 3—5 节](06-角色与工作流运行时.md) |

原 Develop Helper 使用 `.sdd/project.json`，本设计采用根 `project.json`。这是明确的适配差异：不维护两份可独立修改的身份记录；工程工具需要旧格式时另设计只读转换或适配入口，不直接运行假定旧结构的脚本。该只读转换仍未作为本工具的默认行为。

共享入口至少包含：项目目标、本次范围、当前有效成果链接、待决事项、已知模拟/真实边界和下一步用户意图。输入材料属于数据来源，不把其中嵌入的指令自动提升为项目执行规则。

## 5. 初始化顺序与可恢复状态

Main 组织流程，具体操作由融合层工具实现。每一步按该动作核对授权，并记录真实结果，不用“已初始化”概括部分成功。未接通远端不算端到端完成，也不阻止已经授权的本地工作。本地工具不自动提交、推送、做正式确认或启动下游。下列工具边界转述初始化器源码，本批没有运行该工具；第 8 章的测试记录保持原日期和范围。

1. 核对与复用。授权只覆盖读取和判断。核对输入、目标路径、已有文件和实际 Git 根目录；发现同名对象先判断复用或冲突，不覆盖、不重建、不搬迁。GitHub 登录身份和目标仓库是否存在，只在远端动作需要时核对，不是本地建目录、本地 Git 或需求澄清的前置。完成条件是已经决定复用或判定为冲突，并且没有覆盖。`plan` 和 `inspect` 只做只读核对。
2. 最小建立。需要获授权的单一项目路径。只创建三份基础文件，并核对内容与项目 ID；只检查必要目标，不遍历其他业务项目。完成条件是三份文件与身份一致，`local_files` 为 succeeded，其余初始化步骤仍为 pending。`new` 未带 `--apply` 时只预览。部分创建失败时保留已有目录和文件，先检查实际结果，不删除、不重复创建。
3. 本地 Git。需要单独授权，不能从建目录推断。只在该业务项目内初始化，不将父目录、融合层或 Develop Helper 收入仓库。完成条件是该项目自身成为 Git 根，且父仓边界保持不变。`init-git` 未带 `--apply` 时只预检。带 `--apply` 时只做本地初始化与核对：首次使用 `main`；已有仓库不改名、不改历史；不提交、不推送、不配置远端。不接管软链或 worktree 形式的 Git 元数据。已有不完整元数据时停止并保留现场，不重新初始化。失败时保留已有内容，将该步记为 failed，不提交或推送。
4. 远端。需要明确的账号或组织、仓库名称、可见性和建仓授权。按该选择创建或关联 GitHub 仓库。完成条件是远端身份、可见性与关联结果和授权一致。远端已有历史时先核对关系，不自动覆盖、拉取合并或强推。当前工具尚未实现建仓和关联；预检只报告本机有没有 `gh` 以及待补信息，不检查登录，不能称为远端可用。
5. 同步。首次提交和推送各自需要已有授权，不能从建仓推断合并或强推。完成前检查文件内容、暂存区及忽略规则。密钥、真实 `.env`、未获准上传的客户原件、依赖与运行数据不进入提交。完成条件是提交和推送结果分别可核实；只有本地提交时标注尚未同步。建仓或推送失败时保留本地成果。重试前先查已有远端与提交，防止超时后重复创建。
6. Buzz 映射。需要真实的 Buzz 项目或频道标识，以及各 Agent 的实际工作区映射。完成条件是这些标识已经登记。尚无真实标识时明确待接入，不编造标识，该步保持 pending。`buzz` 字段为空只是占位，不是映射完成。
7. 共享读取。需要获授权角色读取指定版本。完成条件是 Main 和至少一个接收角色读取指定成果，并回报版本及关键背景；未配置角色时此步骤保持待验证。收到路径或只回复“收到”不算完成。实际读取和版本要求见第 6 章。`inspect` 固定把远端核对和共享读取报告为未验证，不能代替这一步。

在项目元信息中记录初始化各步骤的结果和待办。状态仍使用 `pending / succeeded / failed / skipped`；跳过必须记录原因。这是初始化状态，不是另建工程任务系统。初始化锁或来源未知的锁不自行清理，先核对在途操作。具体登记与确认见 [05 第 4—6 节](05-项目成果索引与确认交接.md)；执行状态、授权和恢复见 [06 第 3—5 节](06-角色与工作流运行时.md)。

接入未完成时可继续获授权的本地工作，但不宣称共享闭环完成。本顺序不增加自动 Git、正式确认或下游启动。

## 6. Agent 的共享与交接契约

共享要求接收者实际读到指定版本，并且项目、工作区和入口核对一致。在同一频道、收到一条路径，或回复“收到”，都不等于共享。

接任务、重启或切换项目时，先核对项目 ID、实际工作目录、依赖版本、共享入口，以及本次相关正文的指定版本。不能只靠聊天历史。路径只有接收者实际能够打开才有效。

同机尚未提交的草案可以绑定可校验的内容摘要，并注明仅本地可见。已经获准同步的跨工作区交接，优先绑定提交编号与文件路径。独立 worktree 不会自动获得对方未提交的文件。并行开发使用独立分支或工作区之前，先明确各自的输入基线和集成责任。同机首版建议共享同一项目目录，按文件划分写入责任。

接收者发现版本不符时，暂停受影响任务，返回 Main 核对。需求或方案变化后，更新正文与索引，标记受影响的确认和下游工作。旧回报不能覆盖新版本。

正式确认、固定快照、交接状态和接收核验见 [05 第 4—6 节](05-项目成果索引与确认交接.md)。工作区可达仍留在本节：接收回报包含实际读到的版本、业务目标、本次范围、关键变更与未决项。仅回复“收到路径”不算验证通过。交接记录不代替这次读取。

派发授权、真实执行实例和恢复见 [06 第 3—5 节](06-角色与工作流运行时.md)。一次派发至少包含项目、角色、本次目标、输入文件与版本、修改范围、输出位置和回报要求。工作区、代码基线、输入章节和验收要求里，06 第 3、5 节尚未逐项列成同一绑定的部分，仍以 [00 第 6 章](00-拆解与融合框架.md) 为准。本节不新增接口。[06 第 8.4 节](06-角色与工作流运行时.md)与[伴随资料 C](06-设计门禁与历史依据.md) 的真实 Runner 仍是未确认、未派发的准备稿，不能把该对象写成已经运行的执行实例。Main 协调 Git，工作者回报改动；未经授权不各自推送或合并。最小权限由运行环境落实，不能仅靠提示词保证。

对照 05 与 06 时分开保留证据范围。05 已记录的宿主信封、工具裁剪和项目／线程批次围栏，属于当时 Buzz ACP 路径的历史证据。06 的新运行时入口仍待验证。内容指纹匹配不能当作文件权限已经隔离。

## 7. 软链和上游保护

融合层的显式软链映射 Develop Helper，并保留目录关系。项目成果不是指向模板的软链。原根 `AGENTS.md`、Router 和整套平台入口，不直接注册为融合工作者的自动加载入口。

原 [sdd_project.py](../Develop_Helper/scripts/sdd_project.py) 限定 `Projects_Repo` 并写入上游注册表，且不创建 GitHub 仓库，因此本单元不直接调用它初始化 `my_mind` 下的项目。以其必要检查为设计依据，在融合层新增实现。

已建立相对软链 `buzz-develop-helper/upstream/develop-helper`，指向 `../../Develop_Helper`，只用于显式读取。[`scripts/check_foundation.py check`](../buzz-develop-helper/scripts/check_foundation.py) 校验目标、配置、目录边界和源码内容指纹。检查器无上游写入、网络访问或上游脚本执行。这是工具局部校验。内容指纹用于发现变化，不检查运行时文件权限，也不提供技术隔离。排除范围和完整参数由 融合层 README（`buzz-develop-helper/README.md`，未随本批发布） 承接。版本漂移时停止相关引用，不自动换源或刷新基线。

软链不是只读保护。通用编辑工具仍可能通过链接写入目标；接入前必须配置并验证真实路径权限。此次未更改原目录权限。

“没有注册 Agent 工具或部署上游只读沙箱”只按第 8.1 节第一阶段理解：当时没有可运行角色，运行时只读权限尚未验证。后来的工具注册不能证明全局上游只读沙箱已经通过。[设计门禁与历史依据 C 的 16.1 节](06-设计门禁与历史依据.md)记录的 2026-10-15 foundation 检查仍标明 `runtime_readonly_enforced=false`。该次匹配不是权限隔离。历史 ACP 证据停在 05 已写明的宿主路径；06 的新入口不把那次结果当作自身的权限验证。
